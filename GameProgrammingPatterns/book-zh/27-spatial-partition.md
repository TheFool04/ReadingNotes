# 空间分区

**优化模式**

## 意图

*通过将对象存储在按位置组织的数据结构中，来高效地定位它们。*

## 动机

游戏让我们得以造访另一个世界，但那些世界与我们自己的世界往往并无太大不同——它们通常共享着与我们宇宙相同的基本物理法则和实体感。这正是为什么它们尽管只是由比特和像素构成，却依然能令人感到真实。

在这里，我们要关注的一种虚假现实是*位置*。游戏世界有着*空间*的感觉，对象存在于这片空间的某处。这体现在诸多方面：最显而易见的是物理——对象移动、碰撞和交互——但还有其他例子。音频引擎可能需要考虑声源与玩家之间的相对位置，使远处的声音更为低沉；在线聊天可能仅限于附近的玩家之间。

这意味着你的游戏引擎经常需要回答这样一个问题："这个位置附近有哪些对象？"如果每帧都要回答足够多次，它就会成为性能瓶颈。

### 战场上的兵卒

假设我们正在制作一款即时战略游戏。两支各有数百个单位的军队将在战场上厮杀交锋。战士们需要知道要向哪个附近的敌人挥刀。处理这一问题的朴素方式，是遍历每一对单位，查看它们彼此之间的距离：

```cpp
void handleMelee(Unit* units[], int numUnits)
{
  for (int a = 0; a < numUnits - 1; a++)
  {
    for (int b = a + 1; b < numUnits; b++)
    {
      if (units[a]->position() == units[b]->position())
      {
        handleAttack(units[a], units[b]);
      }
    }
  }
}
```

这是一个双重嵌套循环，每层循环都在遍历战场上<span name="all">所有</span>单位。这意味着每帧需要执行的成对比较次数，随单位数量的*平方*增长。每新增一个单位，都需要与*所有*之前的单位进行比较。单位数量一旦庞大，就会失控。

> **注：** 内层循环其实并不遍历所有单位，只遍历外层循环尚未访问过的那些——这样可以避免每对单位被比较*两次*（分别以不同顺序）。如果 A 和 B 之间的碰撞已经处理过，就不需要再检查 B 和 A 之间的碰撞了。但从大 O 表示法的角度看，这依然是 *O(n²)*。

### 划定战线

我们遇到的问题在于，单位数组没有任何内在的顺序。要找到某个位置附近的单位，必须遍历整个数组。现在，假设我们将游戏稍加简化：把二维*战场*变成一维*战线*。

*（图示：一条数轴，各单位位于不同坐标上。）*

在这种情况下，我们可以按照单位在战线上的位置*排序*数组，从而让事情变得简单。完成排序后，就可以使用类似<span name="array">[二分查找](http://en.wikipedia.org/wiki/Binary_search)</span>的方法来找到附近的单位，而无需扫描整个数组。

> **注：** 二分查找的时间复杂度为 *O(log n)*，这意味着找到所有交战单位的复杂度从 *O(n²)* 降低到了 *O(n log n)*。如果使用[鸽巢排序](http://en.wikipedia.org/wiki/Pigeonhole_sort)（pigeonhole sort）之类的算法，甚至可以进一步降低至 *O(n)*。

这一思路显而易见：如果我们将对象存储在按位置组织的数据结构中，就能更快地找到它们。本模式正是将这一思想应用于超过一个维度的空间。

## 模式描述

对于一组**对象**，每个对象都有一个**在空间中的位置**。将它们存储在一个按位置组织的**空间数据结构**中。这个数据结构让你能够**高效地查询位于某个位置或其附近的对象**。当对象的位置发生改变时，**更新空间数据结构**，使其能够继续找到该对象。

## 使用场景

这一模式被广泛用于存储活跃的、运动的游戏对象，以及游戏世界的静态美术资产和几何体。复杂的游戏往往针对不同类型的内容使用多种空间分区方案。

使用这一模式的基本前提是：你有一组对象，每个对象都有某种位置，且按位置查找对象的查询操作足够频繁，已经对性能造成了影响。

## 注意事项

空间分区的存在，是为了将 *O(n)* 或 *O(n²)* 的操作降低到可以接受的范围内。对象*越多*，其价值就越显著。反之，如果你的 *n* 足够小，可能根本不值得为此大费周章。

由于这一模式涉及按位置组织对象，*改变*位置的对象处理起来会更麻烦。你需要<span name="hash-change">重新组织</span>数据结构，以在新位置追踪对象，这既增加了代码复杂度，也消耗了 CPU 周期。务必确保这种权衡是值得的。

> **注：** 想象一个哈希表，其中被哈希对象的键会自发地改变——这样你就能体会到为什么这很棘手了。

空间分区还需要为其簿记数据结构额外占用内存。像许多优化手段一样，它以内存换速度。如果你的内存比 CPU 周期更紧张，这可能得不偿失。

## 示例代码

模式的本质在于*变化*——每种实现都会有所不同，空间分区也不例外。与其他模式不同的是，这些<span name="variations">变体</span>大多有完善的文献记录，学术界热衷于发表证明性能提升的论文。由于我只关心模式背后的概念，这里将展示最简单的空间分区形式：*固定网格*（fixed grid）。

> **注：** 本章最后一节列出了游戏中最常用的几种空间分区结构。

### 一张方格纸

想象整片战场。现在，像铺一张方格纸一样，在其上叠加一层固定大小的方格网格。我们不再把单位存储在单一数组中，而是将它们放入这张网格的各个格子里。每个格子存储位置在该格子边界内的单位列表。

*（图示：一个网格，各单位分布在不同格子中，部分格子里有多个单位。）*

在处理战斗时，我们只考虑同一格子内的单位。我们没有将游戏中的每个单位与其他所有单位进行比较，而是将战场*分区*成了一个个规模更小的迷你战场，每个迷你战场内的单位数量要少得多。

### 由链表串联的单位网格

好，让我们开始编码。首先做一些准备工作。以下是我们基本的 `Unit`（单位）类：

```cpp
class Unit
{
  friend class Grid;

public:
  Unit(Grid* grid, double x, double y)
  : grid_(grid),
    x_(x),
    y_(y)
  {}

  void move(double x, double y);

private:
  double x_, y_;
  Grid* grid_;
};
```

每个单位都有一个（二维）位置，以及一个指向其所在 `Grid`（网格）的指针。我们将 `Grid` 设为友元类，因为接下来会看到，当单位位置改变时，它必须与网格配合完成一套精细的更新操作。

以下是网格的大致结构：

```cpp
class Grid
{
public:
  Grid()
  {
    // Clear the grid.
    for (int x = 0; x < NUM_CELLS; x++)
    {
      for (int y = 0; y < NUM_CELLS; y++)
      {
        cells_[x][y] = NULL;
      }
    }
  }

  static const int NUM_CELLS = 10;
  static const int CELL_SIZE = 20;
private:
  Unit* cells_[NUM_CELLS][NUM_CELLS];
};
```

注意每个格子只是一个<span name="stl">指针</span>，指向一个单位。接下来，我们为 `Unit` 添加 `next` 和 `prev` 指针：

```cpp
class Unit
{
  // Previous code...
private:
  Unit* prev_;
  Unit* next_;
};
```

这让我们可以将单位组织成[双向链表](http://en.wikipedia.org/wiki/Doubly_linked_list)，而非数组。

*（图示：一个格子指向一条由单位构成的双向链表。）*

网格中的每个格子指向该格子内单位链表的第一个单位，每个单位都持有指向链表中前后相邻单位的指针。稍后我们就会明白为什么这样设计。

> **注：** 在本书中，我一直刻意回避使用 C++ 标准库中的任何内置集合类型。我希望示例所需的外部知识越少越好，同时像魔术师"袖子里什么都没有"那样，让代码中发生的一切一目了然——细节至关重要，尤其是对于与性能相关的模式。但这只是我*讲解*模式时的选择。如果你在真实代码中*使用*这些模式，就省省吧，直接用几乎所有现代编程语言内置的集合类型。人生苦短，不必从头实现链表。

### 进入战场

首先要确保新单位创建时确实被放入网格。我们让 `Unit` 在其构造函数中处理这一逻辑：

```cpp
Unit::Unit(Grid* grid, double x, double y)
: grid_(grid),
  x_(x),
  y_(y),
  prev_(NULL),
  next_(NULL)
{
  grid_->add(this);
}
```

`add()` 方法的定义如下：

```cpp
void Grid::add(Unit* unit)
{
  // Determine which grid cell it's in.
  int cellX = (int)(unit->x_ / Grid::CELL_SIZE);
  int cellY = (int)(unit->y_ / Grid::CELL_SIZE);

  // Add to the front of list for the cell it's in.
  unit->prev_ = NULL;
  unit->next_ = cells_[cellX][cellY];
  cells_[cellX][cellY] = unit;

  if (unit->next_ != NULL)
  {
    unit->next_->prev_ = unit;
  }
}
```

> **注：** 用世界坐标除以格子大小，可以将世界坐标转换为格子坐标，再强制转换为 `int` 截取小数部分，就得到了格子索引。

这段代码像所有链表代码一样有些繁琐，但基本思路非常简单：找到单位所在的格子，然后将其添加到该格子链表的头部。如果那里已有单位列表，就将新单位链接到其前面。

### 刀光剑影

所有单位都各归其格之后，就可以让它们互相厮杀了。有了这张新网格，处理战斗的主方法变成这样：

```cpp
void Grid::handleMelee()
{
  for (int x = 0; x < NUM_CELLS; x++)
  {
    for (int y = 0; y < NUM_CELLS; y++)
    {
      handleCell(cells_[x][y]);
    }
  }
}
```

它遍历每个格子，并对其调用 `handleCell()`。可以看到，我们确实已经将战场分区成了一场场孤立的小规模交战。每个格子内的战斗由以下方法处理：

```cpp
void Grid::handleCell(Unit* unit)
{
  while (unit != NULL)
  {
    Unit* other = unit->next_;
    while (other != NULL)
    {
      if (unit->x_ == other->x_ &&
          unit->y_ == other->y_)
      {
        handleAttack(unit, other);
      }
      other = other->next_;
    }

    unit = unit->next_;
  }
}
```

抛开遍历链表时那些指针操作的繁琐细节不谈，注意这与我们最初那个朴素的<span name="nested">战斗处理方法</span>完全相同——它比较每对单位，看它们是否处于同一位置。

唯一的区别是，我们不再需要将战场上*所有*单位互相比较，而只比较近到同处一格的那些单位。这就是优化的核心所在。

> **注：** 从简单分析来看，我们似乎让性能*更差*了——从对单位的双重嵌套循环，变成了对格子再对单位的*三重*嵌套循环。妙处在于：内层的两重循环现在遍历的是数量更少的单位，足以抵消外层遍历格子的开销。不过，这在一定程度上取决于格子的粒度。格子过小，外层循环的开销就会开始显现。

### 冲锋向前

我们解决了性能问题，却又制造了一个新问题：单位现在被困在各自的格子里。如果一个单位移动到包含它的格子边界之外，该格子内的其他单位就再也找不到它了，但也没有其他格子能找到它。我们的战场被分割得太彻底了。

为了解决这个问题，每当单位移动时都需要做一些额外的工作。如果它越过了格子的边界，就需要将其从原格子中移除，添加到新的格子中。首先，我们为 `Unit` 提供一个改变位置的方法：

```cpp
void Unit::move(double x, double y)
{
  grid_->move(this, x, y);
}
```

对于电脑控制的单位，AI 代码会调用此方法；对于玩家的单位，则由用户输入代码调用。它所做的只是将控制权交给网格，网格随后执行：

```cpp
void Grid::move(Unit* unit, double x, double y)
{
  // See which cell it was in.
  int oldCellX = (int)(unit->x_ / Grid::CELL_SIZE);
  int oldCellY = (int)(unit->y_ / Grid::CELL_SIZE);

  // See which cell it's moving to.
  int cellX = (int)(x / Grid::CELL_SIZE);
  int cellY = (int)(y / Grid::CELL_SIZE);

  unit->x_ = x;
  unit->y_ = y;
  
  // If it didn't change cells, we're done.
  if (oldCellX == cellX && oldCellY == cellY) return;

  // Unlink it from the list of its old cell.
  if (unit->prev_ != NULL)
  {
    unit->prev_->next_ = unit->next_;
  }

  if (unit->next_ != NULL)
  {
    unit->next_->prev_ = unit->prev_;
  }

  // If it's the head of a list, remove it.
  if (cells_[oldCellX][oldCellY] == unit)
  {
    cells_[oldCellX][oldCellY] = unit->next_;
  }

  // Add it back to the grid at its new cell.
  add(unit);
}
```

这段代码有点长，但思路相当直接。第一段检查是否真的越过了格子边界。如果没有，只需更新单位位置，完事。

如果单位*确实*离开了当前格子，就从该格子的链表中将其摘除，然后重新插入网格。与添加新单位一样，这会将单位插入新格子的链表中。

这就是我们使用双向链表的原因——通过调整几个指针，就能非常快速地在链表中添加和移除单位。每帧都有大量单位在移动，这一点至关重要。

### 保持距离

这看起来相当简单，但我在一个地方作了弊。在刚才的例子中，单位只在*完全相同的*位置时才会交互。这对跳棋和国际象棋来说是对的，但对更写实的游戏来说则不然——通常还需要考虑攻击*距离*。

这一模式依然适用。与其只检查位置是否完全相同，我们改为：

```cpp
if (distance(unit, other) < ATTACK_DISTANCE)
{
  handleAttack(unit, other);
}
```

一旦涉及范围，就出现了一个需要考虑的边界情况：不同格子中的单位可能仍然近到足以相互影响。

*（图示：相邻格子中的两个单位，距离足够近，可以交互。）*

在这里，B 在 A 的攻击范围之内，尽管它们的中心点分属不同的格子。为了处理这种情况，我们不仅要比较同一格子中的单位，还要比较相邻格子中的单位。为此，首先将内层循环从 `handleCell()` 中分离出来：

```cpp
void Grid::handleUnit(Unit* unit, Unit* other)
{
  while (other != NULL)
  {
    if (distance(unit, other) < ATTACK_DISTANCE)
    {
      handleAttack(unit, other);
    }

    other = other->next_;
  }
}
```

现在有了一个函数，它接受一个单位和另一个单位列表，检查是否有命中。然后让 `handleCell()` 使用它：

```cpp
void Grid::handleCell(int x, int y)
{
  Unit* unit = cells_[x][y];
  while (unit != NULL)
  {
    // Handle other units in this cell.
    handleUnit(unit, unit->next_);

    unit = unit->next_;
  }
}
```

注意我们现在传入的是格子的坐标，而不仅仅是其单位链表。目前这与前一个例子并无不同，但接下来稍作扩展：

```cpp
void Grid::handleCell(int x, int y)
{
  Unit* unit = cells_[x][y];
  while (unit != NULL)
  {
    // Handle other units in this cell.
    handleUnit(unit, unit->next_);
    
    // Also try the neighboring cells.
    if (x > 0 && y > 0) handleUnit(unit, cells_[x - 1][y - 1]);
    if (x > 0) handleUnit(unit, cells_[x - 1][y]);
    if (y > 0) handleUnit(unit, cells_[x][y - 1]);
    if (x > 0 && y < NUM_CELLS - 1)
    {
      handleUnit(unit, cells_[x - 1][y + 1]);
    }

    unit = unit->next_;
  }
}
```

这些额外的 `handleUnit()` 调用负责在当前单位与<span name="neighbor">四个</span>相邻格子中的单位之间检测命中。如果相邻格子中的任何单位距离边界足够近，处于当前单位的攻击范围内，就能检测到命中。

> **注：** 当前格子用 `U` 表示，被检查的相邻格子用 `X` 表示（共四个）。*（图示：一个格子及其四个被检查的相邻格子示意图。）*

我们只检查*半数*相邻格子，原因与内层循环从当前单位*之后*开始的原因相同——避免每对单位被比较两次。设想一下，如果我们检查全部八个相邻格子会发生什么。

假设两个单位分处相邻格子，且距离近到可以互相攻击（就像前面的例子）。如果我们检查每个单位周围全部八个格子，会发生这样的情况：

1. 为 A 查找命中时，会检查其右侧的相邻格子，发现 B。于是记录一次 A 与 B 之间的攻击。
2. 为 B 查找命中时，会检查其*左侧*的相邻格子，发现 A。于是又记录一次 A 与 B 之间的攻击。

只检查半数相邻格子可以避免这一问题。至于检查*哪*半边，完全无所谓。

还有另一个边界情况需要考虑：这里我们假设最大攻击距离小于一个格子的大小。如果格子较小而攻击距离较大，可能需要扫描多行之外的若干相邻格子。

## 设计决策

有一份相对简短的、定义明确的空间分区数据结构清单，本可以在这里逐一介绍。但我选择按照它们的基本特性来组织讨论。希望当你日后真正了解四叉树（quadtree）、二叉空间分割（BSP，Binary Space Partitioning）等结构时，这有助于你理解它们*如何*工作、*为何*有效，以及如何在它们之间做出选择。

### 分区是层级式的还是平面式的？

我们的网格示例将空间分区成单一的一组平面格子。相比之下，层级式空间分区将空间划分为<span name="couple">少数几个</span>区域，若某区域仍包含大量对象，则再次细分。这一过程递归地进行，直到每个区域的对象数量少于某个上限为止。

> **注：** 通常将其分成 2、4 或 8 份——对程序员来说都是好看的整数。

**如果是平面分区：**

- *更<span name="simpler">简单</span>。* 平面数据结构更易于理解和实现。

  > **注：** 这是我在几乎每一章都会提到的设计要点，理由充分——能用简单方案就用简单方案，软件工程的很大一部分工作都是在与复杂性做斗争。

- *内存使用固定。* 由于添加新对象无需创建新分区，空间分区的内存用量通常可以提前确定。

- *对象位置变化时，更新速度更快。* 对象移动时，数据结构需要更新，以便在新位置找到该对象。对于层级式空间分区，这可能意味着需要调整层级的多个层级。

**如果是层级式分区：**

- *能更高效地处理空旷区域。* 设想前面例子中，战场的整个一侧完全空旷。我们会有大量空格子，既需要为其分配内存，每帧又要遍历它们。由于层级式空间分区不会细分稀疏区域，大片空旷的空间将保持为单一分区。我们不必遍历大量小分区，只需处理一个大分区。

- *能更高效地处理高密度区域。* 这是另一面：若大量对象聚集在一处，非层级式分区可能效果不佳——你最终会得到一个包含太多对象的分区，分区的效果可能还不如不分。层级式分区则会自适应地将该区域细分成更小的分区，让你回到每次只需考虑少数几个对象的状态。

### 分区是否依赖于对象集合？

在我们的示例代码中，网格间距是事先固定好的，我们只是将单位放入相应的格子。其他分区方案则是自适应的——它们根据实际对象集合及其在世界中的位置来选取分区边界。

目标是拥有一个*平衡的*分区，每个区域包含大致相同数量的对象，以获得最佳性能。设想在我们的网格示例中，所有单位都聚集在战场的一角。它们会全部落在同一个格子里，用于查找攻击的代码就会退化回原先那个我们试图解决的 *O(n²)* 问题。

**如果分区与对象无关：**

- *对象可以增量添加。* 添加一个对象意味着找到合适的分区并放入其中，因此可以逐一添加，不存在性能问题。

- *对象可以快速移动。* 分区固定时，移动一个单位只需将其从一个分区移除，添加到另一个。若分区边界本身会随对象集合变化，那么移动一个对象可能导致<span name="sort">边界</span>移动，进而引起大量其他对象需要迁移到不同的分区。

  > **注：** 这与排序二叉搜索树（如红黑树、AVL 树）直接类似：添加单个元素时，可能需要重新排序整棵树并移动大量节点。

- *分区可能不平衡。* 这种刚性的代价是，你对分区均匀分布的控制力较弱。如果对象聚集在一起，那个区域的性能就会变差，而空旷区域的内存又被白白浪费。

**如果分区自适应于对象集合：**

  BSP（二叉空间分割）和 k-d 树等空间分区结构会递归地划分世界，使每一半包含大致相同数量的对象。为此，在选取分割平面时需要统计两侧各有多少对象。包围体层级结构（Bounding Volume Hierarchy，BVH）是另一类空间分区，专门针对世界中的特定对象集合进行优化。

- *可以确保分区平衡。* 这不仅带来良好的性能，更带来*稳定*的性能：若每个分区的对象数量相同，则世界中所有查询的耗时都大致相同。在需要维持稳定帧率时，这种一致性可能比原始性能更为重要。

- *一次性对整个对象集合进行分区，效率更高。* 当对象的*集合*影响分区边界的位置时，最好在分区之前就将所有对象准备好。这正是此类分区更多用于在游戏中保持静止的美术资产和几何体的原因。

**如果分区与对象无关，但*层级*依赖于对象集合：**

  有一种空间分区值得专门提及，因为它兼具固定分区和自适应分区的优点：<span name="quad">四叉树</span>（quadtree）。

  > **注：** 四叉树对二维空间进行分区。其三维类比是*八叉树*（octree）——将一个*体积*分割成八个*立方体*。除了多了一个维度之外，工作原理与二维版本相同。

  四叉树以整个空间作为单一分区开始。若该空间中的对象数量超过某个阈值，就将其切分为四个更小的正方形。这些正方形的*边界*是固定的：始终将空间对半切分。

  然后，对这四个正方形中的每一个，递归地重复同样的过程，直到每个正方形中的对象数量很少为止。由于我们只对高密度的正方形进行递归细分，这种分区方式会自适应于对象集合，但分区本身并*不移动*。

  *（图示：四叉树分区过程，从左到右展示。）*

  - *对象可以增量添加。* 添加一个新对象，找到合适的正方形并放入。若此举使该正方形的对象数超过上限，则进行细分，将该正方形中的其他对象推入新的更小正方形。这需要一些工作，但工作量是*固定*的：需要移动的对象数永远少于对象上限。添加单个对象永远不会触发超过一次细分。移除对象同样简单：将对象从其所在正方形中移除，若父正方形的对象总数降至阈值以下，则可以折叠那些子细分。

  - *对象可以快速移动。* 这自然是上述特性的推论。"移动"一个对象就是一次添加加一次移除，而这两个操作在四叉树中都很快。

  - *分区是平衡的。* 由于任何给定的正方形中的对象数量都不会超过某个固定上限，即使对象密集地聚集在一起，也不会出现单个分区堆满大量对象的情况。

### 对象是否只存储在分区中？

你可以将空间分区视为游戏中对象*唯一*的存放之所，也可以将其仅视为一个加速查找的辅助缓存，同时另外维护一个直接持有对象列表的集合。

**如果它是唯一存储对象的地方：**

- *避免了维护两个集合的内存开销和复杂度。* 当然，存储一份永远比存储两份便宜。而且，如果有两个集合，就必须确保它们始终保持同步——每次对象被创建或销毁，都必须在两处同时添加或删除。

**如果还有另一个集合存储对象：**

- *遍历所有对象更快。* 如果这些对象是"活跃"的，需要进行某些处理，你可能会发现自己经常需要访问每个对象，不管其位置在哪里。设想在前面的例子中，大多数格子都是空的。为了找到非空格子而不得不遍历整个格子网格，可能是一种浪费。

  一个专门存储对象的第二集合，为你提供了直接遍历所有对象的途径。你拥有两个数据结构，分别针对各自的使用场景进行了优化。

## 参见

- 为了保持本章的高层次视角（且不至于太长！），我有意回避了对具体空间分区结构的详细讨论。你接下来的步骤，应该是学习几种常见的结构。尽管名字听起来有些吓人，它们实际上都出人意料地直观。常见的有：

  - [网格（Grid）](http://en.wikipedia.org/wiki/Grid_(spatial_index))
  - [四叉树（Quadtree）](http://en.wikipedia.org/wiki/Quad_tree)
  - [二叉空间分割（BSP）](http://en.wikipedia.org/wiki/Binary_space_partitioning)
  - [k-d 树（k-d tree）](http://en.wikipedia.org/wiki/Kd-tree)
  - [包围体层级结构（Bounding Volume Hierarchy）](http://en.wikipedia.org/wiki/Bounding_volume_hierarchy)

- 这些空间数据结构本质上是将已有的知名一维数据结构扩展到更多维度。了解它们的一维"亲戚"，有助于你判断它们是否适合你的问题：

  - 网格是持久化的[桶排序（Bucket Sort）](http://en.wikipedia.org/wiki/Bucket_sort)。
  - BSP、k-d 树和包围体层级结构是[二叉搜索树（Binary Search Tree）](http://en.wikipedia.org/wiki/Binary_search_tree)。
  - 四叉树和八叉树是[字典树（Trie）](http://en.wikipedia.org/wiki/Trie)。
