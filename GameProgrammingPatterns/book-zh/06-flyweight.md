# 享元模式

> 所属部分：重访设计模式

迷雾散去，一片古老而壮阔的原始森林显露在眼前。无数株铁杉（一种松科大乔木）拔地而起，高耸入云，共同撑起一座绿色的大教堂。层层叠叠的树冠如彩色玻璃般，将阳光折碎成一束束金色的光柱，在薄雾中漂浮流转。透过巨大的树干，你能依稀看出那片森林向远处无尽延伸。

这正是游戏开发者梦寐以求的奇幻场景，而实现这类场景，往往离不开一个名字再低调不过的模式：朴实无华的享元模式。

## 只见树木，不见森林

用寥寥数语描述一片茂密的树林易如反掌，但要在实时游戏中真正**实现**它，却是另一回事。当整片森林的树木铺满屏幕，图形程序员眼里看到的，是每六十分之一秒就得以某种方式推送到 GPU 上的数百万个多边形。

我们说的是成千上万棵树，每棵树都有包含数千个多边形的精细网格。就算内存够用，要渲染这些树，所有数据都得经过总线从 CPU 传输到 GPU。

每棵树关联着一大堆数据：

- 定义树干、树枝和枝叶形状的多边形网格（mesh）
- 树皮和叶片的纹理（texture）
- 这棵树在森林中的位置和朝向
- 大小、色调等调节参数，让每棵树看起来各不相同

用代码大致勾勒出来，大概长这样：

```cpp
class Tree
{
private:
  Mesh mesh_;
  Texture bark_;
  Texture leaves_;
  Vector position_;
  double height_;
  double thickness_;
  Color barkTint_;
  Color leafTint_;
};
```

数据量不小，其中网格和纹理尤其庞大。如果把整片森林的这些对象全部一次性推送给 GPU，一帧根本吃不消。幸好，有一个行之有效的老办法来应对这个问题。

关键的观察是：虽然森林里可能有成千上万棵树，但它们大多长得相似。它们很可能都使用**相同**的网格和纹理。这意味着这些对象里的大部分字段，在所有实例之间是**相同**的。

> 除非你疯了，或者是个亿万富翁，才会给美术团队拨出预算让他们为整片森林里的每一棵树单独建模。

> （图示：一排树，每棵树各自拥有网格、树皮、叶片、参数和位置。注意小方框里的数据对每棵树都是一样的。）

我们可以把对象一拆为二，明确地反映这一点。首先，把所有树共有的数据单独抽出来，放进一个独立的类：

```cpp
class TreeModel
{
private:
  Mesh mesh_;
  Texture bark_;
  Texture leaves_;
};
```

游戏只需要这个类的一个实例，因为没有理由把相同的网格和纹理在内存里存上一千份。然后，世界中每一棵树的**实例**只需持有一个指向共享 `TreeModel` 的**引用**。留在 `Tree` 里的，只有各实例独有的状态：

```cpp
class Tree
{
private:
  TreeModel* model_;

  Vector position_;
  double height_;
  double thickness_;
  Color barkTint_;
  Color leafTint_;
};
```

可以这样来理解这个结构：

> （图示：一排树，每棵树各自持有参数和位置，但共同指向一个包含网格、树皮和叶片的共享 Model。）

> 这看起来很像[类型对象](type-object.html)模式。两者都涉及将对象的部分状态委托给被多个实例共享的其他对象。不过，两个模式背后的意图不同。类型对象的目标是通过将"类型"提升为你自己的对象模型，来减少需要定义的类的数量——内存共享只是副产品。享元模式则纯粹是为了效率。

这样在主内存里存储数据固然不错，但对渲染没有直接帮助。森林要显示在屏幕上，还得先传输到 GPU。我们需要以显卡能理解的方式来表达这种资源共享。

## 千万实例

为了将推送给 GPU 的数据量降到最低，我们希望共享数据——`TreeModel`——只发送**一次**。然后，再分别推送每棵树实例的独有数据——位置、颜色和缩放比例。最后告诉 GPU："用那个模型来渲染这些实例的每一个。"

今天的图形 API（应用程序接口）和显卡恰好支持这一点。细节比较繁琐，超出了本书的范围，但 Direct3D（微软的图形渲染 API）和 OpenGL（跨平台的开源图形渲染 API）都支持一种叫做[**实例化渲染**](http://en.wikipedia.org/wiki/Geometry_instancing)（instanced rendering）的技术。

在这两个 API 中，你提供两条数据流：第一条是将被多次渲染的公共数据块——在我们的森林示例中，就是网格和纹理；第二条是实例列表及其各自的参数，用于在每次绘制时对第一条数据进行差异化处理。只需一次绘制调用，整片森林就生长出来了。

> 这个 API 直接由显卡硬件实现，这意味着享元模式或许是四人帮设计模式中唯一一个拥有真正硬件级别支持的。

## 享元模式

现在我们有了一个具体的例子打底，我来梳理一下通用模式。顾名思义，享元（Flyweight）在你有大量需要更轻量的对象时登场——通常是因为对象数量太多。

在实例化渲染的场景里，问题不在于对象占用太多内存，而在于把每棵树逐个推送过总线传给 GPU 要花太多**时间**，但基本思路是一样的。

这个模式的解决方法是把对象的数据拆成两类。第一类是非特定于某个对象**实例**的数据，可以在所有实例间共享。四人帮称之为**内在状态**（intrinsic state），我倾向于把它理解为"与上下文无关"的数据。在我们的例子里，就是树的几何网格和纹理。

其余的数据是**外在状态**（extrinsic state），是某个实例独有的。在这里，就是每棵树的位置、缩放和颜色。正如前面的代码所示，这个模式通过在对象出现的所有地方共享内在状态的一份副本来节省内存。

从目前看到的内容来说，这似乎只是基本的资源共享，算不上什么模式。部分原因是，在这个例子里，共享状态有一个清晰独立的**身份**：`TreeModel`。

我发现，当共享对象没有明确身份时，这个模式才显得更加微妙——也因此更加巧妙。在那些情况下，感觉就像一个对象神奇地同时出现在多个地方。让我再举一个例子。

## 扎根之地

这些树生长的地面，也需要在游戏中表示出来。地面可能有草地、泥土、山丘、湖泊、河流，以及你能想到的任何其他地形。我们将地面设计为**基于瓦片**的：世界表面是一个由微小格子组成的巨大网格，每个格子覆盖一种地形。

每种地形类型有若干影响游戏玩法的属性：

- 移动消耗，决定玩家穿越该地形的速度
- 是否是可乘船通行的水域地形
- 用于渲染的纹理

我们游戏程序员对效率有着近乎偏执的追求，绝不会把所有这些状态存储在世界上的**每一个**格子里。一种常见的做法是用枚举来表示地形类型：

> 毕竟，我们已经从那些树的教训中吸取了经验。

```cpp
enum Terrain
{
  TERRAIN_GRASS,
  TERRAIN_HILL,
  TERRAIN_RIVER
  // 其他地形……
};
```

然后，世界维护一个由这些枚举值组成的巨型网格：

```cpp
class World
{
private:
  Terrain tiles_[WIDTH][HEIGHT];
};
```

> 这里我用嵌套数组来存储二维网格。在 C/C++ 中这很高效，因为元素会紧密排列在一起。但在 Java 或其他托管内存的语言中，这实际上会生成一个行数组，其中每个元素是指向列数组的**引用**，内存友好度可能不尽如人意。
>
> 无论如何，真实代码最好将这个实现细节隐藏在一个好用的二维网格数据结构后面。这里这样写只是为了保持简洁。

要获取某个格子的实用数据，我们大概会这样做：

```cpp
int World::getMovementCost(int x, int y)
{
  switch (tiles_[x][y])
  {
    case TERRAIN_GRASS: return 1;
    case TERRAIN_HILL:  return 3;
    case TERRAIN_RIVER: return 2;
      // 其他地形……
  }
}

bool World::isWater(int x, int y)
{
  switch (tiles_[x][y])
  {
    case TERRAIN_GRASS: return false;
    case TERRAIN_HILL:  return false;
    case TERRAIN_RIVER: return true;
      // 其他地形……
  }
}
```

能用，但我觉得很丑。移动消耗和是否是水域在我看来是地形的**数据**，但这里它们被嵌进了代码里。更糟的是，单种地形类型的数据被分散在一堆方法中。如果能把这些数据封装在一起就好了——毕竟，这正是对象存在的意义。

能有一个真正的地形**类**就好了，比如这样：

```cpp
class Terrain
{
public:
  Terrain(int movementCost,
          bool isWater,
          Texture texture)
  : movementCost_(movementCost),
    isWater_(isWater),
    texture_(texture)
  {}

  int getMovementCost() const { return movementCost_; }
  bool isWater() const { return isWater_; }
  const Texture& getTexture() const { return texture_; }

private:
  int movementCost_;
  bool isWater_;
  Texture texture_;
};
```

> 你会注意到，这里所有方法都是 `const` 的。这不是巧合。由于同一个对象被用于多个上下文，如果你修改它，改动会同时出现在多个地方。
>
> 这很可能不是你想要的。通过共享对象来节省内存，应该是一种不影响应用可见行为的优化手段。正因如此，享元对象几乎总是不可变的。

但我们不想为世界上的每个格子都单独创建一个 `Terrain` 实例来承担开销。仔细看这个类，你会发现，其中实际上**没有任何**内容是特定于格子**位置**的。用享元的话来说，地形的**所有**状态都是"内在的"或"与上下文无关的"。

既然如此，每种地形类型就没有理由拥有超过一个实例。地面上每一块草地格子和其他草地格子完全相同。与其让世界是一个枚举或 `Terrain` 对象的网格，不如让它是一个指向 `Terrain` 对象的**指针**网格：

```cpp
class World
{
private:
  Terrain* tiles_[WIDTH][HEIGHT];

  // 其他内容……
};
```

使用相同地形的每个格子都会指向同一个地形实例。

> （图示：一排格子，每个格子指向共享的草地、河流或山丘对象之一。）

由于地形实例被多处使用，如果动态分配它们，其生命周期管理会稍显复杂。我们索性把它们直接存储在世界对象里：

```cpp
class World
{
public:
  World()
  : grassTerrain_(1, false, GRASS_TEXTURE),
    hillTerrain_(3, false, HILL_TEXTURE),
    riverTerrain_(2, true, RIVER_TEXTURE)
  {}

private:
  Terrain grassTerrain_;
  Terrain hillTerrain_;
  Terrain riverTerrain_;

  // 其他内容……
};
```

然后就可以像这样来铺设地面了：

```cpp
void World::generateTerrain()
{
  // 用草地填满地面。
  for (int x = 0; x < WIDTH; x++)
  {
    for (int y = 0; y < HEIGHT; y++)
    {
      // 随机散布一些山丘。
      if (random(10) == 0)
      {
        tiles_[x][y] = &hillTerrain_;
      }
      else
      {
        tiles_[x][y] = &grassTerrain_;
      }
    }
  }

  // 铺一条河流。
  int x = random(WIDTH);
  for (int y = 0; y < HEIGHT; y++) {
    tiles_[x][y] = &riverTerrain_;
  }
}
```

> 我承认，这不是世界上最出色的程序化地形生成算法。

现在，不再由 `World` 上的方法来访问地形属性，我们可以直接把 `Terrain` 对象暴露出来：

```cpp
const Terrain& World::getTile(int x, int y) const
{
  return *tiles_[x][y];
}
```

这样，`World` 就不再与各种地形细节耦合了。如果你想获取某个格子的某个属性，直接从对象上取就好了：

```cpp
int cost = world.getTile(2, 3).getMovementCost();
```

我们回到了使用真实对象的那种愉快 API，而开销几乎为零——一个指针的大小通常不比一个枚举值大。

## 性能如何？

我说"几乎"，是因为追求极致效率的人理所当然地想知道，这和用枚举相比怎么样。通过指针引用地形意味着一次间接查找：要获取移动消耗这样的地形数据，你得先沿着网格里的指针找到地形对象，再从那里取出移动消耗。追踪指针可能导致**缓存未命中**，进而拖慢速度。

> 关于指针追踪和缓存未命中的更多内容，参见[数据局部性](data-locality.html)章节。

一如既往，优化的黄金法则是**先做性能分析**。现代计算机硬件太过复杂，性能问题早已不是纯靠推理就能解决的了。在我为这一章所做的测试中，使用享元对象相比枚举没有任何性能损耗。享元实际上还明显更快——当然，这完全取决于其他数据在内存中的布局。

我**有把握**的是：不应该贸然否定享元对象。它让你兼得面向对象风格的便利和避免大量对象的高效。如果你发现自己在写枚举并频繁对它做 switch，不妨考虑换用这个模式。如果担心性能，至少先做性能分析，再考虑把代码改成维护性更差的风格。

## 另请参阅

- 在地形这个例子里，我们直接为每种地形类型创建了实例，并存储在 `World` 中——这让查找和复用共享实例变得简单。但在很多情况下，你不会想预先创建**所有**享元对象。

  如果无法预测实际需要哪些，按需创建会更好。为了获得共享的好处，当你请求一个享元时，先查看是否已经创建了一个完全相同的。如果有，直接返回那个实例。

  这通常意味着你要把构造过程封装在某个接口后面，让它先查找已有对象。这种隐藏构造函数的方式，正是[工厂方法（Factory Method）](http://en.wikipedia.org/wiki/Factory_method_pattern)模式的一个典型例子。

- 为了能返回之前创建的享元，你需要追踪已经实例化的对象池。顾名思义，[对象池](object-pool.html)是存储它们的好地方。

- 使用[状态模式](state.html)时，你经常会有一些"状态"对象，它们没有任何特定于正在使用该状态的状态机的字段。状态的身份和方法本身就足够用了。在这种情况下，你可以应用享元模式，在多个状态机中同时复用同一个状态实例，完全没有问题。
