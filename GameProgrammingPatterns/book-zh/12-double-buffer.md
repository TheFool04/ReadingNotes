# 双缓冲

**时序模式**

## 意图

*令一系列顺序执行的操作看起来瞬间完成或同时发生。*

## 动机

计算机在骨子里是<span name="sequential">顺序执行</span>的机器。它的强大之处在于能够将最庞杂的任务分解成一个个微小的步骤，逐一执行。然而，用户往往需要看到事情在一瞬间发生，或者多个任务同时完成。

> **注：** 随着多线程和多核架构的普及，这一说法正在慢慢改变，但即便拥有多个核心，同时运行的操作也只是少数。

一个典型的例子——也是每个游戏引擎都必须解决的问题——是渲染。游戏在绘制用户所见的世界时，是一次绘制一个部分的：远处的山脉、起伏的丘陵、树木，依次轮流。如果用户真的*看着*画面这样一块一块地出现，连贯世界的幻觉就会彻底破碎。画面必须平滑而快速地更新，呈现出一系列完整的帧，每一帧都仿佛瞬间显现。

双缓冲解决了这个问题，但要理解其原理，我们首先需要回顾一下计算机如何显示图像。

### 计算机图形学原理（简述）

像计算机显示器这样的<span name="scan">视频</span>显示设备，是逐像素绘制画面的。它从左到右扫描每一行像素，然后移到下一行。当它到达右下角后，再扫描回左上角重新开始。它的速度极快——每秒约六十次——快到我们的眼睛无法察觉扫描过程。对我们来说，看到的是一片静止的彩色像素场——也就是一张图像。

> **注：** 这里的解释经过了"简化"。如果你是底层硬件工程师，看到这里可能已经皱眉，那就随意跳到下一节吧——你已经掌握了理解本章其余内容所需的一切。如果你不是，我在这里的目标只是给你足够的背景，帮助你理解后续要讨论的模式。

你可以把这个过程想象成一根细小的水管，将像素喷送到显示器上。颜色数据从管子的一端进入，然后被逐一喷射到显示器上，每次一点颜色对应一个像素。那么，水管怎么知道哪里该喷什么颜色？

在大多数计算机中，答案是从*帧缓冲区*（framebuffer）读取。帧缓冲区是内存中的一个像素数组，一块 RAM，其中每几个<span name="color">字节</span>代表一个像素的颜色。水管在显示器上喷射时，逐字节从这个数组中读取颜色值。

> **注：** 字节值与颜色之间的具体对应关系，由系统的*像素格式*和*色深*描述。当今大多数游戏主机上，每个像素占 32 位：红、绿、蓝三个通道各 8 位，另有 8 位用于其他用途。

归根结底，要让游戏画面出现在屏幕上，我们所做的一切就是向那个数组写入数据。所有奇妙复杂的图形算法，最终都归结于此：向帧缓冲区设置字节值。但这里有个小问题。

前面说过，计算机是顺序执行的。如果机器正在执行我们的一段渲染代码，我们不指望它同时还在做别的事情。这大体上是对的，但有几件事*确实*会在程序运行期间同时发生。其中之一，就是视频显示器会在游戏运行期间*持续不断*地从帧缓冲区读取数据。这可能给我们带来麻烦。

假设我们想在屏幕上显示一张笑脸。程序开始遍历帧缓冲区，逐个着色像素。我们没有意识到的是，视频驱动程序正好在我们写入的同时读取帧缓冲区。当它扫过我们已经写入的像素时，笑脸开始出现——但随即它超过了我们的写入进度，移入了我们还没来得及写入的像素区域。结果就是*撕裂*（tearing），一种可怕的视觉 bug：屏幕上出现了半张绘制好的画面。

*（图示：帧渲染过程中的一系列画面。一个指针在写入像素，另一个在读取。读取指针超过了写入指针，开始读取尚未渲染的像素。）*

> **注：** 我们刚开始绘制像素，视频驱动程序也恰好开始从帧缓冲区读取（图1）。驱动程序最终追上了渲染器，并超过它，读取到我们尚未写入的像素（图2）。我们完成了绘制（图3），但驱动程序没有捕捉到这些新像素。最终结果（图4）是用户只看到了半张图。"撕裂"这个名字来源于画面看起来像是下半部分被撕掉了一样。

这就是为什么我们需要这个模式。程序逐像素地渲染，但我们需要显示驱动程序一次性看到所有像素——上一帧没有笑脸，下一帧它就完整地出现了。双缓冲解决了这个问题。下面我用一个类比来说明。

### 第一幕，第一场

想象我们的用户正在观看一场由我们自己制作的话剧。第一场结束、第二场开始时，我们需要更换舞台布景。如果我们让布景工人在场景结束后跑上台拖动道具，连贯场所的幻觉就会被打破。我们可以在换景时调暗灯光（现实中的剧院当然是这么做的），但观众仍然知道*有什么事正在发生*。我们希望场景之间没有任何时间间隔。

凭借一点地产资源，我们想出了这个聪明的解决方案：建造<span name="stage">*两座*</span>舞台，让观众两座都能看到。每座都有自己的灯光。我们称之为舞台 A 和舞台 B。第一场在舞台 A 上演出。与此同时，舞台 B 一片黑暗，布景工人正在布置第二场的场景。第一场一结束，我们就熄灭舞台 A 的灯光，点亮舞台 B。观众的目光转向新舞台，第二场立刻开始。

与此同时，布景工人已经在现在黑暗的舞台 *A* 上，拆除第一场的布景，布置第 *三* 场。第二场一结束，我们再将灯光切换回舞台 A。整场演出就这样持续下去，用暗着的那座舞台作为准备下一场景的工作区。每次场景切换，我们只需在两座舞台之间切换灯光。观众得到了一场没有停顿的连续演出，永远看不到布景工人的身影。

> **注：** 利用半镀银镜子和非常精妙的布局，你其实可以将两座舞台搭建在观众眼中完全相同的*位置*。灯光一切换，他们看的就是另一座舞台，但他们永远不需要转移视线。实现这一点就留给读者作为练习吧。

### 回到图形学

这<span name="sync">正是</span>双缓冲的工作原理，这一机制是你所见过的几乎所有游戏的渲染系统的基础。我们不再只有一个帧缓冲区，而是有*两个*。其中一个代表当前帧——类比中的舞台 A——是视频硬件正在读取的那个。GPU 可以随时随意地扫描它。

> **注：** 不过并非*所有*游戏和主机都这样做。内存有限的老式和简单主机会小心地将绘制与视频刷新同步，这相当棘手。

与此同时，我们的渲染代码正在向*另一个*帧缓冲区写入。这是我们黑暗的舞台 B。当渲染代码绘制完场景后，通过*交换*两个缓冲区来"切换灯光"。这告知视频硬件现在从第二个缓冲区读取，而非第一个。只要在刷新周期末尾完成这次切换，就不会出现撕裂，整个场景会瞬间完整地显示出来。

与此同时，旧的帧缓冲区现在可以重新使用了。我们开始在它上面渲染下一帧。就这么简单！

## 模式描述

一个**缓冲类**封装了一个**缓冲区**：一段可以被修改的状态。这个缓冲区是被增量编辑的，但我们希望所有外部代码都将这些编辑视为一次原子性的变更。为此，该类保持*两份*缓冲区实例：一个**后备缓冲区**和一个**当前缓冲区**。

从缓冲区*读取*信息时，始终读取*当前*缓冲区。向缓冲区*写入*信息时，写入*后备*缓冲区。修改完成后，一次**交换**操作将后备缓冲区和当前缓冲区瞬间对调，使新的缓冲区成为公开可见的版本。旧的当前缓冲区现在可作为新的后备缓冲区重复使用。

## 使用场景

这是那种"你一旦需要，自然就知道"的模式。如果某个系统缺少双缓冲，它可能看起来明显有问题（撕裂等），或行为不正确。不过，"你自然就知道"并不能给你太多指引。更具体地说，当以下所有条件都成立时，这个模式就适用：

- 有一段状态正在被增量修改。
- 该状态在修改过程中可能被访问。
- 我们希望阻止访问该状态的代码看到正在进行中的工作。
- 我们希望能够读取该状态，且不希望在写入期间等待。

## 注意事项

与较大的架构模式不同，双缓冲存在于较低的实现层面。因此，它对代码库其余部分的影响较小——大多数游戏代码甚至感知不到任何区别。但还是有几点需要注意。

### 交换本身需要时间

双缓冲需要在状态修改完成后执行一次*交换*步骤。该操作必须是原子性的——在交换期间，任何代码都不能访问*任一*状态。通常情况下，交换不过是赋值一个指针，速度极快。但如果交换所需的时间比修改状态本身还长，我们就没能得到任何好处。

### 我们必须拥有两份缓冲区

这一模式的另一个后果是内存使用量的增加。顾名思义，该模式要求你始终在内存中保存*两份*状态副本。在内存受限的设备上，这可能是一笔不小的代价。如果负担不起两个缓冲区，你可能需要寻找其他方式来确保状态在修改期间不被访问。

## 示例代码

理论说完了，让我们看看实践中如何运作。我们将编写一个非常基础的图形系统，让我们能够在帧缓冲区上绘制像素。在大多数主机和 PC 上，视频驱动程序提供了这个图形系统的底层部分，但在这里手动实现，可以让我们看清发生了什么。首先是缓冲区本身：

```cpp
class Framebuffer
{
public:
  Framebuffer() { clear(); }

  void clear()
  {
    for (int i = 0; i < WIDTH * HEIGHT; i++)
    {
      pixels_[i] = WHITE;
    }
  }

  void draw(int x, int y)
  {
    pixels_[(WIDTH * y) + x] = BLACK;
  }

  const char* getPixels()
  {
    return pixels_;
  }

private:
  static const int WIDTH = 160;
  static const int HEIGHT = 120;

  char pixels_[WIDTH * HEIGHT];
};
```

它提供了将整个缓冲区清为默认颜色的基本操作，以及设置单个像素颜色的操作。还有一个 `getPixels()` 函数，用于暴露存储像素数据的原始内存数组。示例中不会直接用到它，但视频驱动程序会频繁调用该函数，将缓冲区内存串流到屏幕上。

我们将这个原始缓冲区包装在一个 `Scene`（场景）类中。它的职责是通过在其缓冲区上进行一系列 `draw()` 调用来渲染内容：

```cpp
class Scene
{
public:
  void draw()
  {
    buffer_.clear();

    buffer_.draw(1, 1);
    buffer_.draw(4, 1);
    buffer_.draw(1, 3);
    buffer_.draw(2, 4);
    buffer_.draw(3, 4);
    buffer_.draw(4, 3);
  }

  Framebuffer& getBuffer() { return buffer_; }

private:
  Framebuffer buffer_;
};
```

> **注：** 具体来说，它绘制的是这幅艺术杰作：*（图示：一张像素化的笑脸。）*

每帧，游戏告知场景进行绘制。场景清空缓冲区，然后逐一绘制若干像素。它还通过 `getBuffer()` 暴露内部缓冲区，供视频驱动程序访问。

这看起来相当简单，但如果就这样放着不管，就会遇到问题。麻烦在于，视频驱动程序可以在*任意*时刻调用缓冲区的 `getPixels()`，甚至就在这里：

```cpp
buffer_.draw(1, 1);
buffer_.draw(4, 1);
// <- Video driver reads pixels here!
buffer_.draw(1, 3);
buffer_.draw(2, 4);
buffer_.draw(3, 4);
buffer_.draw(4, 3);
```

发生这种情况时，用户会看到笑脸的眼睛，但嘴巴会消失整整一帧。在下一帧，又可能在别的地方被中断。最终结果是令人痛苦的画面闪烁。我们用双缓冲来修复这个问题：

```cpp
class Scene
{
public:
  Scene()
  : current_(&buffers_[0]),
    next_(&buffers_[1])
  {}

  void draw()
  {
    next_->clear();

    next_->draw(1, 1);
    // ...
    next_->draw(4, 3);

    swap();
  }

  Framebuffer& getBuffer() { return *current_; }

private:
  void swap()
  {
    // Just switch the pointers.
    Framebuffer* temp = current_;
    current_ = next_;
    next_ = temp;
  }

  Framebuffer  buffers_[2];
  Framebuffer* current_;
  Framebuffer* next_;
};
```

现在 `Scene` 拥有两个缓冲区，存储在 `buffers_` 数组中。我们不直接从数组引用它们，而是通过两个成员 `next_` 和 `current_` 来指向数组中的各个元素。绘制时，我们向 `next_` 所指的后备缓冲区绘制。视频驱动程序需要获取像素时，始终通过 `current_` 访问*另一个*缓冲区。

这样，视频驱动程序永远看不到我们正在操作的那个缓冲区。拼图的最后一块，是在场景完成绘制后调用 `swap()`。它通过简单地互换 `next_` 和 `current_` 的指向来完成交换。下次视频驱动程序调用 `getBuffer()` 时，将得到我们刚刚绘制完成的新缓冲区，把我们最新绘制的内容呈现到屏幕上。撕裂和难看的闪烁就此消失。

### 不只用于图形

双缓冲所解决的核心问题是：状态在被修改的同时遭到访问。这有两种常见的成因。我们已经通过图形示例覆盖了第一种——状态被另一个线程或中断上的代码直接访问。

但还有另一种同样常见的成因：*进行修改的代码*本身正在访问它所修改的同一状态。这在物理和 AI 代码中尤为常见，因为那里的实体会彼此交互。双缓冲在这里同样大有用处。

### 人造蠢蛋

假设我们正在为一款以滑稽闹剧为主题的游戏构建行为系统。游戏中有一个舞台，上面跑着一群演员，整天搞各种恶作剧和闹剧。以下是基础演员类：

```cpp
class Actor
{
public:
  Actor() : slapped_(false) {}

  virtual ~Actor() {}
  virtual void update() = 0;

  void reset()      { slapped_ = false; }
  void slap()       { slapped_ = true; }
  bool wasSlapped() { return slapped_; }

private:
  bool slapped_;
};
```

每帧，游戏负责对演员调用<span name="update">`update()`</span>，使其有机会进行处理。关键在于，从用户的角度来看，*所有演员应当看起来是同时更新的*。

> **注：** 这是[更新方法](18-update-method.md)模式的一个示例。

演员之间也可以互动——如果所谓"互动"是指"互相扇巴掌"的话。更新时，演员可以调用另一个演员的 `slap()` 来扇它一巴掌，并调用 `wasSlapped()` 来判断自己是否被扇过。

演员们需要一个可以互动的舞台，让我们来搭建它：

```cpp
class Stage
{
public:
  void add(Actor* actor, int index)
  {
    actors_[index] = actor;
  }

  void update()
  {
    for (int i = 0; i < NUM_ACTORS; i++)
    {
      actors_[i]->update();
      actors_[i]->reset();
    }
  }

private:
  static const int NUM_ACTORS = 3;

  Actor* actors_[NUM_ACTORS];
};
```

`Stage` 让我们添加演员，并提供一个 `update()` 调用来依次更新每个演员。对用户来说，演员似乎是同时移动的，但在内部，它们是逐一更新的。

还有一点值得注意：每个演员的"被扇"状态在更新后立即被清除，这样演员对每一次扇巴掌只会响应一次。

接下来，让我们定义一个具体的演员子类。我们的喜剧演员很简单：他面对着另一个演员，每当他被扇——不管被谁扇——就会回手扇他所面对的那个演员。

```cpp
class Comedian : public Actor
{
public:
  void face(Actor* actor) { facing_ = actor; }

  virtual void update()
  {
    if (wasSlapped()) facing_->slap();
  }

private:
  Actor* facing_;
};
```

现在，让我们把几个喜剧演员放上舞台，看看会发生什么。我们设置三个演员，每人面对下一个，最后一个面对第一个，形成一个圆圈：

```cpp
Stage stage;

Comedian* harry = new Comedian();
Comedian* baldy = new Comedian();
Comedian* chump = new Comedian();

harry->face(baldy);
baldy->face(chump);
chump->face(harry);

stage.add(harry, 0);
stage.add(baldy, 1);
stage.add(chump, 2);
```

由此形成的舞台布局如下图所示。箭头表示演员的朝向，数字表示他们在舞台数组中的索引。

*（图示：Harry、Baldy、Chump 三人依次排列。Harry 的箭头指向 Baldy，Baldy 的箭头指向 Chump，Chump 的箭头指回 Harry。）*

我们先扇 Harry 一巴掌，触发整个流程，看看开始处理时会发生什么：

```cpp
harry->slap();

stage.update();
```

记住，`Stage` 中的 `update()` 函数依次更新每个演员，所以逐步执行代码，我们会看到如下过程：

```
Stage updates actor 0 (Harry)
  Harry was slapped, so he slaps Baldy
Stage updates actor 1 (Baldy)
  Baldy was slapped, so he slaps Chump
Stage updates actor 2 (Chump)
  Chump was slapped, so he slaps Harry
Stage update ends
```

仅仅一帧，我们对 Harry 的初始那一巴掌就传遍了所有喜剧演员。现在，为了增加变数，假设我们重新排列舞台数组中演员的顺序，但保持他们的朝向不变。

*（图示：同样的三人，同样的朝向箭头，但现在顺序变为 Chump、Baldy、Harry。）*

我们保留其他舞台设置不变，只把添加演员的那段代码替换成：

```cpp
stage.add(harry, 2);
stage.add(baldy, 1);
stage.add(chump, 0);
```

再次运行实验，看看会发生什么：

```
Stage updates actor 0 (Chump)
  Chump was not slapped, so he does nothing
Stage updates actor 1 (Baldy)
  Baldy was not slapped, so he does nothing
Stage updates actor 2 (Harry)
  Harry was slapped, so he slaps Baldy
Stage update ends
```

呃，完全不同了。问题很直接。当我们更新演员时，我们修改了他们的"被扇"状态——而这正是我们在更新过程中也*读取*的那个状态。由此，在更新初期对该状态的修改，会影响到同一更新步骤<span name="cascade">后期</span>的部分。

> **注：** 如果你继续更新舞台，会看到扇巴掌逐渐在演员之间级联传递，每帧传一次。第一帧，Harry 扇 Baldy；下一帧，Baldy 扇 Chump，依此类推。

最终结果是：一个演员响应被扇的时机——究竟是在*同一帧*还是*下一帧*——完全取决于这两个演员在舞台上碰巧如何排序。这违反了我们"演员看起来应当并行运行"的要求——单帧之内它们的更新顺序不应有任何影响。

### 带缓冲的扇巴掌

幸运的是，双缓冲模式可以帮上忙。这一次，我们不再维护一个整体性"缓冲区"对象的两份副本，而是在更细的粒度上进行缓冲：每个演员的"被扇"状态：

```cpp
class Actor
{
public:
  Actor() : currentSlapped_(false) {}

  virtual ~Actor() {}
  virtual void update() = 0;

  void swap()
  {
    // Swap the buffer.
    currentSlapped_ = nextSlapped_;

    // Clear the new "next" buffer.
    nextSlapped_ = false;
  }

  void slap()       { nextSlapped_ = true; }
  bool wasSlapped() { return currentSlapped_; }

private:
  bool currentSlapped_;
  bool nextSlapped_;
};
```

现在每个演员不再只有一个 `slapped_` 状态，而是有两个。就像之前的图形示例一样，当前状态用于读取，后备状态用于写入。

`reset()` 函数被替换成了 `swap()`。现在，在清空交换后的状态之前，它先将后备状态复制到当前状态，使其成为新的当前状态。`Stage` 也需要做一点相应的修改：

```cpp
void Stage::update()
{
  for (int i = 0; i < NUM_ACTORS; i++)
  {
    actors_[i]->update();
  }
  
  for (int i = 0; i < NUM_ACTORS; i++)
  {
    actors_[i]->swap();
  }
}
```

`update()` 函数现在先更新所有演员，*然后*再交换所有演员的状态。最终结果是：演员只会在被扇的*下一帧*才感知到这一巴掌。这样，无论演员在舞台数组中的顺序如何，他们的行为都将保持一致。从用户或任何外部代码的角度来看，所有演员都在一帧之内同步更新。

## 设计决策

双缓冲相当直接，我们目前所见的示例已经覆盖了你可能遇到的大多数变体。实现这一模式时主要有两个决策。

### 缓冲区如何进行交换？

交换操作是整个流程中最关键的步骤，因为在交换进行期间，我们必须阻止对两个缓冲区的一切读取和修改。为了获得最佳性能，我们希望这一步尽可能快。

**交换指向缓冲区的指针或引用：**

这是我们图形示例的做法，也是双缓冲图形最常见的解决方案。

- *速度快。* 无论缓冲区多大，交换只是几次指针赋值，在速度和简洁性上难以超越。

- *外部代码无法存储指向缓冲区的持久指针。* 这是主要限制。由于我们并不实际移动*数据*，本质上是在定期告知代码库的其余部分去别处查找缓冲区——就像最初的舞台类比一样。这意味着代码库的其余部分不能直接存储指向缓冲区内部数据的指针——片刻之后那个指针可能指向的就是错误的缓冲区了。

  在视频驱动程序要求帧缓冲区始终位于内存固定位置的系统上，这一点尤为棘手。在那种情况下，就无法使用这个选项了。

- *缓冲区上的现有数据来自两帧前，而非上一帧。* 连续的帧交替绘制在两个缓冲区上，帧间不复制数据，如下所示：

  ```
  Frame 1 drawn on buffer A
  Frame 2 drawn on buffer B
  Frame 3 drawn on buffer A
  ...
  ```

  你会注意到，当我们去绘制第三帧时，缓冲区上已有的数据来自第*一*帧，而非更近的第二帧。大多数情况下这不是问题——我们通常会在绘制前清空整个缓冲区。但如果我们打算<span name="blur">复用</span>缓冲区上的现有数据，就需要注意这些数据比我们预期的要老一帧。

  > **注：** 复用旧帧缓冲区数据的一个经典用途是模拟运动模糊（motion blur）。当前帧与少量上一帧渲染结果混合，产生一张更接近真实相机拍摄效果的图像。

**在缓冲区之间复制数据：**

如果无法将用户重定向到另一个缓冲区，唯一的选择就是将数据从后备帧实际复制到当前帧。这正是我们那些滑稽喜剧演员的做法。在那个例子中，我们选择这种方式，是因为状态——一个布尔标志——复制起来并不比指针更慢。

- *后备缓冲区上的数据只比当前帧老一帧。* 这是复制数据相比于在两个缓冲区之间来回切换的好处。如果我们需要访问之前的缓冲区数据，这种方式能给我们更新的数据。

- *交换可能需要更多时间。* 这当然是最大的缺点。交换操作现在意味着在内存中复制整个缓冲区。如果缓冲区很大，比如整个帧缓冲区，这会消耗相当多的时间。在此期间，任何代码都不能读写*任一*缓冲区，这是很大的限制。

### 缓冲区的粒度如何？

另一个问题是缓冲区本身如何组织——是单一的整体数据块，还是分布在一组对象中？我们的图形示例使用前者，演员们使用后者。

大多数情况下，你所缓冲的内容的性质会自然引导出答案，但也有一些灵活空间。例如，我们的演员本可以将各自的消息存储在一个统一的消息块中，通过各自的索引来引用。

**如果缓冲区是整体的：**

- *交换更简单。* 由于只有一对缓冲区，一次交换就够了。如果可以通过改变指针来完成交换，那么无论缓冲区多大，只需几次赋值就能完成整个缓冲区的交换。

**如果许多对象各持有一片数据：**

- *交换更慢。* 为了完成交换，需要遍历整个对象集合，逐一告知每个对象进行交换。

  在喜剧演员的例子中，这还可以接受，因为我们本来也需要清除后备的"被扇"状态——每片缓冲状态在每帧都需要被触及。如果我们不需要以其他方式触及旧缓冲区，可以使用一个简单的优化手段，在保持分布式缓冲区的同时获得整体缓冲区的性能。

  思路是将"当前"和"后备"指针的概念应用到每个对象上，将其转化为相对于对象的*偏移量*，如下所示：

  ```cpp
  class Actor
  {
  public:
    static void init() { current_ = 0; }
    static void swap() { current_ = next(); }

    void slap()        { slapped_[next()] = true; }
    bool wasSlapped()  { return slapped_[current_]; }

  private:
    static int current_;
    static int next()  { return 1 - current_; }

    bool slapped_[2];
  };
  ```

  演员通过使用 `current_` 作为索引来访问其当前的"被扇"状态，后备状态始终是数组中的另一个索引，可以通过 `next()` 计算出来。交换状态只需切换 `current_` 索引。巧妙之处在于，`swap()` 现在是一个*静态*函数——只需调用一次，*所有*演员的状态都会被交换。

## 参见

- 几乎所有图形 API 中都能找到双缓冲模式的身影。例如，OpenGL 提供了 `swapBuffers()`，Direct3D（微软的图形 API）有"交换链"（swap chains），而微软的 XNA 框架则在其 `endDraw()` 方法中完成帧缓冲区的交换。
