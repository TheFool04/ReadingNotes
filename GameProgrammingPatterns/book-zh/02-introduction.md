# 引言

五年级时，我和几个朋友偶然获准使用一间废弃的小教室，里面摆着几台破旧不堪的 TRS-80（Tandy/Radio Shack 于 1977 年推出的早期家用电脑）。一位老师想激发我们的兴趣，找来了几份简单的 BASIC（一种早期的高级编程语言）程序打印稿让我们捣鼓。

这些电脑的磁带驱动器都坏了，所以每次想运行什么程序，都得从头一个字母一个字母地敲进去。这让我们自然而然地偏爱那些只有寥寥几行的程序：

```basic
10 PRINT "BOBBY IS RADICAL!!!"
20 GOTO 10
```

> 也许只要打印次数够多，它就会神奇地成真。

即便如此，这个过程依然险象环生。我们根本不懂**怎么**编程，哪怕一个微小的语法错误也让我们束手无策。程序跑不起来就只能从头再来，这种情况发生得相当频繁。

在那沓打印稿的最后，藏着一个真正的庞然大物——一段占满了好几页纸的密密麻麻的代码。我们鼓起勇气去尝试它花了不少时间，但它实在令人难以抗拒——代码清单上方的标题写着"Tunnels and Trolls"（一款桌游）。我们完全不知道它是干什么的，但听起来像个游戏——还有什么比自己编写的电脑游戏更酷呢？

我们始终没能让它跑起来。一年后，我们搬离了那间教室。（很多年后，当我真正学会了一点 BASIC，才发现那不过是一个桌游的角色生成器，本身并不是游戏。）但命运就此定下——从那以后，我想成为一名游戏程序员。

十几岁时，家里买了一台 Macintosh（苹果公司的个人电脑），带着 QuickBASIC（微软推出的 BASIC 编程环境），后来又有了 THINK C（Mac 平台的 C 语言开发工具）。几乎每个暑假，我都泡在里面鼓捣游戏。自学既缓慢又痛苦。一开始总能比较顺利地弄出点东西——也许是一个地图界面，或一个小谜题——但随着程序越来越大，一切变得越来越难。

> 那些暑假里，我也花了不少时间在路易斯安那南部的沼泽里抓蛇捉龟。要不是外面热得要命，这本书说不定就成了一本爬行动物学专著，而不是编程书。

起初，挑战只是让程序跑起来。后来，问题变成了：怎样写出超出自己脑容量的程序？我不再只读"如何用 C++ 编程"，开始寻找那些讲如何**组织**程序的书。

时间快进几年——一个朋友递给我一本书：《设计模式：可复用面向对象软件的基础》。终于！这正是我从少年时代就一直在寻找的书。我一口气把它从头读到尾。我的程序依然问题重重，但看到别人也在挣扎、并且找到了解决办法，心里着实松了一口气。感觉自己终于不再是赤手空拳，手里有了几件**工具**。

> 那是我们第一次见面。认识不到五分钟，我就坐到他的沙发上，接下来几个小时完全无视他，只顾看书。我愿意相信，从那以后我的社交技能多少有所长进。

2001 年，我得到了梦寐以求的工作：Electronic Arts（美国知名游戏公司，简称 EA）的软件工程师。我迫不及待地想一探真正的游戏内部，看看专业人士是怎么把它们搭建起来的。像《麦登橄榄球》（Madden Football）这样的大型游戏，架构是怎样的？各个系统之间如何交互？他们怎么让一套代码库跑在多个平台上？

打开源代码的那一刻，既让人自愧不如，又充满惊喜。图形、AI、动画、视觉特效——每个领域都有令人叹为观止的代码。有些人知道如何把 CPU 的每一个时钟周期都榨干，物尽其用。有些事我连觉得**可能**都没想过，这些人在午饭前就已经做完了。

但这些精彩代码所依托的**架构**，却常常只是事后补丁。他们太专注于**功能**，以至于忽略了组织结构。模块之间耦合泛滥。新功能常常被硬塞进代码库里凑合能塞下的地方。在我那双幻灭的眼睛看来，很多程序员就算翻开过《设计模式》，也从没读到[单例模式](singleton.html)之后。

当然，现实并没有那么糟。我原本以为游戏程序员们坐在某座布满白板的象牙塔里，一连几周心平气和地讨论架构细节。现实是，这些代码出自赶着截止日期的人之手。他们已经尽力而为，而我慢慢意识到，他们的最好水平，往往真的很好。在游戏代码里浸泡越久，我在表面之下发现的精妙之处就越多。

遗憾的是，"藏在表面之下"往往是个相当贴切的形容。代码里埋着宝石，但很多人从它们身上踩过去，浑然不觉。我眼睁睁看着同事费力地重新发明已有的好方案，而他们需要的例子，就藏在他们脚下的那套代码库里。

这本书想解决的，正是这个问题。我把游戏开发中发现的最好的模式挖掘出来、打磨一番，呈现于此——这样我们就可以把时间花在发明新东西上，而不是**重新**发明已有的东西。

## 书里有什么

市面上已经有几十本游戏编程书了。为什么还要再写一本？

我见过的大多数游戏编程书，都属于以下两类之一：

- **领域专项书。** 这类书专注于游戏开发的某一具体方面，带你深入钻研。它们会教你 3D 图形、实时渲染、物理模拟、人工智能或音频。这些正是许多游戏程序员随着职业发展而深耕的方向。

- **完整引擎书。** 与之相对，这类书试图覆盖完整游戏引擎的方方面面，以构建适合特定类型游戏的完整引擎为目标，通常是 3D 第一人称射击游戏。

这两类书我都喜欢，但我认为它们都留下了一些空白。领域专项书很少告诉你，那块代码如何与游戏的其余部分互动。你也许是物理和渲染方面的高手，但你知道如何优雅地把它们连接在一起吗？

第二类书覆盖了这一点，但我发现完整引擎书往往过于整体化，也过于依赖特定游戏类型。尤其随着移动游戏和休闲游戏的兴起，我们正处在一个各种不同类型游戏百花齐放的时代。我们不再只是在克隆《雷神之锤》（Quake）了。当**你的**游戏不符合那个模板时，带你一步步搭建单一引擎的书就帮不上什么忙了。

我在这里尝试做的，更像是一份自助菜单。书中每一章都是一个独立的思路，可以直接应用到你的代码中。这样，你可以自由组合，找到最适合自己游戏的搭配。

> 同样采用这种自助式风格的，还有广受喜爱的 [Game Programming Gems](http://www.satori.org/game-programming-gems/)（《游戏编程精粹》）系列。

## 与《设计模式》的关系

书名里带有"模式"二字的编程书，显然都与经典著作《设计模式：可复用面向对象软件的基础》（Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides 著，人称"四人帮"——这名号听起来颇为不祥）有着渊源。

> 《设计模式》本身也有所师承。用一套模式语言来描述问题的开放性解决方案，这一理念来自 Christopher Alexander（及 Sarah Ishikawa、Murray Silverstein）所著的 [A Pattern Language](http://en.wikipedia.org/wiki/A_Pattern_Language)（《建筑模式语言》）。那本书谈的是建筑（就是真正意义上有楼有墙的那种建筑），但作者希望其他人能用同样的框架来描述其他领域的解决方案。《设计模式》正是四人帮在软件领域的这一尝试。

我把这本书命名为《游戏编程模式》，并非暗示四人帮的著作不适用于游戏开发。恰恰相反：本书中的[重访设计模式](design-patterns-revisited.html)部分涵盖了《设计模式》里的许多模式，只是着重探讨它们如何应用于游戏编程。

反过来，我认为本书同样适用于非游戏软件。我完全可以把这本书命名为《更多设计模式》，但我觉得游戏能提供更有趣的示例。你真的想再读一本关于员工档案和银行账户的书吗？

话虽如此，书中介绍的模式虽然在其他软件中也有用武之地，但我认为它们尤其契合游戏开发中常见的工程挑战：

- 时间与时序往往是游戏架构的核心。事情必须以正确的顺序、在正确的时机发生。
- 开发周期极度压缩，多名程序员需要能够快速构建并迭代丰富多样的行为，而不互相踩脚、不在代码库里到处留下脚印。
- 一旦所有行为定义完毕，它们就开始互相作用。怪物咬英雄，药水相互混合，炸弹无差别地炸飞敌我。这些交互必须在代码库不变成一团乱麻的前提下正常发生。
- 最后，性能在游戏中至关重要。游戏开发者在持续竞争，看谁能从硬件平台上榨取更多性能。省出几个时钟周期的技巧，可能意味着一款 A 级游戏和百万销量，或者帧率卡顿和怒气冲冲的评测者之间的差距。

## 如何阅读本书

《游戏编程模式》分为三大部分。第一部分介绍全书的背景与框架，也就是你正在读的这章，加上[下一章](architecture-performance-and-games.html)。

第二部分"[重访设计模式](design-patterns-revisited.html)"，梳理了四人帮著作中的几个模式。每章我都会分享自己对一个模式的理解，以及我认为它与游戏编程之间的关联。

最后一部分是全书的重头戏，介绍了我认为有价值的十三个设计模式，分为四大类：[时序模式](sequencing-patterns.html)、[行为模式](behavioral-patterns.html)、[解耦模式](decoupling-patterns.html)和[优化模式](optimization-patterns.html)。

每个模式都遵循统一的结构描述，方便你把本书当作参考手册，快速定位所需内容：

- **意图**：用一句话概括该模式，描述它意图解决的问题。放在最前面，是为了让你能快速翻阅全书，找到能帮你解决当前困境的模式。
- **动机**：描述一个将要应用该模式的示例问题。与具体算法不同，模式通常是抽象的，必须落到具体问题上才能成形。脱离示例讲模式，就像讲烘焙却不提面团。这一节提供的，正是供后续章节烘焙的面团。
- **模式详解**：从前面的示例中提炼出模式的本质。如果你想要一段干燥的教科书式定义，这里就是。如果你已经熟悉某个模式只是想温故知新，这里也是一个好的复习点。
- **适用场景** 与 **注意事项**：前者提供一些判断标准，告诉你什么时候该用这个模式、什么时候最好绕开它；后者则指出使用该模式时可能带来的后果和风险。
- **示例代码**：如果你和我一样，需要具体的例子才能真正**理解**一件事，这一节就是为你准备的。它会一步一步完整实现该模式，让你清楚地看到它是如何运作的。
- **设计决策**：模式与单一算法的区别在于它的开放性。每次使用同一个模式，实现方式往往各有不同。这一节正是在这个空间里展开，展示应用模式时可以考虑的不同选项。
- **另请参阅**：简短介绍该模式与其他模式的关联，并指向现实世界中使用它的开源代码。

## 关于示例代码

本书的代码示例使用 C++ 编写，但这并不意味着这些模式只在这门语言中有用，或者 C++ 比其他语言更适合它们。几乎任何语言都可以，尽管有些模式确实默认你的语言支持对象和类。

我选择 C++ 有几个原因。首先，它是商业游戏中最流行的语言，是这个行业的*通用语*。更重要的是，C++ 所基于的 C 语法，也是 Java、C#、JavaScript 以及许多其他语言的基础。就算你不懂 C++，只要稍加努力，理解这里的代码示例也不是难事。

本书的目标**不是**教你 C++。示例代码尽量保持简洁，并不代表良好的 C++ 风格或用法。阅读代码示例，是为了理解它所表达的思想，而不是代码本身。

特别要说的是，这些代码没有采用"现代" C++ 风格——也就是 C++11 及更新版本的风格。它不使用标准库，也几乎不用模板。这使得代码在 C++ 标准看来算是"差劲"的，但我希望通过保持精简，它对于来自 C、Objective-C、Java 以及其他语言的读者会更加友好。

为了避免在你已经见过的、或与当前模式无关的代码上浪费篇幅，示例中有时会省略部分代码。出现这种情况时，会用省略号标注缺失代码的位置。假设一个函数会做一些处理然后返回一个值，而当前讲解的模式只关心返回值，不关心具体处理过程，示例代码则会是这样：

```cpp
bool update()
{
  // 在此处理游戏逻辑……
  return isDone();
}
```

## 下一步去哪里

模式是软件开发中一个持续演变、不断扩展的领域。本书延续了四人帮开创的工作——记录并分享他们所见的软件模式。这项工作，在这些文字定稿之后，还会继续下去。

而你，是这个过程中不可或缺的一部分。当你发展出自己的模式，或者完善（乃至推翻！）本书中的模式时，你就在为整个软件社区做出贡献。如果你对书中内容有任何建议、勘误或其他反馈，欢迎联系我！
