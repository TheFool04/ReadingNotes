# 事件队列

**所属章节：解耦模式**

## 意图

*将消息或事件的发送时机与其被处理的时机解耦。*

## 动机

除非你住在极少数仍然没有互联网的地方，否则你大概早就听说过<span name="message">"事件队列"</span>了。如果没有，或许"消息队列"、"事件循环"或"消息泵"这些词会让你想起些什么。为了唤醒记忆，我们来看看这个模式的几种常见表现形式。

> **注：** 本章中大部分时候"事件"和"消息"可互换使用。当两者的区别重要时，我会明确指出。

### GUI 事件循环

如果你做过任何<span name="event-driven">用户界面</span>编程，那你对*事件*一定不陌生。每当用户与你的程序交互——点击按钮、展开菜单或按下某个键——操作系统就会生成一个事件。它把这个对象抛给你的应用程序，你的工作就是接住它，并将其与某些有趣的行为挂钩。

> **注：** 这种应用程序风格非常普遍，已被视为一种编程范式：[事件驱动编程](http://en.wikipedia.org/wiki/Event-driven_programming)。

为了接收这些信号，你的代码深处藏着一个*事件循环*，大致如下所示：

```cpp
while (running)
{
  Event event = getNextEvent();
  // Handle event...
}
```

对 `getNextEvent()` 的调用会把一条未处理的用户输入拉进你的应用程序。你将其路由到事件处理器，应用程序就像变魔术一样活了起来。有趣的地方在于，应用程序是在*它*想要的时候*主动拉取*事件的。当用户拨弄外设时，操作系统并不会直接跳转到你应用程序中的某段代码。

> **注：** 相比之下，来自操作系统的*中断*确实是那样工作的。中断发生时，操作系统会停止你的程序正在做的事，强制它跳转到中断处理程序。这种粗暴方式正是中断难以处理的原因。

这意味着当用户输入到来时，它需要有个地方存放，以免在设备驱动上报输入到你的应用程序调用 `getNextEvent()` 之间的这段时间里丢失。这个"地方"就是*队列*。

*（图示：事件队列。操作系统将 Shift、Down、Up、Click 事件依次入队，`getNextEvent()` 函数从队列中出队。）*

当用户输入到来时，操作系统将其加入未处理事件的队列。当你调用 `getNextEvent()` 时，它从队列头部取出最旧的事件，交给你的应用程序处理。

### 中央事件总线

大多数<span name="game-loop">游戏</span>并不像这样采用事件驱动的方式，但游戏通常会有自己的事件队列作为神经系统的主干。你会经常听到用"中央"、"全局"或"主"来描述它。它用于在那些希望保持解耦的游戏系统之间进行高层次的通信。

> **注：** 如果你想知道游戏为什么不采用事件驱动，翻开[游戏循环](13-game-loop.md)章节就能找到答案。

假设你的游戏有一个<span name="tutorial">新手引导</span>系统，用于在特定游戏事件发生后显示提示框。例如，玩家第一次击败一只丑陋的怪物时，你想弹出一个小气泡说："按 X 键拾取战利品！"

> **注：** 新手引导系统实现起来颇为棘手，而大多数玩家只会在很少的时间里用到游戏内的帮助，所以感觉好像不值得花这么多功夫。但在他们*确实*使用引导的那段时间里，它对于帮助玩家入门可能是无价之宝。

你的游戏玩法和战斗代码已经足够复杂了。你最不想做的事就是在里面塞满一堆触发引导的检查逻辑。取而代之，你可以有一个中央事件队列。任何游戏系统都可以向它发送消息，于是战斗代码每当你击杀一个敌人时就可以发送一个"敌人死亡"事件。

<span name="blackboard">类似地</span>，任何游戏系统也可以从队列中*接收*事件。新手引导引擎在队列中注册自己，表示它想接收"敌人死亡"事件。这样，"敌人死亡"这条信息就从战斗系统传递到了引导引擎，而两者不需要直接感知对方的存在。

> **注：** 这种实体可以向共享空间发布信息并被通知的模型，类似于 AI 领域的[黑板系统](http://en.wikipedia.org/wiki/Blackboard_system)。

*（图示：一个中央事件队列，战斗代码和引导代码都可以读写它。）*

我曾考虑过用这个作为本章其余部分的示例，但我一般不喜欢大型全局系统。事件队列不一定要用于整个游戏引擎的跨系统通信，在单个类或领域内部使用同样大有裨益。

### 说什么？

所以，我们换个例子，给游戏加上声音。人类主要是视觉动物，但听觉与情感和空间感密切相关。模拟出合适的回响能让黑色的屏幕感觉像一座巨大的山洞，恰到好处的小提琴慢板能让你的心弦随之共鸣。

为了让游戏有声有色，我们从最简单的方案开始，看看效果如何。我们添加一个小小的<span name="singleton">"音频引擎"</span>，提供一个通过标识符和音量来播放声音的 API：

> **注：** 虽然我几乎总是对[单例模式](http://c2.com/cgi/wiki?SingletonPattern)敬而远之，但这里可能是它合适的使用场景之一，因为机器通常只有一组扬声器。我采用了一种更简单的方式，直接把方法设为静态的。

```cpp
class Audio
{
public:
  static void playSound(SoundId id, int volume);
};
```

它负责加载对应的音频资源，找到一个可用的声道，然后开始播放。本章并不讨论某个具体平台的音频 API，所以我假设有一个在别处实现的音频 API 供我们使用。基于它，我们这样实现这个方法：

```cpp
void Audio::playSound(SoundId id, int volume)
{
  ResourceId resource = loadSound(id);
  int channel = findOpenChannel();
  if (channel == -1) return;
  startSound(resource, channel, volume);
}
```

我们把这段代码提交上去，创建几个音效文件，然后开始像音频仙女一样在代码库各处撒下 `playSound()` 调用。例如，在 UI 代码中，当选中的菜单项变化时，我们播放一个短促的提示音：

```cpp
class Menu
{
public:
  void onSelect(int index)
  {
    Audio::playSound(SOUND_BLOOP, VOL_MAX);
    // Other stuff...
  }
};
```

这样做之后，我们注意到有时切换菜单项时，整个画面会冻结几帧。我们遇到了第一个问题：

**问题一：API 会阻塞调用方，直到音频引擎完全处理完请求。**

我们的 `playSound()` 方法是*同步的*——在提示音从扬声器中响起之前，它不会返回给调用方。如果音效文件需要先从磁盘加载，这可能需要一段时间，而在此期间，游戏的其余部分都被冻结了。

暂且忽略这个问题，我们继续。在 AI 代码中，我们添加了一个调用，让敌人在受到玩家伤害时发出痛苦的嚎叫。没有什么比在虚拟生命上施加模拟伤害更让玩家心满意足的了。

它能运行，但有时当英雄发动一次猛烈攻击，同时命中两个敌人时，游戏会在同一帧内播放两次嚎叫声。<span name="hatsworth">如果</span>你了解音频，就知道混合多个声音等同于叠加波形。当这些是*相同*的波形时，效果就等同于*一个*声音播放了*两倍响*——震耳欲聋。

> **注：** 我在开发 [Henry Hatsworth in the Puzzling Adventure（一款 DS 平台解谜冒险游戏）](http://en.wikipedia.org/wiki/Henry_Hatsworth_in_the_Puzzling_Adventure)时就遇到了这个问题，我在那里采用的解决方案和本章介绍的类似。

在 Boss 战中还有一个相关问题：大量小怪四处乱跑制造混乱，而硬件同时能播放的声音数量是有限的。一旦超出上限，声音就会被忽略或截断。

要处理这些问题，我们需要统观所有声音请求，对它们进行聚合和优先级排序。然而，我们的音频 API 对每个 `playSound()` 调用都独立处理，它通过一个针眼来看请求，一次只看一个。

**问题二：无法批量处理请求。**

这些问题与下一个摆在我们面前的问题相比，简直是小菜一碟。至此，我们已经在代码库的许多不同游戏系统中散落了大量 `playSound()` 调用。但我们的游戏引擎运行在现代多核硬件上，为了利用这些核心，我们把这些系统分布在不同的线程上——渲染在一个线程，AI 在另一个，等等。

由于我们的 API 是同步的，它运行在*调用方的*线程上。当我们从不同的游戏系统调用它时，多个线程会并发地访问我们的 API。看看那段示例代码——有看到任何线程同步机制吗？我也没看到。

这尤其令人恼火，因为我们原本打算为音频设置一个*独立的*线程，而它就那么白白闲置着，其他线程则忙着互相踩踏、把事情搞砸。

**问题三：请求在错误的线程上被处理。**

这些问题有一个共同点：音频引擎把调用 `playSound()` 理解为"放下一切，现在立刻播放这个声音！"*即时性*才是根源所在。其他游戏系统在*它们*方便的时候调用 `playSound()`，但不一定是音频引擎方便处理该请求的时候。要修复这个问题，我们需要将*接收*请求与*处理*请求解耦。

## 模式结构

**队列**以先进先出的顺序存储一系列**通知或请求**。发送通知时将**请求入队并立即返回**。请求处理器随后在稍后的某个时间**从队列中处理条目**。请求可以被**直接处理**，也可以被**路由给感兴趣的各方**。这种方式在**静态层面**和**时间层面**都实现了**发送方与接收方的解耦**。

## 使用时机

如果你只想解耦消息的*接收方*与发送方，像[观察者模式](http://c2.com/cgi/wiki?ObserverPattern)和[命令模式](http://c2.com/cgi/wiki?CommandPattern)这样的模式能以更低的<span name="simple">复杂度</span>做到这一点。只有当你想在*时间层面*实现解耦时，才需要队列。

> **注：** 我在几乎每一章都提到这点，但值得反复强调：复杂度会拖慢你的步伐，所以要把简洁视为珍贵的资源。

我喜欢从推和拉的角度来思考。代码 A 希望另一段代码 B 来做某些工作。A 发起请求的自然方式是向 B *推送*该请求。

与此同时，B 处理该请求的自然方式是在*它自己*的运行周期中，在方便的时候*拉取*该请求。当一端是推模型、另一端是拉模型时，你就需要在它们之间放置一个缓冲区，这正是队列比更简单的解耦模式多提供的东西。

队列把控制权交给从它拉取数据的代码——接收方可以延迟处理、聚合请求或彻底丢弃它们。但队列这样做是以*剥夺*发送方的控制权为代价的。发送方所能做的只是把请求丢进队列，然后寄望于最好的结果。因此，当发送方需要得到响应时，队列并不合适。

## 注意事项

与本书中一些更为低调的模式不同，事件队列较为复杂，往往对我们游戏的架构产生深远影响。这意味着你需要认真思考是否——以及如何——使用它。

### 中央事件队列本质上是一个全局变量

这个模式的一种常见用途是作为类似"纽约中央车站"的东西，让游戏的所有部分都能通过它来路由消息。这是一个强大的基础设施，但*强大*并不总是意味着*好*。

费了不少周折，我们大多数人都通过惨痛的教训认识到：全局变量是有害的。当程序的任何部分都可以随意修改某段状态时，各种微妙的相互依赖就会悄然渗入。这个模式用一个漂亮的小协议把那些状态包裹起来，但它本质上仍然是全局的，所有风险犹在。

### 世界的状态可能在你不知情时发生变化

假设某些 AI 代码在一个虚拟小兵驾鹤西归时向队列发布了一个"实体死亡"事件。这个事件在队列中不知等待了多少帧，直到它终于排到队列头部被处理。

与此同时，经验系统想要统计女英雄的击杀数量，并根据她的战斗效率给予奖励。它接收每个"实体死亡"事件，并判断被击杀实体的种类和击杀难度，从而给出相应的奖励。

这需要用到世界中的各种状态。我们需要那个死去的实体来判断它有多难打。我们可能还想检查其周围环境，看看附近有哪些障碍物或小兵。但如果事件在稍后才被接收，这些信息可能已经消失了——实体可能已被释放，附近的敌人也可能溜走了。

当你接收到一个事件时，必须小心，不能假设*当前*的世界状态反映了*事件被触发时*的世界状态。这意味着队列中的事件往往比同步系统中的事件携带更多数据。在后者中，通知可以只说"发生了某件事"，然后接收方自行查看详情；而在队列中，那些转瞬即逝的细节必须在事件发送时就被捕获，以便稍后使用。

### 可能陷入反馈死循环

所有事件和消息系统都必须警惕循环问题：

1. A 发送一个事件；
2. B 接收它，并通过发送一个事件作为响应；
3. 那个事件恰好是 A 关心的，于是 A 接收到它，并在响应中再次发送一个事件……
4. 回到第 2 步。

当你的消息系统是*同步的*时，循环会很快被发现——它们会导致栈溢出并使游戏崩溃。而对于队列，异步性解开了调用栈，所以即使虚假事件在队列中<span name="log">来回涌动</span>，游戏也可能继续运行。一条常见的规避规则是：避免在*处理*事件的代码中*发送*事件。

> **注：** 在你的事件系统中加一点调试日志，大概也是个好主意。

## 示例代码

我们已经见过一些代码了。它并不完美，但具备基本正确的功能——我们想要的公共 API 和正确的底层音频调用。现在我们所要做的就是修复它的问题。

第一个问题是我们的 API 会*阻塞*。当某段代码播放声音时，在 `playSound()` 完成资源加载并真正开始驱动扬声器振动之前，它什么也做不了。

我们希望把这项工作延迟到稍后执行，让 `playSound()` 可以快速返回。为此，我们需要将播放声音的请求*具化（reify）*为一个对象——用一个小结构体来存储待处理请求的详细信息，这样我们就能把它保留到稍后再处理：

```cpp
struct PlayMessage
{
  SoundId id;
  int volume;
};
```

接下来，我们需要给 `Audio` 提供一些存储空间来跟踪这些待处理的播放请求。你的<span name="prof">算法学教授</span>可能会建议你使用某种令人兴奋的数据结构，比如[斐波那契堆（Fibonacci heap）](http://en.wikipedia.org/wiki/Fibonacci_heap)或[跳表（skip list）](http://en.wikipedia.org/wiki/Skip_list)，或者至少是一个*链表*。但在实践中，存储一堆同质数据的最佳方式几乎总是一个普通的数组：

> **注：** 算法研究人员靠发布新颖数据结构的分析文章来获得薪酬，他们并不太有动力坚守基本原则。

- 无需动态分配；
- 无需用于记账信息或指针的内存开销；
- <span name="locality">缓存友好</span>的连续内存使用。

> **注：** 关于"缓存友好"意味着什么，详见[数据局部性](24-data-locality.md)章节。

所以，我们这样做：

```cpp
class Audio
{
public:
  static void init()
  {
    numPending_ = 0;
  }

  // Other stuff...
private:
  static const int MAX_PENDING = 16;

  static PlayMessage pending_[MAX_PENDING];
  static int numPending_;
};
```

我们可以调整数组大小以覆盖最坏情况。播放声音时，我们只需在末尾插入一条新消息：

```cpp
void Audio::playSound(SoundId id, int volume)
{
  assert(numPending_ < MAX_PENDING);

  pending_[numPending_].id = id;
  pending_[numPending_].volume = volume;
  numPending_++;
}
```

这让 `playSound()` 几乎可以立即返回，但声音终究还是要播放的。那段代码需要放在某个地方，那就是一个 `update()` 方法：

<span name="update"></span>

```cpp
class Audio
{
public:
  static void update()
  {
    for (int i = 0; i < numPending_; i++)
    {
      ResourceId resource = loadSound(pending_[i].id);
      int channel = findOpenChannel();
      if (channel == -1) return;
      startSound(resource, channel, pending_[i].volume);
    }

    numPending_ = 0;
  }

  // Other stuff...
};
```

> **注：** 顾名思义，这就是[更新方法](14-update-method.md)模式。

现在，我们需要在某个合适的地方调用它。"合适"的含义因游戏而异，可能是从主[游戏循环](13-game-loop.md)中调用，也可能是从专用的音频线程调用。

这样能正常工作，但它假设我们可以在单次 `update()` 调用中处理*所有*声音请求。如果你要做的是在声音资源加载完毕后异步处理请求，这就行不通了。要让 `update()` 一次只处理一个请求，它需要能够从缓冲区中取出请求，同时保留其余部分。换句话说，我们需要一个真正的队列。

### 环形缓冲区

实现队列的方式有很多，但我最喜欢的叫做*环形缓冲区（ring buffer）*。它保留了数组的所有优点，同时让我们能够从队列头部逐步移除条目。

我知道你在想什么：如果我们从数组开头移除条目，不是要把所有剩余条目都往前移吗？那不是很慢吗？

链表之所以让我们学，正是为了这个原因——从链表中移除节点不需要移动其他东西。不过，在数组中实现队列其实也不需要任何移动操作。让我先把这个思路讲清楚，但首先要明确几个术语：

- 队列的**头（head）**是*读取*请求的位置，是最旧的待处理请求所在。
- **尾（tail）**是另一端，是下一条入队请求将被*写入*的数组槽。注意它在队列末尾的*后一个*位置——如果把队列视为半开区间，这样理解会更清晰。

由于 `playSound()` 在数组末尾追加新请求，头部从第零号元素开始，尾部向右增长。

*（图示：一个事件数组。头指针指向第一个元素，尾指针向右增长。）*

让我们写出这段代码。首先，稍微调整一下字段，在类中明确设置这两个标记：

```cpp
class Audio
{
public:
  static void init()
  {
    head_ = 0;
    tail_ = 0;
  }

  // Methods...
private:
  static int head_;
  static int tail_;

  // Array...
};
```

在 `playSound()` 的实现中，`numPending_` 被替换为 `tail_`，其余不变：

```cpp
void Audio::playSound(SoundId id, int volume)
{
  assert(tail_ < MAX_PENDING);

  // Add to the end of the list.
  pending_[tail_].id = id;
  pending_[tail_].volume = volume;
  tail_++;
}
```

更有趣的变化在 `update()` 中：

```cpp
void Audio::update()
{
  // If there are no pending requests, do nothing.
  if (head_ == tail_) return;

  ResourceId resource = loadSound(pending_[head_].id);
  int channel = findOpenChannel();
  if (channel == -1) return;
  startSound(resource, channel, pending_[head_].volume);

  head_++;
}
```

我们处理头部的请求，然后通过将头指针向右推进来丢弃它。通过判断头部和尾部之间是否有距离来检测<span name="empty">空队列</span>。

> **注：** 这就是我们把尾部放在最后一个条目*之后一位*的原因——这样当头尾索引相同时，队列就是空的。

现在我们有了一个队列——可以从末尾添加，从头部移除。然而有一个显而易见的问题：随着请求不断流经队列，头部和尾部持续向右爬行，最终 `tail_` 会触及数组末尾，<span name="party">好景便到了头</span>。这时候就是这个方案的聪明之处了。

> **注：** 你不想好景到头。你不想。

*（图示：同一个数组，但头指针也在向右移动，在左边留下了可用的空槽。）*

注意尾部向前爬行时，*头部*也在爬行。这意味着数组*开头*有一些不再被使用的元素。于是我们的做法是：当尾部跑出数组末尾时，让它绕回数组开头。这就是为什么叫*环形*缓冲区——它表现得像一个循环的单元数组。

*（图示：数组首尾相连，头指针可以绕回起点。）*

实现起来非常简单。入队一个条目时，只需确保尾部到达末尾后绕回到数组开头：

```cpp
void Audio::playSound(SoundId id, int volume)
{
  assert((tail_ + 1) % MAX_PENDING != head_);

  // Add to the end of the list.
  pending_[tail_].id = id;
  pending_[tail_].volume = volume;
  tail_ = (tail_ + 1) % MAX_PENDING;
}
```

用对数组大小取模的递增替换 `tail_++`，尾部就会绕回来。另一个变化是断言。我们需要确保队列不会溢出。只要队列中的请求数少于 `MAX_PENDING`，头部和尾部之间就会有一小段空闲单元。如果队列满了，这些空闲单元就消失了，就像某种奇怪的反向衔尾蛇，尾部会与头部相撞并开始覆盖它。断言确保这种情况不会发生。

在 `update()` 中，我们也同样对头部进行绕回：

```cpp
void Audio::update()
{
  // If there are no pending requests, do nothing.
  if (head_ == tail_) return;

  ResourceId resource = loadSound(pending_[head_].id);
  int channel = findOpenChannel();
  if (channel == -1) return;
  startSound(resource, channel, pending_[head_].volume);

  head_ = (head_ + 1) % MAX_PENDING;
}
```

好了——一个<span name="capacity">无需动态分配</span>、无需移动元素、并具备普通数组缓存友好性的队列。

> **注：** 如果固定容量让你感到不安，可以使用可扩容数组。当队列满时，分配一个当前大小两倍（或其他倍数）的新数组，然后把条目复制过去。虽然数组增长时需要复制，但入队操作的*均摊*复杂度仍然是常数。

### 聚合请求

有了队列之后，我们可以着手解决其他问题了。第一个是：对同一声音的多次播放请求导致声音过响。由于我们现在知道哪些请求正在等待处理，只需要在请求与某个已待处理的请求匹配时进行合并：

```cpp
void Audio::playSound(SoundId id, int volume)
{
  // Walk the pending requests.
  for (int i = head_; i != tail_;
       i = (i + 1) % MAX_PENDING)
  {
    if (pending_[i].id == id)
    {
      // Use the larger of the two volumes.
      pending_[i].volume = max(volume, pending_[i].volume);

      // Don't need to enqueue.
      return;
    }
  }

  // Previous code...
}
```

当我们收到两条播放同一声音的请求时，将它们合并为一条，保留两者中较大的音量。这种"聚合"相当初级，但我们可以用同样的思路做更有趣的批处理。

注意我们是在*入队*时合并，而不是在*处理*时。这对队列更友好，因为不会浪费槽位存放最终要被合并的冗余请求，实现起来也更简单。

不过，这把处理负担转移到了调用方身上。`playSound()` 在返回前会遍历整个队列，如果队列很长，这可能会<span name="slow">很慢</span>。在 `update()` 中聚合也许更合理。

> **注：** 另一种避免 O(n) 扫描队列开销的方式是使用不同的数据结构。如果我们用以 `SoundId` 为键的哈希表，就能在常数时间内检查是否有重复。

这里有一点需要特别注意：我们能聚合的"同时"请求的窗口，只有队列本身那么大。如果请求被快速处理，队列保持较小，批量处理的机会就更少；反之，如果处理滞后，队列变大，能合并的内容就更多。

这个模式将请求者与请求何时被处理隔离开来，但当你把整个队列视为一个可操作的活数据结构时，从发出请求到处理请求之间的延迟可能会明显影响行为。在采用这种做法之前，确保你能接受这一点。

### 跨线程

最后，来解决最棘手的问题。在我们同步音频 API 中，调用 `playSound()` 的线程就是处理请求的线程，这通常并不是我们想要的结果。

在当今的<span name="multicore">多核</span>硬件上，要充分发挥芯片的性能，就需要多个线程。在线程之间分配代码的方式多种多样，但一种常见策略是让游戏的每个领域运行在它自己的线程上——音频、渲染、AI 等。

> **注：** 直线式代码在任何时刻只能运行在单个核心上。如果不使用线程，即使你采用当下流行的异步风格编程，最多也只能让一个核心保持忙碌，这只是 CPU 能力的一小部分。服务器程序员通过把应用拆分成多个独立进程来弥补这一点，让操作系统在不同核心上并发运行它们。游戏几乎总是单进程的，所以使用少量线程确实很有帮助。

现在我们已经具备了三个关键要素，完全可以做到这一点：

1. 请求声音的代码与播放声音的代码已经解耦；
2. 我们有了一个队列在两者之间传递数据；
3. 队列相对程序其余部分是封装好的。

剩下的只是让修改队列的方法——`playSound()` 和 `update()`——线程安全。通常我会写出具体的代码来做这件事，但由于本书关注的是架构，我不想深陷于任何特定 API 或锁机制的细节。

从高层来看，我们所需要做的就是确保队列不会被并发修改。由于 `playSound()` 做的工作非常少——基本上只是给几个字段赋值——它加锁时不会长时间阻塞处理。在 `update()` 中，我们在类似条件变量的东西上等待，这样在没有请求需要处理时就不会白白消耗 CPU 周期。

## 设计决策

许多游戏将事件队列作为通信结构的核心部分，你可以花大量时间设计各种复杂的消息路由和过滤机制。但在你去构建类似"洛杉矶电话总机"那样的东西之前，我建议从简单开始。以下是几个入门问题：

### 队列中存放的是什么？

我一直在互换使用"事件"和"消息"，因为大多数时候这没什么区别。无论你往队列里塞什么，都能获得同样的解耦和聚合能力，但在概念上还是有一些差异。

**如果你存放的是事件：**

"事件"或"通知"描述的是*已经*发生的事情，比如"怪物死亡"。你把它入队，让其他对象能够对该事件作出*响应*，有点像异步的[观察者模式](http://c2.com/cgi/wiki?ObserverPattern)。

- *很可能允许多个监听者。* 由于队列包含的是已经发生的事情，发送方大概不关心谁接收它。对发送方来说，事件已成过去，早已抛之脑后。
- *队列的范围往往更广。* 事件队列通常用于向所有感兴趣的各方*广播*事件。为了最大限度地灵活支持各种感兴趣的对象，这些队列往往具有更大的可见范围。

**如果你存放的是消息：**

<span name="command">"消息"</span>或"请求"描述的是我们*希望在未来发生*的动作，比如"播放声音"。可以把它看作对某个服务的异步 API。

> **注：** "请求"的另一种说法是"命令"，对应四人帮的[命令模式](http://c2.com/cgi/wiki?CommandPattern)，队列也可以在那里使用。

- *<span name="locator">更可能</span>只有一个监听者。* 在我们的示例中，队列中的消息是专门发给*音频 API* 来播放声音的。如果游戏引擎的其他随机部分开始从队列中截走消息，那就没什么意义了。

  > **注：** 我说"更可能"，是因为你可以在不关心哪段代码处理消息的情况下入队，只要它按你期望的方式被处理就行。在这种情况下，你的做法更接近[服务定位器](22-service-locator.md)模式。

### 谁可以从队列中读取？

在我们的示例中，队列是封装好的，只有 `Audio` 类可以从中读取。在用户界面的事件系统中，你可以随心所欲地注册监听者。你有时会听到"单播"和"广播"这两个术语来区分这两种情况，两种风格都有其用武之地。

**单播队列：**

当队列是某个类 API 的一部分时，这是最自然的选择。就像我们的音频示例，从调用方的角度来看，它们只看到一个可以调用的 `playSound()` 方法。

- *队列成为读取方的实现细节。* 发送方所知道的只是它发送了一条消息。
- *队列的封装性更好。* 在同等条件下，更好的封装通常就是更好的设计。
- *不必担心监听者之间的竞争。* 有多个监听者时，你需要决定它们是否都能收到每个条目（广播），还是队列中的每个条目只分发给*一个*监听者（更像工作队列）。无论哪种情况，监听者都可能做重复的工作或相互干扰，需要仔细考虑你想要的行为。只有单个监听者时，这种复杂性就消失了。

**广播队列：**

大多数"事件"系统的工作方式。如果一个事件到来时有十个监听者，十个都会看到这个事件。

- *事件可能无人处理。* 上一点的推论是：如果你有*零个*监听者，所有零个监听者都会看到这个事件。在大多数广播系统中，如果在事件被处理的那一刻没有监听者，事件就被丢弃了。
- *可能需要过滤事件。* 广播队列通常对程序的大部分可见，最终可能有一大堆监听者。大量事件乘以大量监听者，需要调用的事件处理函数数量就相当庞大了。为了缩减规模，大多数广播事件系统允许监听者筛选它们想接收的事件——例如，它们可以声明只想接收鼠标事件，或者 UI 某个特定区域内的事件。

**工作队列：**

类似广播队列，这里同样有多个监听者。区别在于队列中的每个条目只发往*其中一个*监听者。这是一种常见的模式，用于将任务分发给一组并发运行的线程。

- *需要进行调度。* 由于条目只发给一个监听者，队列需要逻辑来决定最佳的选择对象。这可以简单到轮询或随机选取，也可以是更复杂的优先级系统。

### 谁可以向队列写入？

这是上一个设计决策的另一面。这个模式适用于所有可能的读/写<span name="configs">配置</span>：一对一、一对多、多对一或多对多。

> **注：** 你有时会听到"扇入（fan-in）"用来描述多对一的通信系统，"扇出（fan-out）"用于一对多。

**只有一个写入者：**

这种风格与同步的观察者模式最为相似。你有一个特权对象来生成事件，其他对象可以接收。

- *你可以隐式地知道事件来自哪里。* 由于只有一个对象能向队列添加内容，任何监听者都可以安全地假设那就是发送方。
- *通常允许多个读取者。* 你可以做一个单发送者-单接收者的队列，但那开始感觉不像这个模式所关注的通信系统，而更像是一个普通的队列数据结构。

**有多个写入者：**

这是我们音频引擎示例的工作方式。由于 `playSound()` 是公共方法，代码库的任何地方都可以向队列添加请求。"全局"或"中央"事件总线也是如此运作的。

- *需要更加警惕循环。* 由于任何地方都可能向队列添加内容，更容易不小心在处理事件的过程中入队新内容。如果不小心，这可能触发反馈死循环。
- *可能需要在事件本身中包含对发送方的引用。* 当监听者收到事件时，它不知道是谁发送的，因为可以是任何人。如果监听者需要知道，就要把这个信息打包进事件对象，以便监听者使用。

### 队列中对象的生命周期如何？

在同步通知中，执行要等到所有接收方都处理完消息后才返回给发送方。这意味着消息本身可以安全地存活在栈上的局部变量中。而对于队列，消息的生命周期超过了将其入队的那次调用。

如果你使用的是垃圾回收语言，就不必太担心这个问题——把消息塞进队列，它会在需要时一直留在内存里。在 C 或 C++ 中，你需要自行确保对象存活足够长的时间。

**转移所有权：**

这是手动管理内存时的<span name="unique">传统</span>做法。消息入队时，队列声明对它的所有权，发送方不再拥有它。消息被处理时，接收方获得所有权，并负责释放它。

> **注：** 在 C++ 中，`unique_ptr<T>` 开箱即用地提供了这种语义。

**共享所有权：**

如今，即使是 C++ 程序员也越来越习惯垃圾回收的思路，<span name="shared">共享所有权</span>变得更加可接受。在这种模式下，只要有任何对象持有消息的引用，消息就会留在内存中，当被遗忘时自动释放。

> **注：** 同样，C++ 中对应的类型是 `shared_ptr<T>`。

**由队列持有：**

<span name="pool">另一种方案</span>是让消息*始终*存活在队列中。发送方不需要自己分配消息，而是向队列"申请"一条新的。队列返回队列内存中某条消息的引用，发送方填写内容。消息被处理时，接收方引用的仍然是队列中的那条消息。

> **注：** 换句话说，队列的后端存储是一个[对象池](26-object-pool.md)。

- 与许多模式一样，事件队列有多个别名。一个公认的术语是"消息队列"，通常指的是更高层面的表现形式——我们的事件队列是在应用程序*内部*使用的，而消息队列通常用于应用程序*之间*的通信。另一个术语是"发布/订阅（publish/subscribe）"，有时缩写为"pubsub"，通常指的是更大的分布式系统，而非我们关注的这种朴实的编码模式。
