# 子类沙箱

**行为模式**

## 意图

*使用基类提供的一组操作，在子类中定义行为。*

## 动机

每个孩子都梦想过成为超级英雄，可惜宇宙射线在地球上实在稀缺。让你扮演超级英雄的游戏，是最接近这个梦想的替代品。由于我们的游戏设计师从未学会说"不"，*我们的*超级英雄游戏打算提供几十种乃至上百种英雄可以选择的不同超能力。

我们的计划是设计一个 `Superpower`（超能力）基类，然后为每种超能力派生一个子类。我们把设计文档分配给团队的程序员们，然后开始编码。完成后，我们将拥有一百个超能力类。

> 当你发现自己有*大量*子类时（就像这个例子），这往往意味着数据驱动的方式更合适。与其用大量*代码*定义不同的能力，不如试着找一种在*数据*中定义这些行为的方式。[类型对象](type-object.html)、[字节码](bytecode.html)和[解释器](http://en.wikipedia.org/wiki/Interpreter_pattern)模式都能提供帮助。

我们想让玩家沉浸在一个充满多样性的世界里。无论他们小时候幻想过什么能力，我们都希望出现在游戏中。这意味着这些超能力子类几乎什么都能做：播放音效、生成视觉特效、与 AI 交互、创建和销毁其他游戏实体，以及影响物理。代码库的每个角落它们都会触碰。

假设我们放手让团队开始写超能力类，会发生什么？

- *会有大量重复代码。* 尽管不同的能力千差万别，但我们仍然可以预见大量重叠。许多能力会以相同的方式生成视觉特效和播放音效。冰冻射线、热能射线和第戎芥末射线，深究起来其实大同小异。如果实现这些的人不协调，就会有大量重复的代码和工作。

- *游戏引擎的每个部分都会与这些类耦合。* 没有更好的指引，大家会写出调用那些本不应直接与超能力类绑定的子系统的代码。如果我们的渲染器被组织成几个整洁的层次，其中只有一层设计为供图形引擎外部代码使用，我们可以打赌，超能力代码最终会戳进每一层。

- *当这些外部系统需要变更时，很可能有某个超能力类随之崩溃。* 一旦不同的超能力类与游戏引擎的各种部分耦合，这些系统的变更势必影响能力类。这并不好受，因为你的图形、音频和 UI 程序员大概也不想同时兼任玩法程序员。

- *很难为所有超能力定义统一约束。* 假设我们想确保所有能力播放的音频都被正确地排队和优先处理。如果我们的一百个类都各自直接调用音频引擎，这根本无从实现。

我们想做的是：给每个负责实现超能力的玩法程序员提供一套可以使用的基础原语。你的能力需要播放音效？这里有 `playSound()` 函数。你需要粒子效果？这里有 `spawnParticles()`。我们会确保这些操作覆盖你需要做的一切，这样你就不必 `#include` 各种头文件、四处探头嗅代码库的其他部分。

实现方式是把这些操作变成 `Superpower` *基类的受保护方法*。把它们放在基类中，每个子类都能直接、便捷地访问这些方法。将它们声明为 protected（且很可能是非虚函数），传递了一个信息：它们的存在就是为了被子类*调用*。

有了这些工具，我们还需要一个使用它们的地方。为此，我们定义一个*沙箱方法*——一个子类必须实现的抽象受保护方法。有了这些设定，实现一种新能力只需：

1. 创建一个继承自 `Superpower` 的新类。
2. 覆写沙箱方法 `activate()`。
3. 在方法体内调用 `Superpower` 提供的受保护方法来实现行为。

现在我们可以通过让提供的操作尽量高层来解决重复代码问题。每当我们看到多个子类之间重复的代码，都可以把它提升到 `Superpower` 中，作为一个所有子类都可以使用的新操作。

我们也解决了耦合问题，方法是将耦合约束在一个地方。`Superpower` 本身最终会与不同的游戏系统耦合，但我们的一百个派生类不会。它们*只*与基类耦合。当某个游戏系统变更时，修改 `Superpower` 也许是必要的，但几十个子类不必被触动。

这个模式导向一种"浅而宽"的类层次结构。你的*继承*链不*深*，但有*大量*类挂在 `Superpower` 上。通过拥有一个带有许多直接子类的单一类，我们在代码库中获得了一个支点。我们投入在 `Superpower` 上的时间和精力，能让游戏中大量的类受益。

> 最近你会发现很多人在批评面向对象语言中的继承。继承*确实*有问题——代码库中没有比基类与子类之间更深的耦合了——但我发现"宽"的继承树比"深"的更容易维护。

## 模式详解

**基类**定义一个抽象的**沙箱方法**和若干**提供的操作**。将它们标记为 protected 表明它们专供派生类使用。每个派生的**沙箱子类**使用提供的操作来实现沙箱方法。

## 适用场景

子类沙箱是一个非常简单、常见的模式，潜伏在许多代码库中，甚至游戏之外也不例外。如果你有非虚的受保护方法，你很可能已经在使用类似的东西了。子类沙箱在以下情况下非常合适：

- 你有一个带有若干派生类的基类。
- 基类能够提供派生类可能需要执行的所有操作。
- 子类之间存在行为重叠，你希望更容易地在它们之间共享代码。
- 你希望最小化这些派生类与程序其余部分之间的耦合。

## 注意事项

如今在很多编程圈子里，"继承"是个贬义词，原因之一是基类往往会越积越多代码。这个模式对此尤为敏感。

由于子类要通过基类来访问游戏的其余部分，基类最终会与*任何*派生类需要交互的每一个系统耦合。当然，子类本身也与基类紧密相连。这张耦合的蜘蛛网使得修改基类而不破坏某些东西变得非常困难——你陷入了[脆弱基类问题](http://en.wikipedia.org/wiki/Fragile_base_class)。

另一面是：由于大部分耦合已被推到基类，派生类现在与世界其余部分的分离更干净了。理想情况下，你的大部分行为都在那些子类里。这意味着代码库的大部分是隔离的，更易于维护。

不过，如果你发现这个模式正在把你的基类变成一大锅代码杂烩，可以考虑把某些提供的操作抽出来放到独立的类中，让基类把职责分派给它们。[组件](component.html)模式可以在这里提供帮助。

## 示例代码

因为这是如此简单的模式，示例代码并不多。这不代表它没有用——这个模式关注的是*意图*，而非实现的复杂度。

我们从 `Superpower` 基类开始：

```cpp
class Superpower
{
public:
  virtual ~Superpower() {}

protected:
  virtual void activate() = 0;

  void move(double x, double y, double z)
  {
    // 代码在这里……
  }

  void playSound(SoundId sound, double volume)
  {
    // 代码在这里……
  }

  void spawnParticles(ParticleType type, int count)
  {
    // 代码在这里……
  }
};
```

`activate()` 方法是沙箱方法。由于它是虚纯虚函数，子类*必须*覆写它。这让创建能力子类的人清楚地知道他们的工作要放在哪里。

另外几个受保护的方法——`move()`、`playSound()` 和 `spawnParticles()`——是提供的操作，也是子类在实现 `activate()` 时会调用的。

在这个例子中我们没有实现提供的操作，但真实的游戏里那里会有真正的代码。这些方法正是 `Superpower` 与游戏中其他系统耦合的地方——`move()` 可能调用物理代码，`playSound()` 会与音频引擎交互，等等。由于这一切都在基类的*实现*中，它将耦合封装在 `Superpower` 内部。

好了，现在让我们把放射性蜘蛛放出来，创建一个能力。这是其中一个：

> 好吧，也许能够*跳跃*并不是多么*超凡*的能力，但我在这里尽量保持简单。

```cpp
class SkyLaunch : public Superpower
{
protected:
  virtual void activate()
  {
    // 跃入空中。
    playSound(SOUND_SPROING, 1.0f);
    spawnParticles(PARTICLE_DUST, 10);
    move(0, 0, 20);
  }
};
```

这个能力让超级英雄跃入空中，播放合适的音效，扬起一小团尘雾。如果所有超能力都这么简单——只是音效、粒子效果和移动的组合——那我们根本不需要这个模式。直接在 `Superpower` 里内置一个 `activate()` 实现，通过字段存储音效 ID、粒子类型和移动量就够了。但那只适用于每种能力本质上以相同方式运作、只是数据有所不同的情况。让我们稍微丰富一下：

```cpp
class Superpower
{
protected:
  double getHeroX()
  {
    // 代码在这里……
  }

  double getHeroY()
  {
    // 代码在这里……
  }

  double getHeroZ()
  {
    // 代码在这里……
  }

  // 原有内容……
};
```

我们添加了几个获取英雄位置的方法。现在 `SkyLaunch` 子类可以使用它们：

```cpp
class SkyLaunch : public Superpower
{
protected:
  virtual void activate()
  {
    if (getHeroZ() == 0)
    {
      // 在地面上，跃入空中。
      playSound(SOUND_SPROING, 1.0f);
      spawnParticles(PARTICLE_DUST, 10);
      move(0, 0, 20);
    }
    else if (getHeroZ() < 10.0f)
    {
      // 靠近地面，执行二段跳。
      playSound(SOUND_SWOOP, 1.0f);
      move(0, 0, getHeroZ() + 20);
    }
    else
    {
      // 在高空中，执行俯冲攻击。
      playSound(SOUND_DIVE, 0.7f);
      spawnParticles(PARTICLE_SPARKLES, 1);
      move(0, 0, -getHeroZ());
    }
  }
};
```

有了对某些状态的访问，我们的沙箱方法现在可以实现真正有趣的控制流了。这里只是几个简单的 `if` 语句，但你可以做任何你想做的事。沙箱方法是一个真正完整的方法，可以包含任意代码，天空才是极限。

> 前文我建议过对能力使用数据驱动的方式。这正是你可能决定*不*那么做的原因之一。如果你的行为是复杂的命令式逻辑，在数据中定义就更困难了。

## 设计决策

如你所见，子类沙箱是一个相当"柔性"的模式。它描述了一个基本思路，但没有太多具体的机制。这意味着每次应用它时，你都会面临一些有趣的选择。以下是一些需要考虑的问题。

### 应该提供哪些操作？

这是最重要的问题，深刻影响着这个模式的感觉和效果。在最小化的极端，基类不提供*任何*操作，只有一个沙箱方法。要实现它，你必须调用基类之外的系统。如果走这条路，说你在使用这个模式都有些勉强。

在另一个极端，基类提供了子类可能需要的*每一种*操作。子类*只*与基类耦合，完全不调用任何外部系统。

> 具体来说，这意味着每个子类的源文件只需要一个 `#include`——它的基类头文件。

在这两个极端之间，有广阔的中间地带：某些操作由基类提供，另一些则直接从定义它们的外部系统访问。你提供的操作越多，子类与外部系统的耦合就越少，但基类的耦合就*越多*。这从派生类中移除了耦合，但代价是把耦合推到了基类本身。

如果你有一堆派生类都与某个外部系统耦合，把耦合提升到一个提供的操作中是有价值的——你把它集中到了一个地方：基类。但你做得越多，那个类就越大、越难维护。

那么该在哪里划定界限？以下几条经验之谈：

- 如果某个提供的操作只被一个或少数几个子类使用，性价比就不高。你增加了影响所有人的基类复杂度，却只有少数类从中受益。也许值得这么做以保持操作风格的一致性，也许直接让那些特殊子类调用外部系统反而更简单清晰。

- 当你调用游戏某个角落里的方法时，如果那个方法不修改任何状态，侵入性就较小。它仍然创建了耦合，但这是一种"安全"的耦合，因为它不会破坏游戏中的任何东西。

  > 这里的"安全"加了引号，因为即使只是读取数据，技术上也可能引发问题。如果你的游戏是多线程的，你可能在读取某个数据的同时，它正被修改。稍有不慎，就可能得到错误的数据。
  >
  > 另一个棘手的情况是：如果你的游戏状态是严格确定性的（许多联网游戏为了保持玩家同步而如此），访问同步游戏状态集合之外的内容，可能导致极其痛苦的非确定性 bug。

  另一方面，*会*修改状态的调用与代码库那些部分的绑定更深，你需要对此更加警觉。这使它们成为值得整合到基类中可见提供操作的好候选。

- 如果某个提供操作的实现只是把调用转发给某个外部系统，那它并没有增加太多价值。这种情况下，直接调用外部方法可能更简单。

  不过，即使简单的转发也可能有用——这些方法往往访问基类不想直接暴露给子类的状态。比如，假设 `Superpower` 提供了这个：

  ```cpp
  void playSound(SoundId sound, double volume)
  {
    soundEngine_.play(sound, volume);
  }
  ```

  它只是把调用转发给 `Superpower` 中的某个 `soundEngine_` 字段。但好处是，它把该字段封装在 `Superpower` 内部，子类无法直接操弄它。

### 方法应该直接提供，还是通过包含它们的对象来提供？

这个模式的挑战在于，你可能会把大量方法塞进基类，令人痛苦。你可以通过把某些方法移到其他类来缓解这个问题。基类中的提供操作只需返回其中某个对象即可。

例如，要让能力播放音效，我们可以直接在 `Superpower` 上添加：

```cpp
class Superpower
{
protected:
  void playSound(SoundId sound, double volume)
  {
    // 代码在这里……
  }

  void stopSound(SoundId sound)
  {
    // 代码在这里……
  }

  void setVolume(SoundId sound)
  {
    // 代码在这里……
  }

  // 沙箱方法和其他操作……
};
```

但如果 `Superpower` 已经很庞大臃肿，我们可能想避免这样做。转而创建一个暴露这些功能的 `SoundPlayer` 类：

```cpp
class SoundPlayer
{
  void playSound(SoundId sound, double volume)
  {
    // 代码在这里……
  }

  void stopSound(SoundId sound)
  {
    // 代码在这里……
  }

  void setVolume(SoundId sound)
  {
    // 代码在这里……
  }
};
```

然后 `Superpower` 提供对它的访问：

```cpp
class Superpower
{
protected:
  SoundPlayer& getSoundPlayer()
  {
    return soundPlayer_;
  }

  // 沙箱方法和其他操作……

private:
  SoundPlayer soundPlayer_;
};
```

把提供的操作分流到辅助类中可以带来以下好处：

- *减少了基类中的方法数量。* 在这个例子里，我们从三个方法缩减到了一个 getter。
- *辅助类中的代码通常更易于维护。* 像 `Superpower` 这样的核心基类，尽管我们有最好的意图，往往难以修改，因为太多东西依赖于它。把功能移到一个耦合更少的次要类中，让我们在不破坏东西的情况下更容易调整那些代码。
- *降低了基类与其他系统之间的耦合。* 当 `playSound()` 直接是 `Superpower` 上的方法时，基类与 `SoundId` 和实现所调用的任何音频代码直接绑定。把它移到 `SoundPlayer` 后，`Superpower` 的耦合降低为对单一 `SoundPlayer` 类的依赖，而 `SoundPlayer` 则封装了它所有的其他依赖。

### 基类如何获取它需要的状态？

基类经常需要一些想要封装起来、对子类隐藏的数据。在我们的第一个例子中，`Superpower` 类提供了 `spawnParticles()` 方法。如果该方法的实现需要某个粒子系统对象，它要怎么获取？

**通过构造函数传入基类：**

最简单的方案是让基类通过构造函数参数来接收：

```cpp
class Superpower
{
public:
  Superpower(ParticleSystem* particles)
  : particles_(particles)
  {}

  // 沙箱方法和其他操作……

private:
  ParticleSystem* particles_;
};
```

这能安全地确保每个超能力在构造时就拥有粒子系统。但来看看派生类：

```cpp
class SkyLaunch : public Superpower
{
public:
  SkyLaunch(ParticleSystem* particles)
  : Superpower(particles)
  {}
};
```

问题就在这里。每个派生类都需要有一个调用基类构造函数并传递该参数的构造函数。这把我们不想让它们了解的状态暴露给了每一个派生类。

这也是一个维护噩梦。如果我们后来向基类添加另一块状态，每个派生类的每个构造函数都必须被修改以传递它。

**采用两阶段初始化：**

为了避免通过构造函数传递所有内容，我们可以把初始化分成两步。构造函数不接收任何参数，只是创建对象。然后，我们调用一个直接定义在基类上的单独方法来传递它所需的其余数据：

```cpp
Superpower* power = new SkyLaunch();
power->init(particles);
```

注意，由于我们没有向 `SkyLaunch` 的构造函数传递任何东西，它不与我们想在 `Superpower` 中保持私有的任何内容耦合。不过，这种方式的麻烦在于，你必须确保始终记得调用 `init()`。如果你忘了，你会得到一个处于某种暮光般半创建状态、无法正常工作的能力。

你可以通过把整个过程封装进一个函数来解决这个问题：

> 借助私有构造函数和友元类之类的小技巧，你可以确保这个 `createSkyLaunch()` 函数是*唯一*能真正创建能力的函数。这样你就不会忘记任何初始化阶段了。

```cpp
Superpower* createSkyLaunch(ParticleSystem* particles)
{
  Superpower* power = new SkyLaunch();
  power->init(particles);
  return power;
}
```

**将状态设为静态：**

在前面的例子中，我们用粒子系统初始化每个 `Superpower` *实例*。当每个能力需要自己独有的状态时，这很合理。但如果粒子系统是一个[单例](singleton.html)，所有能力共享同一状态呢？

在这种情况下，我们可以让状态对基类私有，同时让它成为*静态*的。游戏仍然必须确保初始化这个状态，但只需在整个游戏生命周期中初始化一次 `Superpower` *类*，而不是每个实例。

```cpp
class Superpower
{
public:
  static void init(ParticleSystem* particles)
  {
    particles_ = particles;
  }

  // 沙箱方法和其他操作……

private:
  static ParticleSystem* particles_;
};
```

注意这里 `init()` 和 `particles_` 都是静态的。只要游戏在早期调用一次 `Superpower::init()`，每个能力都能访问粒子系统。与此同时，`Superpower` 实例可以通过调用相应派生类的构造函数自由创建。

更妙的是，现在 `particles_` 是一个*静态*变量，我们不必为 `Superpower` 的每个实例都存储它，从而减少了类的内存占用。

> 请记住，这仍然具有单例的许多问题。你有一些在大量对象（所有 `Superpower` 实例）之间共享的状态。粒子系统被封装起来，不是全局*可见*的，这一点是好的，但它仍然可能让推理能力的行为变得更难，因为它们都在戳同一个对象。

**使用服务定位器：**

前面的选项要求外部代码专门记得在基类需要它之前把状态推进来，这把初始化的负担放在了周围的代码上。另一个选项是让基类自行拉取所需的状态。做到这一点的一种方式是使用[服务定位器](service-locator.html)模式：

```cpp
class Superpower
{
protected:
  void spawnParticles(ParticleType type, int count)
  {
    ParticleSystem& particles = Locator::getParticles();
    particles.spawn(type, count);
  }

  // 沙箱方法和其他操作……
};
```

这里，`spawnParticles()` 需要粒子系统。它不是由外部代码*提供*，而是自己从服务定位器取来。

## 另请参阅

- 当你应用[更新方法](update-method.html)模式时，更新方法本身通常也会是一个沙箱方法。
- 这个模式是四人帮[模板方法](http://en.wikipedia.org/wiki/Template_method_pattern)（Template Method）模式的角色互换。两个模式都使用一组基础原语来实现一个方法。在子类沙箱中，方法在派生类里，基础原语在基类里。在模板方法中，*基类*持有方法，基础原语由*派生类*实现。
- 你也可以把它看作四人帮[外观](http://en.wikipedia.org/wiki/Facade_Pattern)（Facade）模式的变体。外观模式将若干不同的系统隐藏在一个简化的 API 背后。在子类沙箱中，基类充当外观，将整个游戏引擎对子类隐藏起来。
