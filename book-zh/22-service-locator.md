# 服务定位器

**所属章节：解耦模式**

## 意图

*为服务提供全局访问点，同时避免使用者与实现该服务的具体类耦合。*

## 动机

游戏中有些对象或系统几乎无处不在，几乎触及代码库的每一个角落。很难找到哪个游戏模块完全不需要内存分配器、日志或随机数。这类系统可以被看作是需要向整个游戏提供的*服务*。

在我们的示例中，以音频为例。它的渗透范围不如内存分配器这样的底层系统那么广，但仍然触及许多游戏系统。掉落的石头砸到地面时发出轰鸣声（物理）；一个狙击手 NPC 开枪，枪声响起（AI）；用户选择菜单项时发出确认的提示音（用户界面）。

上述每个地方都需要能够调用音频系统，大致类似这样：

```cpp
// Use a static class?
AudioSystem::playSound(VERY_LOUD_BANG);

// Or maybe a singleton?
AudioSystem::instance()->playSound(VERY_LOUD_BANG);
```

两种方式都能达到目的，但途中我们陷入了一些麻烦的耦合。游戏中每个调用音频系统的地方都直接引用了具体的 `AudioSystem` 类，以及访问它的机制——无论是静态类还是[单例](http://c2.com/cgi/wiki?SingletonPattern)。

当然，这些调用点必须与*某些东西*耦合才能播放声音，但让它们直接访问具体的音频实现，就像把一百个陌生人领到你家门口，只是为了让他们在门阶上放一封信。这不仅有些*太过于*直接，当你搬家时还得一一通知每个人新地址，真是麻烦透顶。

有个更好的解决方案：电话簿。需要联系我们的人可以按名字查找我们并获取当前地址。当我们搬家时，告知电话公司，他们更新电话簿，所有人就都有了新地址。事实上，我们甚至不必提供真实地址，改用邮政信箱或其他某种"替代品"也行。通过让调用者经由电话簿找到我们，*我们就有了一个方便的单一控制点来管理自己如何被找到*。

这就是服务定位器模式的精髓——它将需要某项服务的代码，与*是谁*提供这项服务（具体实现类型）以及*在哪里*找到它（如何获取实例）都解耦开来。

## 模式结构

**服务**类定义了一组操作的抽象接口。具体的**服务提供者**实现这个接口。单独的**服务定位器**通过寻找合适的提供者来提供对服务的访问，同时对外隐藏提供者的具体类型和定位过程。

## 使用时机

每当你让某些东西对程序的每个部分都可访问时，你就是在自找麻烦。这是[单例模式](http://c2.com/cgi/wiki?SingletonPattern)的主要问题，这个模式也不例外。关于何时使用服务定位器，我最简单的建议是：*谨慎使用*。

在使用全局机制让某段代码访问它所需的对象之前，先考虑*直接把对象传给它*。这再简单不过了，而且让耦合关系一目了然。这能满足你的大多数需求。

*但是……* 有时手动传递对象实在多余，甚至会让代码更难读。有些系统，比如日志或内存管理，不应该成为模块公共 API 的一部分。渲染代码的参数应该与*渲染*相关，而不是诸如日志之类的东西。

同样，还有一些系统在本质上是单一的。你的游戏大概只有一个音频设备或显示系统可供使用，它是环境的一种固有属性——为了让深度嵌套的某个调用能够访问它，把它通过十层方法一路传递下去，只会给代码增加不必要的复杂性。

在这类情况下，这个模式可以帮上忙。正如我们将看到的，它是单例模式更灵活、更可配置的近亲。使用<span name="well">得当</span>时，它能以极低的运行时开销使代码库更加灵活。

> **注：** 反之，使用不当时，它会带来单例模式的所有包袱，同时运行时性能更差。

## 注意事项

服务定位器的核心难点在于：它把一种依赖——两段代码之间的一点耦合——推迟到运行时才进行连接。这给了你灵活性，但代价是：通过阅读代码来理解依赖关系变得更加困难。

### 服务实际上需要被定位

对于单例或静态类，我们需要的实例*不可能*不可用。调用代码可以想当然地认为它在那里。但由于这个模式需要*定位*服务，我们可能需要处理定位失败的情况。好在后文会介绍一种策略来解决这个问题，确保在需要时我们总能得到*某种*服务。

### 服务不知道是谁在定位它

由于定位器是全局可访问的，游戏中的任何代码都可能在请求服务并操作它。这意味着服务必须能在任何情况下正确工作。例如，一个只期望在游戏循环的模拟阶段而非渲染阶段被使用的类，可能不适合作为服务——它无法确保自己在正确的时机被使用。因此，如果一个类期望只在特定上下文中使用，最安全的做法是不要用这个模式把它暴露给整个世界。

## 示例代码

回到我们的音频系统问题，让我们通过服务定位器将该系统暴露给代码库的其余部分。

### 服务

我们从音频 API 开始，这是我们的服务将要暴露的接口：

```cpp
class Audio
{
public:
  virtual ~Audio() {}
  virtual void playSound(int soundID) = 0;
  virtual void stopSound(int soundID) = 0;
  virtual void stopAllSounds() = 0;
};
```

真实的音频引擎当然要比这复杂得多，但这展示了基本思路。重要的是：它是一个没有绑定任何实现的抽象接口类。

### 服务提供者

单独的音频接口本身并没什么用，我们需要一个具体实现。本书不讨论如何为游戏主机编写音频代码，所以你需要想象这些函数体里有一些实际代码，但整体思路如此：

```cpp
class ConsoleAudio : public Audio
{
public:
  virtual void playSound(int soundID)
  {
    // Play sound using console audio api...
  }

  virtual void stopSound(int soundID)
  {
    // Stop sound using console audio api...
  }

  virtual void stopAllSounds()
  {
    // Stop all sounds using console audio api...
  }
};
```

现在我们有了接口和实现。剩下的部分是服务定位器——那个将两者联系在一起的类。

### 简单的定位器

这里的实现是你能定义的最简单的服务定位器之一：

<span name="di"></span>

```cpp
class Locator
{
public:
  static Audio* getAudio() { return service_; }

  static void provide(Audio* service)
  {
    service_ = service;
  }

private:
  static Audio* service_;
};
```

> **注：** 这里使用的技术叫做*依赖注入（dependency injection）*——一个听起来别扭，但描述的是极简单思路的术语。假设你有一个依赖另一个的类，在我们的例子中，`Locator` 类需要一个 `Audio` 服务的实例。通常，定位器自己负责构造那个实例。而依赖注入则说：由外部代码负责将该依赖*注入*到需要它的对象中。

静态函数 `getAudio()` 负责定位工作。我们可以在代码库的任何地方调用它，它会返回一个可用的 `Audio` 服务实例：

```cpp
Audio *audio = Locator::getAudio();
audio->playSound(VERY_LOUD_BANG);
```

它"定位"的方式非常简单——它依赖外部代码在任何人尝试使用服务之前先注册一个服务提供者。游戏启动时，会调用类似这样的代码：

```cpp
ConsoleAudio *audio = new ConsoleAudio();
Locator::provide(audio);
```

这里需要注意的关键之处是：调用 `playSound()` 的代码并不知道具体的 `ConsoleAudio` 类，它只知道抽象的 `Audio` 接口。同样重要的是，就连*定位器*类也不与具体服务提供者耦合。代码库中唯一知道实际具体类的地方，是提供该服务的初始化代码。

这里还有一层解耦：`Audio` 接口本身并不知道它在大多数地方是通过服务定位器被访问的。对它来说，它不过是一个普通的抽象基类。这很有用，因为这意味着我们可以把这个模式应用到*现有的*类上，而这些类不一定是为此模式专门设计的。这与[单例模式](http://c2.com/cgi/wiki?SingletonPattern)形成对比——单例模式会影响"服务"类本身的设计。

### 空服务

到目前为止，我们的实现确实简单，也颇为灵活。但它有一个重大缺陷：如果我们在提供者注册之<span name="temporal">前</span>就尝试使用服务，它会返回 `NULL`。如果调用代码不检查这一点，游戏就会崩溃。

> **注：** 我有时听人把这称为"时序耦合（temporal coupling）"——程序正确运行要求两段独立代码必须以正确的顺序被调用。所有有状态的软件都存在一定程度的这种耦合，但与其他形式的耦合一样，减少时序耦合会让代码库更易于管理。

幸运的是，还有另一种叫做"空对象（Null Object）"的设计模式可以解决这个问题。基本思路是：在我们原本因无法找到或创建对象而返回 `NULL` 的地方，我们改为返回一个实现了与目标对象相同接口的特殊对象。它的实现基本上什么也不做，但它让接收到它的代码可以安全地继续运行，就好像拿到了一个"真实"的对象。

为了使用这种方式，我们定义另一个"空"服务提供者：

```cpp
class NullAudio: public Audio
{
public:
  virtual void playSound(int soundID) { /* Do nothing. */ }
  virtual void stopSound(int soundID) { /* Do nothing. */ }
  virtual void stopAllSounds()        { /* Do nothing. */ }
};
```

如你所见，它实现了服务接口，但实际上什么也不做。现在，我们把定位器改成这样：

<span name="ref"></span>

```cpp
class Locator
{
public:
  static void initialize() { service_ = &nullService_; }

  static Audio& getAudio() { return *service_; }

  static void provide(Audio* service)
  {
    if (service == NULL)
    {
      // Revert to null service.
      service_ = &nullService_;
    }
    else
    {
      service_ = service;
    }
  }

private:
  static Audio* service_;
  static NullAudio nullService_;
};
```

> **注：** 你可能注意到我们现在通过引用而不是指针来返回服务。由于 C++ 中的引用（理论上！）永远不会是 `NULL`，返回引用向代码使用者暗示：他们始终可以期待得到一个有效的对象。另外值得注意的是，我们在 `provide()` 函数中而非访问器中检查 `NULL`。这要求我们尽早调用 `initialize()` 以确保定位器初始时正确地默认使用空提供者。作为回报，这把条件判断从 `getAudio()` 中移出，每次访问服务时都能节省几个时钟周期。

调用代码永远不会知道没有找到"真实"服务，也不必担心处理 `NULL`。它被保证始终能获得一个有效对象。

这对于*有意*禁用某项服务也很有用。如果我们想<span name="disable">临时禁用</span>某个系统，现在有了简便的方法：只需不为该服务注册提供者，定位器就会默认使用空提供者。

> **注：** 在开发过程中关闭音频非常方便，可以释放一些内存和 CPU 周期。更重要的是，当一段刺耳的声音正在播放时断点调试，能避免耳膜受苦。没有什么比二十毫秒的尖叫音效以最大音量循环播放更能让你一早提神醒脑的了。

### 日志装饰器

现在系统相当健壮了，让我们讨论这个模式还支持的另一种改进——装饰服务。我用一个例子来说明。

在开发过程中，当有趣的事件发生时记录一些日志，能帮助你搞清楚游戏引擎内部发生了什么。如果你在做 AI，你会想知道实体何时改变了 AI 状态。如果你是音效程序员，你可能想记录每个声音的播放时间，以便检查它们是否以正确的顺序触发。

典型的解决方案是在代码里到处散落 `log()` 函数调用。不幸的是，这只是以一个问题换来另一个问题——现在日志*太多*了。AI 程序员不关心声音何时播放，音效程序员不关心 AI 状态转换，但现在他们都得从对方的日志消息中艰难跋涉。

理想情况下，我们希望能够有选择地只为自己关心的内容启用日志，在最终游戏版本中则完全没有日志。如果我们想有条件地记录日志的那些不同系统都是以服务形式暴露的，就可以用[装饰器模式（Decorator）](http://www.c2.com/cgi/wiki?DecoratorPattern)来解决。让我们这样定义另一个音频服务提供者实现：

```cpp
class LoggedAudio : public Audio
{
public:
  LoggedAudio(Audio &wrapped)
  : wrapped_(wrapped)
  {}

  virtual void playSound(int soundID)
  {
    log("play sound");
    wrapped_.playSound(soundID);
  }

  virtual void stopSound(int soundID)
  {
    log("stop sound");
    wrapped_.stopSound(soundID);
  }

  virtual void stopAllSounds()
  {
    log("stop all sounds");
    wrapped_.stopAllSounds();
  }

private:
  void log(const char* message)
  {
    // Code to log message...
  }

  Audio &wrapped_;
};
```

如你所见，它包裹了另一个音频提供者并暴露相同的接口。它把实际的音频行为转发给内部提供者，同时记录每一次声音调用。如果某个程序员想启用音频日志，他们可以这样调用：

```cpp
void enableAudioLogging()
{
  // Decorate the existing service.
  Audio *service = new LoggedAudio(Locator::getAudio());

  // Swap it in.
  Locator::provide(service);
}
```

现在，所有对音频服务的调用都会先被记录日志，然后一切照旧。当然，这与我们的空服务配合得天衣无缝——你可以在*禁用*音频的同时，仍然记录它*本应*播放的声音。

## 设计决策

我们已经介绍了一种典型实现，但基于对几个核心问题的不同回答，实现方式也会有所差异：

### 服务如何被定位？

**由外部代码注册：**

这是我们的示例代码用于定位服务的机制，也是我在游戏中见过的最常见设计。

- *快速且简单。* `getAudio()` 函数只是返回一个指针，编译器往往会将其内联，这样我们几乎零性能代价地获得了一个良好的抽象层。
- *我们控制提供者的构造方式。* 考虑一项用于访问游戏手柄的服务。我们有两个具体提供者：一个用于本地游戏，一个用于联网游戏。联网提供者通过网络传递手柄输入，使得对游戏其余部分而言，远程玩家看起来就像在使用本地手柄。要实现这一点，联网具体提供者需要知道另一名远程玩家的 IP 地址。如果由定位器自己构造对象，它怎么知道传入什么？`Locator` 类对联网一无所知，更别说某个用户的 IP 地址了。外部注册的提供者绕过了这个问题：不由定位器构造类，而是由游戏的联网代码实例化联网专属的服务提供者（传入所需的 IP 地址），然后将其传给定位器，定位器只需知道服务的抽象接口。
- *可以在游戏运行时更换服务。* 最终游戏版本中也许用不到这个，但在开发中是个很棒的技巧。测试时，我们可以用空服务替换音频服务，在游戏仍在运行时临时禁用声音。
- *定位器依赖外部代码。* 这是缺点所在。任何访问服务的代码都假设某处有代码已经注册了它。如果这个初始化没有发生，我们要么崩溃，要么服务莫名其妙地不工作。

**在编译时绑定：**

这里的思路是：实际的"定位"过程发生在编译时，通过预处理器宏实现，像这样：

```cpp
class Locator
{
public:
  static Audio& getAudio() { return service_; }

private:
  #if DEBUG
    static DebugAudio service_;
  #else
    static ReleaseAudio service_;
  #endif
};
```

以这种方式定位服务意味着：

- *快速。* 所有真正的工作都在编译时完成，运行时什么都不剩。编译器很可能会内联 `getAudio()` 调用，给我们带来尽可能快的解决方案。
- *可以保证服务可用。* 由于定位器现在持有服务并在编译时选择，只要游戏能编译通过，我们就不必担心服务不可用。
- *不能轻易更换服务。* 这是主要缺点。由于绑定发生在构建时，每次想更换服务，都必须重新编译并重启游戏。

**在运行时配置：**

在那片穿卡其裤的企业级软件领地里，如果你说"服务定位器"，他们心里想的就是这个。服务被请求时，定位器在运行时做一些<span name="reflection">魔法</span>来寻找实际请求的实现。

> **注：** *反射（Reflection）*是某些编程语言在运行时与类型系统交互的能力。例如，我们可以通过名字找到一个类，找到其构造函数，然后调用它来创建实例。Lisp、Smalltalk、Python 等动态类型语言天然就支持这一点，而较新的静态语言如 C# 和 Java 也支持反射。

通常，这意味着加载一个配置文件来指定提供者，然后使用反射在运行时实例化那个类。这带来了以下效果：

- *无需重新编译就可以换掉服务。* 这比编译时绑定的服务更灵活，但不如注册式那么灵活——注册式实际上可以在游戏运行时更换服务。
- *非程序员可以更换服务。* 当设计师希望能够打开或关闭某些游戏功能，却不方便修改源代码时，这很方便。（或者更可能是，*程序员*们不希望他们去动源代码。）
- *同一套代码库可以同时支持多种配置。* 由于定位过程已完全从代码库中分离出来，我们可以用同一套代码同时支持多种服务配置。这是这种模式在企业 Web 领域颇具吸引力的原因之一：只需更改一些配置，就能部署一个在不同服务器环境上运行的单一应用程序。历史上，这对游戏用处不大，因为主机硬件相当标准化，但随着越来越多的游戏面向形形色色的移动设备，这一点变得越来越相关。
- *复杂。* 与前几种方案不同，这种方案相当重量级。你必须创建某个配置系统，可能还要编写代码来加载和解析配置文件，总之要*做一些工作*才能定位服务。花在这些代码上的时间，就是没有花在其他游戏功能上的时间。
- *定位服务需要时间。* 现在笑容真的变成了苦瓜脸。采用运行时配置意味着你在定位服务时消耗了一些 CPU 周期。缓存可以将其降至最低，但这仍意味着第一次使用服务时，游戏必须花时间去寻找它。游戏开发者*痛恨*把 CPU 周期消耗在不能改善玩家游戏体验的事情上。

### 如果找不到服务，会怎样？

**让用户自行处理：**

最简单的解决方案是把皮球踢给用户。如果定位器找不到服务，就返回 `NULL`。这意味着：

- *让用户决定如何处理失败。* 有些用户可能认为找不到服务是需要停止游戏的严重错误，有些则可以安全地忽略并继续。如果定位器无法定义一个适用于所有情况的通用策略，那么把失败向下传递，让每个调用点自己决定正确的应对方式，也不失为一个选择。
- *服务的使用者必须处理失败。* 当然，这一点的推论是，每个调用点都*必须*检查服务是否找到。如果几乎所有调用点都以同样的方式处理失败，那就是大量重复代码散落在代码库中。如果可能多达数百个使用服务的地方中，只有一处没有做这个检查，游戏就会崩溃。

**停止游戏：**

我说过，我们无法在编译时*证明*服务始终可用，但这不意味着我们不能*声明*可用性是定位器运行时契约的一部分。最简单的方式是使用断言：

```cpp
class Locator
{
public:
  static Audio& getAudio()
  {
    Audio* service = NULL;

    // Code here to locate service...

    assert(service != NULL);
    return *service;
  }
};
```

如果服务未被找到，游戏会在后续代码尝试使用它之前停止。那个 <span name="assert">`assert()`</span> 调用并不解决找不到服务的问题，但它明确了是谁的问题。通过在这里断言，我们说："找不到服务是定位器的 bug。"

> **注：** [单例模式](http://c2.com/cgi/wiki?SingletonPattern)章节解释了 `assert()` 函数，如果你以前从未见过的话。

这样做有什么效果？

- *用户不需要处理缺失服务的情况。* 由于单个服务可能在数百个地方被使用，这可以节省大量代码。通过声明让定位器始终提供服务，我们免去了服务使用者需要弥补这块空缺的负担。
- *如果找不到服务，游戏将停止。* 万一真的找不到服务，游戏将停止。好处是这迫使我们解决阻止服务被定位的 bug（很可能是某段初始化代码没有在应该调用时被调用），但对于所有被阻塞的其他人来说，在问题修复之前都很痛苦。大型开发团队中，这类情况可能导致一段痛苦的程序员停工期。

**返回空服务：**

我们在示例实现中展示了这种改进。使用它意味着：

- *用户不需要处理缺失服务的情况。* 与上一个方案一样，我们确保始终返回一个有效的服务对象，简化了使用服务的代码。
- *即使服务不可用，游戏也会继续运行。* 这既是好处也是代价。好处在于，即使服务不在，我们也能继续运行游戏。在大型团队中，当我们正在开发的功能可能依赖某个尚未就绪的系统时，这非常有帮助。坏处是，当服务*无意中*缺失时，调试可能更难。假设游戏使用某个服务来访问数据，然后基于这些数据做出决策。如果我们忘记注册真实服务，该代码获得的是空服务，游戏的行为可能就不是我们期望的。<span name="null">这</span>需要花些工夫才能追溯到服务在我们以为它存在时其实并不存在的事实。

  > **注：** 可以通过让空服务在被使用时打印一些调试输出来缓解这一问题。

在这些选项中，我见过最常用的就是直接断言服务可以被找到。当游戏发布时，它已经经过了大量测试，运行在可靠的硬件上，服务找不到的概率已经相当低了。

对于较大的团队，我建议加入一个空服务。实现起来不费多少功夫，却能让你在开发过程中某个服务不可用时免遭停工之苦。它也为你提供了一种简便的方法：当某个服务有 bug 或让你从当前工作中分心时，可以轻松将其关闭。

### 服务的范围是什么？

到目前为止，我们假设定位器将向所有想要的人提供对服务的访问。这是该模式的典型用法，但另一个选项是将访问限制在单个类及其子类中，像这样：

```cpp
class Base
{
  // Code to locate service and set service_...

protected:
  // Derived classes can use service
  static Audio& getAudio() { return *service_; }

private:
  static Audio* service_;
};
```

通过这种方式，对服务的访问被限制在继承 `Base` 的类中。两种方式各有优劣：

**如果访问是全局的：**

- *鼓励整个代码库使用同一项服务。* 大多数服务的设计初衷是单一的。通过允许整个代码库访问同一项服务，我们可以避免代码中随机的地方因无法访问"真实"服务而自行实例化提供者。
- *我们失去了对服务在何处、何时被使用的控制。* 这是让某些东西全局化的显而易见的代价——任何人都可以访问它。[单例模式](http://c2.com/cgi/wiki?SingletonPattern)章节展示了全局范围可能催生的恐怖剧情。

**如果访问被限制在某个类：**

- *我们控制耦合关系。* 这是主要优势。通过将服务限制在继承树的某个分支，我们可以确保本应解耦的系统保持解耦。
- *可能导致重复劳动。* 潜在的缺点是：如果一对不相关的类*确实*需要访问该服务，它们各自需要持有自己对它的引用。用于定位或注册服务的任何过程都必须在这些类之间重复。（另一个选项是调整类层次结构，为这些类设置一个公共基类，但那可能得不偿失。）

我的一般指导原则是：如果服务被限定于游戏中的单一领域，就将其范围限制在某个类中。例如，用于访问网络的服务大概可以限制在联网类中。像日志这类被更广泛使用的服务则应该是全局的。

## 参考

- 在许多方面，服务定位器模式是[单例模式](http://c2.com/cgi/wiki?SingletonPattern)的兄弟，值得将两者都了解，看看哪个更适合你的需求。
- Unity（游戏引擎）框架在其 [`GetComponent()`](http://docs.unity3d.com/412/Documentation/ScriptReference/Component.GetComponent.html?from=index) 方法中，将这个模式与[组件模式](20-component.md)配合使用。
- 微软的 XNA（微软推出的游戏开发框架）游戏开发框架将这个模式内置于其核心 `Game` 类中。每个实例都有一个 `GameServices` 对象，可用于注册和定位任意类型的服务。
