# 脏标记

**所属章节：优化模式**

## 意图

*通过将工作推迟到真正需要结果时才执行，来避免不必要的计算。*

## 动机

许多游戏中都有一个叫做*场景图*的东西。这是一个大型数据结构，包含了世界中的所有对象。渲染引擎用它来确定在屏幕上的哪里绘制什么内容。

最简单的场景图只是一个对象的扁平列表。每个对象都有一个模型（或其他图形图元）和一个<span name="transform">*变换（transform）*</span>。变换描述了对象在世界中的位置、旋转和缩放。要移动或旋转一个对象，只需改变它的变换。

> **注：** 变换的具体存储和操作方式不在本书讨论范围之内。简短到可笑的概括是：它是一个 4×4 矩阵。通过将两个矩阵相乘，可以得到一个合并两个变换的单一变换——比如先平移再旋转一个对象。其原理留给读者作为练习。

当渲染器绘制一个对象时，它取出对象的模型，对其应用变换，然后在世界中的对应位置渲染它。如果我们用的是场景*袋*而非场景*图*，那就到此为止，生活会很简单。

然而，大多数场景图是<span name="hierarchical">*层级式*</span>的。图中的一个对象可能有一个父对象，它被锚定在父对象上。在这种情况下，它的变换是相对于*父对象*位置的，而不是世界中的绝对位置。

举个例子：假设我们的游戏世界里有一艘海上的海盗船。船的桅杆顶上有一个瞭望台，瞭望台里蜷缩着一名海盗，海盗肩上停着一只鹦鹉。船的局部变换决定了船在海上的位置，瞭望台的变换决定了它在船上的位置，依此类推。

<span name="pirate"></span>

*（图示：一艘海盗船，船上有瞭望台，台内有海盗，海盗肩上停着鹦鹉。）*

> **注：** 程序员画的图！

这样，当父对象移动时，其子对象会自动随之移动。如果我们改变船的局部变换，瞭望台、海盗和鹦鹉都会跟着动。如果每次船移动都要手动调整船上所有对象的变换才能防止它们"滑落"，那简直是<span name="slide">噩梦</span>。

> **注：** 说实话，在海上你*确实*要不断手动调整位置以免被甩出去。也许我应该选一个更"陆地"的例子。

但要在屏幕上实际绘制鹦鹉，我们需要知道它在世界中的绝对位置。我把相对于父对象的变换称为对象的*局部变换*，而渲染一个对象需要知道的是它的*世界变换*。

### 局部变换与世界变换

计算一个对象的世界变换相当直接——只需从根节点沿着父链一路向下到达该对象，沿途合并各个变换。换句话说，鹦鹉的世界变换是：

<span name="degenerate"></span>

*（图示：鹦鹉的世界位置由船、瞭望台、海盗和鹦鹉各自局部位置相乘得到。）*

> **注：** 在退化情况下，即对象没有父节点时，其局部变换与世界变换等价。

我们每帧都需要世界中每个对象的世界变换，所以尽管每个模型只有寥寥几次矩阵乘法，这段代码仍位于性能关键的热路径上。保持变换随时更新并不容易——当父对象移动时，会递归地影响其自身及所有子对象的世界变换。

最简单的做法是在渲染时动态计算变换：每帧从层级顶部开始递归遍历场景图，对每个对象即时计算其世界变换并绘制它。

但这实在太浪费宝贵的 CPU 了！世界中许多对象每帧都*不会*移动，想想那些构成关卡的所有静态几何体——每帧都重新计算它们未曾改变的世界变换纯属浪费。

### 缓存世界变换

显而易见的答案是*缓存*它。在每个对象中，我们同时存储其局部变换和推导出的世界变换。渲染时只使用预先计算好的世界变换。如果对象从不移动，缓存的变换始终是最新的，皆大欢喜。

当对象*确实*移动时，简单的做法是立即刷新其世界变换。但别忘了层级！当父对象移动时，我们必须*递归地*重新计算它及其*所有子对象*的世界变换。

想象一帧繁忙的游戏：船在海浪中颠簸，瞭望台在风中摇晃，海盗俯身探向边缘，鹦鹉跳到他头上。我们改变了四个局部变换。如果每次局部变换改变时都急切地重新计算世界变换，最终会发生什么？

<span name="stars"></span>

*（图示：每当对象移动，世界坐标都被急切且冗余地重新计算。）*

> **注：** 标有 ★ 的那几行可以看出，当我们只需要最终结果时，鹦鹉的世界变换却被计算了*四*次。

我们只移动了四个对象，却做了*十*次世界变换计算，其中六次毫无意义——在被渲染器用到之前就被丢弃了。鹦鹉的世界变换被计算了*四*次，但它只被渲染了一次。

问题在于：一个世界变换可能依赖多个局部变换。由于我们每次有*一个*变换改变就立即重新计算，当同一帧内它所依赖的多个局部变换都发生变化时，我们就会多次重新计算同一个变换。

### 推迟重新计算

我们将通过<span name="decoupling">解耦</span>局部变换的改变与世界变换的更新来解决这个问题。这让我们可以批量地修改一堆局部变换，然后在所有修改完成后、渲染需要用到世界变换之前，只重新计算一次受影响的世界变换。

> **注：** 软件架构有多少内容是在刻意地设计一点"松弛"，着实耐人寻味。

为此，我们给图中的每个对象添加一个*标志（flag）*。"标志"和"位"在编程中是同义词——它们都是一微小的数据，只能处于两种状态之一，我们称之为"真"和"假"，或者有时叫"置位"和"清位"，本文会混用这些说法。

当局部变换改变时，我们置位标志；当我们需要对象的世界变换时，检查该标志；如果已置位，就计算世界变换并清位标志。这个标志代表的含义是："世界变换过时了吗？"由于某些不甚明朗的历史原因，这种"过时状态"的传统名称是"脏（dirty）"。因此得名：*脏标记（dirty flag）*。"脏位（dirty bit）"是这个模式同样<span name="specific">常见</span>的叫法，不过我还是选择了听起来不那么古怪的名字。

> **注：** 维基百科的编辑们没有我这种自制力，直接用了 [dirty bit](http://en.wikipedia.org/wiki/Dirty_bit)。

将这个模式应用到前面的示例后，游戏最终会这样做：

*（图示：推迟到所有移动完成后，我们只重新计算一次。）*

这就是你所能期望的最优结果——每个受影响对象的世界变换恰好计算一次。仅用一个比特的数据，这个模式为我们做到了几件事：

- 将对象父链上多个局部变换的修改合并为该对象上的单次重计算；
- 避免对未移动的对象进行重计算；
- 还有一个小奖励：如果一个对象在被渲染之前就被移除了，它的世界变换根本不会被计算。

## 模式结构

一组**主数据**随时间变化。一组**派生数据**通过某种**代价高昂的处理**从主数据推导得出。一个**"脏"标志**跟踪派生数据何时与主数据不同步：在**主数据改变时置位**。当需要派生数据时，若标志已置位，则**重新处理并清位标志**；否则使用此前**缓存的派生数据**。

## 使用时机

与本书中的一些其他模式相比，这个模式解决的是一个相当具体的问题。同样，和大多数优化一样，只有在性能问题足以证明增加代码复杂度值得的时候，才应该考虑使用它。

脏标记应用于两类工作：*计算*和*同步*。在这两种情况下，从主数据到派生数据的过程都是耗时或代价高昂的。

在我们的场景图示例中，这个过程慢是因为需要大量数学运算。而将此模式用于同步时，通常是因为派生数据在*别的地方*——要么在磁盘上，要么在网络另一端的另一台机器上——仅仅是把数据从 A 点传到 B 点就已经代价不菲了。

此外，还有几个前提条件：

- **主数据的改变频率必须高于派生数据的使用频率。** 这个模式的原理是：当后续的主数据改变会在派生数据被用到之前使其失效时，避免对派生数据进行处理。如果你发现每次主数据修改后都立即需要派生数据，这个模式帮不了你。

- **增量更新应当是困难的。** 假设我们游戏里的海盗船只能装载有限的战利品，我们需要知道货舱里所有东西的总重量。我们*可以*使用这个模式，为总重量设一个脏标记——每次添加或移除战利品时置位，需要总重量时把所有战利品加一遍然后清位。但更简单的解决方案是*维护一个滚动总和*：添加或移除物品时，直接把其重量加到或从当前总量中减去。如果能"随用随付"地更新派生数据，这通常比使用这个模式、在需要时从头计算派生数据要好。

这听起来好像脏标记很少适用，但你会在这里那里发现它派上用场的地方。<span name="hacks">在普通游戏代码库中搜索</span>"dirty"这个词，往往会翻出这个模式的使用痕迹。

> **注：** 据我的研究，搜索结果里还会翻出大量为"dirty"补丁道歉的注释。

## 注意事项

即使确信这个模式很合适，也有几个褶皱可能让你不舒服。

### 推迟太久是有代价的

这个模式把某些缓慢的工作推迟到真正需要结果时才执行，但一旦需要，往往是*立刻*就要。而我们使用这个模式的原始原因恰恰是计算这个结果很慢！

在我们的示例中，这不是问题，因为我们仍然能在一帧内快速计算出世界坐标；但可以想象其他情况：你要做的工作是一大块，需要明显的时间来啃完。如果游戏在玩家期待看到结果的那一刻才*开始*啃，可能会造成令人不快的可见<span name="gc">卡顿</span>。

> **注：** 这与自动管理内存的系统中不同的垃圾回收策略如出一辙。引用计数在内存不再需要时立即释放，但会急切地在每次引用改变时消耗 CPU 时间更新引用计数。简单的垃圾回收器会把内存回收推迟到真正需要时，代价是令人闻风丧胆的"GC 停顿"——整个游戏冻结直到回收器扫完堆。介于两者之间的是更复杂的系统，如延迟引用计数和增量 GC，回收内存的积极性介于纯引用计数和全停收集器之间。

推迟的另一个问题是：如果出了什么差错，你可能完全无法执行那项工作。当你使用这个模式把某些状态保存到更持久的形式时，这尤其棘手。

例如，文本编辑器知道你的文档是否有"未保存的更改"——文件标题栏里那个小圆点或星号，字面上就是脏标记的可视化。主数据是内存中打开的文档，派生数据是磁盘上的文件。

*（图示：一个窗口标题栏，显示表示未保存更改的小图标。）*

许多程序要等到文档被关闭或应用程序退出时才写入磁盘，大多数时候没什么问题，但如果你不小心踢掉了电源线，你的杰作就没了。

在后台自动保存备份的编辑器，正是专门为了弥补这一缺陷。自动保存的频率是在崩溃时不丢失太多工作与不因频繁保存而过度消耗文件系统之间的平衡点。

### 每次状态改变时都必须确保置位标志

由于派生数据是从主数据计算出来的，它本质上是一个缓存。每当有缓存数据，最棘手的方面就是<span name="cache">*缓存失效（cache invalidation）*</span>——正确地标注缓存何时与其源数据不同步。在这个模式中，这意味着在*任何*主数据改变时都要置位脏标志。

> **注：** Phil Karlton 有句名言："计算机科学中只有两件难事：缓存失效和命名。"

只要有一处遗漏，程序就会错误地使用过时的派生数据，导致玩家困惑和极难追踪的 bug。使用这个模式时，必须确保任何修改主状态的代码同时也置位脏标志。

一种缓解措施是将对主数据的修改封装在某个接口后面。如果所有能改变状态的操作都经过一个单一的窄 API，就可以在那里置位脏标志，确保不会有遗漏。

### 必须在内存中保留之前的派生数据

<span name="sync"></span>

当需要派生数据且脏标志*未*置位时，使用的是之前计算好的数据。这显而易见，但确实意味着你必须把那份派生数据保留在内存中，以备后续需要时使用。

> **注：** 当你使用这个模式将主状态同步到其他地方时，这不是什么大问题——在那种情况下，派生数据通常根本不在内存中。

如果不使用这个模式，可以在需要时动态计算派生数据，用完后丢弃。这避免了把数据缓存在内存中的开销，代价是每次需要结果时都要重新计算。

和许多优化一样，这个模式在<span name="trade">以内存换速度</span>。通过把之前计算好的数据保留在内存中，避免了在数据未改变时重新计算。当计算很慢而内存廉价时，这种取舍是合算的；当你时间充裕但内存紧张时，按需计算更好。

> **注：** 反之，压缩算法做的是相反的取舍——以解压所需的处理时间为代价来优化*空间*。

## 示例代码

假设我们满足了那个出乎意料之长的前提条件列表，来看看这个模式的代码实现。如前所述，变换矩阵背后的实际数学超出了本书的目标范围，所以我会把它封装在一个类里，其实现假设存在于某处：

```cpp
class Transform
{
public:
  static Transform origin();

  Transform combine(Transform& other);
};
```

我们在这里只需要一个操作：`combine()`，用它来通过合并父链上所有局部变换来获得一个对象的世界变换。它还有一个获取"原点"变换的方法——基本上就是一个单位矩阵，表示没有任何平移、旋转或缩放。

接下来，我们粗略描绘场景图中一个对象的类。这是应用这个模式*之前*所需的最少内容：

```cpp
class GraphNode
{
public:
  GraphNode(Mesh* mesh)
  : mesh_(mesh),
    local_(Transform::origin())
  {}

private:
  Transform local_;
  Mesh* mesh_;

  GraphNode* children_[MAX_CHILDREN];
  int numChildren_;
};
```

每个节点都有一个局部变换，描述它相对于父节点的位置；有一个网格（mesh），是对象的实际图形（我们也允许 `mesh_` 为 `NULL`，以处理仅用于对子节点分组的非可视节点）；最后，每个节点还有一个可能为空的子节点集合。

有了这些，"场景图"实际上只是一个单一的根 `GraphNode`，其子节点（以及孙节点等）是世界中的所有对象：

```cpp
GraphNode* graph_ = new GraphNode(NULL);
// Add children to root graph node...
```

为了渲染一个场景图，我们只需从根节点开始遍历整棵节点树，为每个节点的网格以正确的世界变换调用以下函数：

```cpp
void renderMesh(Mesh* mesh, Transform transform);
```

我们不在这里实现它，但如果实现，它将执行渲染器在给定世界位置绘制该网格所需的任何魔法。如果能正确高效地为场景图中的每个节点调用它，我们就达到目标了。

### 未经优化的遍历

为了入手，让我们随手搭建一个基本的场景图遍历来渲染，动态计算世界位置。这不是最优的，但很简单。我们给 `GraphNode` 添加一个新方法：

```cpp
void GraphNode::render(Transform parentWorld)
{
  Transform world = local_.combine(parentWorld);

  if (mesh_) renderMesh(mesh_, world);

  for (int i = 0; i < numChildren_; i++)
  {
    children_[i]->render(world);
  }
}
```

我们用 `parentWorld` 传入节点父对象的世界变换。有了它，要得到*当前*节点正确的世界变换，只需将其与自身的局部变换合并。我们不必*往上*沿父链计算世界变换，因为在*向下*遍历时我们是边走边算的。

我们计算节点的世界变换并存入 `world`，然后渲染网格（如果有）。最后，我们递归进入子节点，传入*当前*节点的世界变换。总体而言，这是一个紧凑而简洁的递归方法。

要绘制整个场景图，从根节点开始启动这个过程：

```cpp
graph_->render(Transform::origin());
```

### 引入脏标记

这段代码做的事是正确的——它把所有网格都绘制在正确的位置——但效率不高：它对图中每个节点、每帧都调用 `local_.combine(parentWorld)`。让我们看看这个模式如何修复它。首先，需要给 `GraphNode` 添加两个字段：

```cpp
class GraphNode
{
public:
  GraphNode(Mesh* mesh)
  : mesh_(mesh),
    local_(Transform::origin()),
    dirty_(true)
  {}

  // Other methods...

private:
  Transform world_;
  bool dirty_;
  // Other fields...
};
```

`world_` 字段缓存之前计算的世界变换，`dirty_` 当然就是脏标志。注意标志初始值为 `true`——当我们创建一个新节点时，还没有计算其世界变换，它一出生就已经与局部变换不同步了。

我们需要这个模式的唯一原因是对象可以*移动*，所以我们加上对此的支持：

```cpp
void GraphNode::setTransform(Transform local)
{
  local_ = local;
  dirty_ = true;
}
```

重要的是它同时置位了脏标志。我们是否遗漏了什么？对——子节点！

当父节点移动时，其所有子节点的世界坐标也失效了。但在这里，我们没有置位它们的脏标志。我们*可以*这样做，但那是递归且缓慢的。相反，我们会在渲染时做一些聪明的事情。让我们看看：

<span name="branch"></span>

```cpp
void GraphNode::render(Transform parentWorld, bool dirty)
{
  dirty |= dirty_;
  if (dirty)
  {
    world_ = local_.combine(parentWorld);
    dirty_ = false;
  }

  if (mesh_) renderMesh(mesh_, world_);

  for (int i = 0; i < numChildren_; i++)
  {
    children_[i]->render(world_, dirty);
  }
}
```

> **注：** 这里有一个微妙的假设：`if` 检查比矩阵乘法更快。直觉上你会认为确实如此——测试单个位肯定比一堆浮点运算快。然而，现代 CPU 极其复杂，它们大量依赖*流水线*——将一系列顺序指令排队。像这里的 `if` 这样的分支可能导致*分支预测失败*，迫使 CPU 浪费周期重新填充流水线。[数据局部性](24-data-locality.md)章节有更多关于现代 CPU 如何尝试提速以及如何避免像这样绊倒它们的内容。

这与原始的朴素实现类似，关键的变化是：在计算世界变换之前检查节点是否为脏状态，并将结果存入字段而非局部变量。当节点是干净的，我们完全跳过 `combine()`，直接使用虽旧但仍正确的 `world_` 值。

<span name="clever">聪明</span>之处在于那个 `dirty` 参数。如果这个节点在父链中任何一个祖先节点是脏的，`dirty` 就为 `true`。正如 `parentWorld` 在向下遍历层级时逐步更新世界变换，`dirty` 追踪整条父链的脏状态。

这让我们在 `setTransform()` 中无需递归地标记每个子节点的 `dirty_` 标志——我们在渲染时把父节点的脏状态向下传递给子节点，并综合考虑它来判断是否需要重新计算世界变换。

最终结果正是我们想要的：改变节点的局部变换只是几次赋值操作，而渲染世界时会恰好计算自上一帧以来改变过的最少量的世界变换。

> **注：** 注意这个聪明的技巧只有在 `render()` 是 `GraphNode` 中*唯一*需要最新世界变换的东西时才有效。如果有其他地方也需要访问它，就得做些不同的处理。

## 设计决策

这个模式相当具体，所以可以调整的地方只有几个：

### 脏标志何时被清除？

**当需要结果时：**

- *如果结果永远不被用到，可以完全避免计算。* 对于比派生数据被访问频率高得多的主数据，这可能是很大的收益。
- *如果计算耗时，可能导致明显的卡顿。* 把工作推迟到玩家期待看到结果的那一刻，可能会影响游戏体验。通常足够快，不成问题，但如果真成了问题，就得提前执行这项工作。

**在明确定义的检查点：**

有时，游戏中存在某个时间点或进程节点，在那里做推迟的处理是自然的。例如，我们可能只在海盗驶入港口时才保存游戏；或者同步点不是游戏机制的一部分，只是把工作藏在加载屏幕或过场动画后面。

- *执行工作不影响用户体验。* 与上一个选项不同，通常可以给玩家一些分散注意力的东西，让他们在游戏忙于处理时不会注意到。
- *你失去了对工作何时发生的控制。* 这与上一点的方向相反——你对处理时机有微观层面的控制，可以确保游戏优雅地处理它。但你*无法*确保玩家真的到达了检查点或满足了你定义的任何条件。如果玩家迷路或游戏进入奇怪的状态，你最终推迟的时间可能远超预期。

**在后台：**

通常，在第一次修改时启动一个固定的<span name="hysteresis">计时器</span>，然后处理在此期间到计时器触发之间发生的所有变化。

> **注：** 人机交互中，程序接收到用户输入到做出响应之间有意设置的延迟叫做 [*hysteresis（迟滞）*](http://en.wikipedia.org/wiki/Hysteresis)。

- *可以调整处理频率。* 通过调整计时器间隔，可以确保处理以你希望的频率（或低频率）发生。
- *可能做更多冗余的工作。* 如果在计时器运行期间主状态只改变了一点点，你可能最终处理了大量几乎没有变化的数据。
- *需要支持异步执行工作。* "在后台"处理数据意味着玩家同时可以继续做他们正在做的事。这意味着可能需要线程或某种并发支持，以便游戏在仍在运行时也能处理数据。由于玩家很可能在与你正在处理的同一份主状态交互，还需要考虑如何使其安全地支持并发修改。

### 脏状态追踪的粒度如何？

想象我们的海盗游戏让玩家建造和定制自己的海盗船，船会自动在线保存，玩家可以从中断处继续。我们使用脏标志来确定船的哪些甲板被改动过、需要发送到服务器。我们发送给服务器的每个数据块包含一些修改过的船体数据和描述该修改发生在船上哪个位置的元数据。

**粒度更细时：**

假设你给每块甲板的每一根木板都贴上脏标志。

- *只处理实际改变的数据。* 你只会把被修改的那些面发送给服务器。

**粒度更粗时：**

或者，我们可以将一个脏位关联到每块整体甲板，对其上任何内容的改动都把整块甲板标记为<span name="swab">脏</span>。

> **注：** 这里本可以讲个关于"甲板要洗干净"的糟糕双关，但我忍住了。

- *会处理未改变的数据。* 在甲板上放一个木桶，就得把整块甲板发送给服务器。
- *存储脏标志所用的内存更少。* 在甲板上放十个木桶，只需一个位来追踪它们全部。
- *固定开销上花的时间更少。* 处理某些改变过的数据时，除了处理数据本身之外，往往还有一些固定的工作要做。在本例中，那就是标识变更数据在船上位置所需的元数据。处理的数据块越大，块数就越少，开销也就越少。

## 参考

- 这个模式在游戏之外也很常见，比如浏览器端的 Web 框架 Angular（一个前端 Web 框架）。它们使用脏标志来追踪哪些数据在浏览器端发生了变化、需要推送到服务器。
- 物理引擎追踪哪些对象在运动、哪些在静止。处于静止的物体在受到冲击之前不会移动，所以在被触及之前不需要处理。这个"是否在运动"的位就是一个脏标志，标注哪些对象受到了力的作用、需要解算物理。
