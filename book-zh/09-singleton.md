# 单例模式

> **重访设计模式**

这一章是个异类。本书其他每一章都在告诉你如何**使用**一个设计模式，这一章却在告诉你如何**不**使用它。

尽管出发点是好的，四人帮所描述的[单例（Singleton）](http://c2.com/cgi/wiki?SingletonPattern)模式，造成的伤害往往大于它带来的益处。他们强调这个模式应该谨慎使用，但这句话在传入游戏行业时，却经常被丢失在翻译里。

就像任何模式一样，在不该用单例的地方用它，大概和用夹板治疗枪伤一样有用。由于它被过度使用，本章大部分内容都将讲**避免**使用单例——但首先，让我们过一遍模式本身。

> 当行业从 C 语言转向面向对象编程时，遇到了一个问题："我怎么获取实例？"他们有想调用的方法，却手头没有提供那个方法的对象实例。单例——换句话说，就是把它变成全局的——是一种省事的出路。

## 单例模式

《设计模式》对单例的概括如下：

> 确保一个类只有一个实例，并为其提供一个全局访问点。

我们在"并"字处切开，分别考虑两半。

### 将类限制为单个实例

有时候，如果一个类有多于一个实例，它就无法正常工作。常见情况是这个类与某个维护自身全局状态的外部系统交互。

设想一个封装了底层文件系统 API 的类。由于文件操作可能需要一段时间才能完成，这个类以异步方式执行操作。这意味着多个操作可以并发运行，所以它们必须相互协调。如果我们同时发起一个创建文件的调用和一个删除同一文件的调用，我们的封装类需要同时感知这两者，以确保它们不会互相干扰。

为此，调用我们封装类的代码需要能访问所有之前的操作。如果用户可以随意创建类的实例，一个实例就无从得知其他实例发起的操作。单例模式正是解法：它提供了一种在编译期确保类只有单一实例的方式。

### 提供全局访问点

游戏中多个不同的系统都会用到我们的文件系统封装类：日志、内容加载、游戏存档，等等。如果这些系统无法自行创建文件系统封装类的实例，它们怎么拿到那个实例？

单例模式对这个问题也有解法。除了创建唯一实例，它还提供了一个全局可访问的方法来获取它。这样，任何地方的任何代码都能拿到那个宝贵的实例。综合起来，经典实现长这样：

```cpp
class FileSystem
{
public:
  static FileSystem& instance()
  {
    // 懒初始化。
    if (instance_ == NULL) instance_ = new FileSystem();
    return *instance_;
  }

private:
  FileSystem() {}

  static FileSystem* instance_;
};
```

静态成员 `instance_` 持有类的一个实例，私有构造函数确保它是**唯一**一个。公有静态方法 `instance()` 从代码库中任何地方授予对该实例的访问。它还负责在第一次有人请求时懒初始化（lazy initialize）单例实例。

更现代的写法是这样：

```cpp
class FileSystem
{
public:
  static FileSystem& instance()
  {
    static FileSystem *instance = new FileSystem();
    return *instance;
  }

private:
  FileSystem() {}
};
```

C++11 规定局部静态变量的初始化器只会执行一次，即便在并发环境下也是如此。因此，假设你用的是现代 C++ 编译器，这段代码是线程安全的，而第一个例子则不是。

> 当然，你的单例类本身是否线程安全，那是完全另一个问题！这里只保证了它的**初始化**是线程安全的。

## 为什么我们使用它

看来我们找到了赢家。文件系统封装类在任何需要它的地方都唾手可得，无需到处传递它的麻烦。这个类本身也聪明地确保我们不会因为创建几个实例而把事情搞砸。它还有一些其他优点：

**如果没有人使用它，就不创建实例。** 节省内存和 CPU 时钟周期永远是好事。由于单例只在第一次被访问时初始化，如果游戏从不请求它，它根本不会被实例化。

**它在运行时初始化。** 单例的一个常见替代方案是带静态成员变量的类。我偏爱简单的方案，所以尽可能用静态类代替单例，但静态成员有一个限制：自动初始化。编译器在 `main()` 被调用之前初始化静态变量，这意味着它们无法使用只有在程序运行起来之后才能得知的信息（例如从文件加载的配置）。这也意味着它们无法可靠地相互依赖——编译器不保证静态变量之间的初始化顺序。

懒初始化解决了这两个问题。单例会尽可能晚地初始化，到那时它所需的任何信息都应该已经就绪。只要没有循环依赖，一个单例甚至可以在初始化自身时引用另一个单例。

**可以对单例进行子类化。** 这是一个强大但经常被忽视的能力。假设我们需要文件系统封装类支持跨平台。为此，我们希望它成为文件系统的一个抽象接口，子类针对每个平台实现该接口。基类如下：

```cpp
class FileSystem
{
public:
  virtual ~FileSystem() {}
  virtual char* readFile(char* path) = 0;
  virtual void  writeFile(char* path, char* contents) = 0;
};
```

然后我们为几个平台定义派生类：

```cpp
class PS3FileSystem : public FileSystem
{
public:
  virtual char* readFile(char* path)
  {
    // 使用 Sony 文件 IO API……
  }

  virtual void writeFile(char* path, char* contents)
  {
    // 使用 Sony 文件 IO API……
  }
};

class WiiFileSystem : public FileSystem
{
public:
  virtual char* readFile(char* path)
  {
    // 使用 Nintendo 文件 IO API……
  }

  virtual void writeFile(char* path, char* contents)
  {
    // 使用 Nintendo 文件 IO API……
  }
};
```

接下来，我们把 `FileSystem` 改造成单例：

```cpp
class FileSystem
{
public:
  static FileSystem& instance();

  virtual ~FileSystem() {}
  virtual char* readFile(char* path) = 0;
  virtual void  writeFile(char* path, char* contents) = 0;

protected:
  FileSystem() {}
};
```

聪明的地方在于实例如何创建：

```cpp
FileSystem& FileSystem::instance()
{
  #if PLATFORM == PLAYSTATION3
    static FileSystem *instance = new PS3FileSystem();
  #elif PLATFORM == WII
    static FileSystem *instance = new WiiFileSystem();
  #endif

  return *instance;
}
```

只需一个简单的编译器开关，我们就把文件系统封装类绑定到了正确的具体类型。整个代码库都可以通过 `FileSystem::instance()` 访问文件系统，而不必与任何平台特定的代码耦合。那种耦合被封装在 `FileSystem` 类本身的实现文件里。

走到这一步，我们大多数人在面对类似问题时基本就到头了。文件系统封装类有了，运行可靠，全局可访问，需要它的地方都能拿到。是时候提交代码，再来一杯好饮料庆祝一番了。

## 为什么我们后悔使用它

短期来看，单例模式相对无害。和很多设计决策一样，代价在长期才会显现。一旦我们向代码里铸入了几个不必要的单例，麻烦就接踵而至：

### 它是个全局变量

当游戏还是几个家伙在车库里写的时候，压榨硬件性能比象牙塔里的软件工程原则重要得多。老派的 C 和汇编程序员毫无顾忌地使用全局变量和静态变量，一样能做出好游戏。随着游戏越来越大、越来越复杂，架构和可维护性开始成为瓶颈。我们无法按时发版，不是因为硬件限制，而是因为**效率**限制。

于是我们迁移到 C++ 这样的语言，开始应用前人软件工程师用血汗换来的智慧。我们学到的一课是：全局变量有多种坏处——

**它们让代码更难推理。** 假设我们在追踪一个别人写的函数里的 bug。如果那个函数不触碰任何全局状态，只需理解函数体本身和传入的参数，就能理清头绪。

> 计算机科学家把不访问或修改全局状态的函数称为"纯"函数（pure function）。纯函数更容易推理，编译器也更容易优化，还能做诸如记忆化这样的好事——把先前调用的结果缓存起来供后续复用。
>
> 尽管纯粹地使用纯函数有其挑战，但好处足够诱人，以至于计算机科学家创造了 Haskell（一种函数式编程语言）这样**只允许**纯函数的语言。

现在，想象就在函数正中间有一句 `SomeClass::getSomeGlobalData()` 的调用。要弄清楚发生了什么，我们得在整个代码库里翻找，看看谁碰了那份全局数据。你只有在凌晨三点 `grep` 过一百万行代码、试图找到那个把静态变量设成错误值的漏网之鱼，才会真正体会到对全局状态的深恶痛绝。

**它们助长耦合。** 团队里的新人不熟悉你精心设计的、松耦合的、可维护的游戏架构，但他刚拿到第一个任务：让巨石砸地时播放音效。你我都知道不应该让物理代码与**音频**这种东西耦合，但他只是想完成任务。偏偏我们的 `AudioPlayer` 实例是全局可见的。于是，一个小小的 `#include` 之后，新人就破坏了一套精心构建的架构。

如果音频播放器没有全局实例，就算他 `#include` 了头文件，也没法用它做任何事。这种阻力清楚地告诉他：这两个模块不应该互相了解，他需要找另一种方式解决问题。**通过控制对实例的访问，你就控制了耦合。**

**它们对并发不友好。** 游戏跑在简单的单核 CPU 上的时代基本已经过去了。今天的代码至少必须**能在**多线程环境下运行，即便不充分利用并发。当我们把什么东西变成全局的，就创造了一块每个线程都能看到并随意拨弄的内存，不管它们是否知道其他线程在对它做什么。这条路通向死锁、竞态条件，以及其他难以修复的线程同步 bug。

这些问题足以让我们对声明全局变量望而却步，进而也对单例模式望而却步。但这仍然没有告诉我们**应该**如何设计游戏。如何在没有全局状态的情况下架构一款游戏？

这个问题有一些深入的答案——本书在很多方面*就是*对这个问题的一个回答——但这些答案并不显而易见，也不容易找到。与此同时，游戏还是得按时发版。单例模式看起来像万灵药，它出现在一本面向对象设计模式的书里，所以架构上一定是合理的，对吧？而且它让我们能用几十年来一直在用的方式写软件。

遗憾的是，它与其说是良药，不如说是安慰剂。翻看全局变量带来的那串问题，你会发现单例模式一个也没解决。因为单例**就是**全局状态——只是封装在了一个类里。

### 它同时解决两个问题，即使你只有其中一个

四人帮在描述单例时用的那个"并"字有点耐人寻味。这个模式是解决一个问题，还是两个？如果我们只有其中一个问题呢？确保唯一实例是有用的，但谁说我们想让**所有人**都去拨弄它？同样，全局访问很方便，但这对允许多个实例的类也同样成立。

这两个问题中，后者——便捷访问——几乎总是我们求助于单例模式的理由。想想一个日志类。游戏里的大多数模块都能从输出诊断信息中受益。然而，把 `Log` 类的实例传给每一个需要它的函数，会污染方法签名，也会分散代码的意图。

显而易见的修法是把 `Log` 类改成单例，之后每个函数都可以直接向类本身要实例。但这么一来，我们不经意间获得了一个奇怪的小限制：突然间，我们再也无法创建多于一个的日志记录器了。

起初这不是问题——我们只写一个日志文件，所以反正只需要一个实例。然后，开发周期深处，麻烦来了。团队里每个人都用日志记录器输出自己的诊断信息，日志文件变成了一个巨大的垃圾场。程序员要在一页页文字里跋山涉水，才能找到自己关心的那条记录。

我们想通过把日志分割成多个文件来解决这个问题：为不同的游戏领域设置独立的日志记录器，如网络、UI、音频、玩法。但我们做不到。不仅是我们的 `Log` 类不允许创建多个实例，这个设计限制还深入地嵌在每一个使用它的调用点里：

```
Log::instance().write("Some event.");
```

要让 `Log` 类支持多实例化（就像它最初那样），我们既要修改类本身，也要修改每一行提到它的代码。那种便捷访问，已经不再便捷了。

> 情况甚至可能更糟。想象你的 `Log` 类在一个被多个**游戏**共享的库里。现在，要改变这个设计，你必须协调多个团队的变更，而他们中的大多数人既没有时间也没有动力去修它。

### 懒初始化剥夺了你的控制权

在拥有虚拟内存和宽松性能要求的桌面 PC 世界里，懒初始化是个聪明的技巧。游戏是另一回事。初始化一个系统可能需要时间：分配内存、加载资源，等等。如果初始化音频系统要几百毫秒，我们需要控制**何时**发生这件事。如果让它在第一次播放声音时懒初始化自己，那可能正好是游戏里一段紧张刺激的场面，导致肉眼可见的掉帧和卡顿。

同样，游戏通常需要严格控制堆内存的布局方式，以避免内存碎片。如果我们的音频系统在初始化时在堆上分配一块内存，我们想知道初始化**何时**发生，这样才能控制那块内存**在堆的哪个位置**。

> 参见[对象池](object-pool.html)，那里有对内存碎片的详细解释。

由于这两个问题，我见过的大多数游戏都不依赖懒初始化。它们改为这样实现单例模式：

```cpp
class FileSystem
{
public:
  static FileSystem& instance() { return instance_; }

private:
  FileSystem() {}

  static FileSystem instance_;
};
```

这解决了懒初始化的问题，但代价是丢弃了单例几个确实优于裸全局变量的特性。用静态实例，就无法再使用多态，而且类必须在静态初始化时就能被构造。当不再需要实例时，也无法释放它占用的内存。

与其说创建了一个单例，这里实际上是一个简单的静态类。这不一定是坏事，但如果一个静态类就是你需要的全部，为何不彻底去掉 `instance()` 方法，直接用静态函数呢？`Foo::bar()` 比 `Foo::instance().bar()` 更简洁，也更清楚地表明你确实在和静态内存打交道。

> 选择单例而不是静态类的惯常理由是：如果你后来决定把静态类改成非静态的，就得修改每一个调用点。理论上，单例不需要这样——你可以传递实例并像普通实例方法一样调用它。
>
> 然而实际上，我从没见过这么做的。大家都直接在一行里写 `Foo::instance().bar()`。如果我们把 Foo 改成非单例，该改的调用点一个也跑不掉。既如此，我宁可有一个更简单的类和更简洁的调用语法。

## 我们能用什么替代

如果我到目前为止达到了目的，你下次遇到问题时，会在伸手拿单例之前三思。但你还是有个问题要解决，应该拿什么工具来用？取决于你想做什么，我有几个选项供你考虑。但首先……

### 先看看是否真的需要这个类

我在游戏里见到的很多单例类都是"管理器"——那些含糊其辞的类，存在的意义仅仅是守护其他对象。我见过这样的代码库：仿佛**每个**类都有一个管理器——Monster、MonsterManager、Particle、ParticleManager、Sound、SoundManager、ManagerManager。有时候为了变化，会夹一个"System"或"Engine"进去，但本质上还是同一回事。

守护者类有时是有用的，但更多时候只是反映了对 OOP 的不熟悉。来看这两个刻意构造的类：

```cpp
class Bullet
{
public:
  int getX() const { return x_; }
  int getY() const { return y_; }

  void setX(int x) { x_ = x; }
  void setY(int y) { y_ = y; }

private:
  int x_, y_;
};

class BulletManager
{
public:
  Bullet* create(int x, int y)
  {
    Bullet* bullet = new Bullet();
    bullet->setX(x);
    bullet->setY(y);

    return bullet;
  }

  bool isOnScreen(Bullet& bullet)
  {
    return bullet.getX() >= 0 &&
           bullet.getX() < SCREEN_WIDTH &&
           bullet.getY() >= 0 &&
           bullet.getY() < SCREEN_HEIGHT;
  }

  void move(Bullet& bullet)
  {
    bullet.setX(bullet.getX() + 5);
  }
};
```

也许这个例子有点蠢，但我见过大量代码，刮去表面那层硬壳后，正是这样的设计。看到这段代码，很自然地会觉得 `BulletManager` 应该是个单例——毕竟，凡是有 `Bullet` 的地方也会需要管理器，你需要几个 `BulletManager` 实例呢？

答案其实是**零**。以下是我们如何解决管理器类的"单例"问题：

```cpp
class Bullet
{
public:
  Bullet(int x, int y) : x_(x), y_(y) {}

  bool isOnScreen()
  {
    return x_ >= 0 && x_ < SCREEN_WIDTH &&
           y_ >= 0 && y_ < SCREEN_HEIGHT;
  }

  void move() { x_ += 5; }

private:
  int x_, y_;
};
```

搞定。没有管理器，没有问题。设计糟糕的单例往往是"助手"，给另一个类添加功能。如果可以，就把所有那些行为直接移进它帮忙的那个类里。毕竟，OOP 的精髓就是让对象照顾好自己。

除了管理器之外，还有其他我们会伸手拿单例来解决的问题。针对这些问题，有几种替代方案值得考虑。

### 将类限制为单个实例

这是单例模式所给你的两样东西之一。就像我们的文件系统例子，确保类只有单一实例有时候至关重要。然而，这不一定意味着我们同时想提供对那个实例的**公开的全局**访问。我们可能想把访问限制在代码的某些区域，甚至让它对某个类私有。在这些情况下，提供一个公开的全局访问点只会削弱架构。

> 例如，我们可能在把文件系统封装类套进**另一层**抽象里。

我们想要一种确保唯一实例化的方式，而**不**提供全局访问。有几种方法可以做到。这里是其中之一：

```cpp
class FileSystem
{
public:
  FileSystem()
  {
    assert(!instantiated_);
    instantiated_ = true;
  }

  ~FileSystem() { instantiated_ = false; }

private:
  static bool instantiated_;
};

bool FileSystem::instantiated_ = false;
```

这个类允许任何人构造它，但如果你试图创建多于一个实例，它会触发断言并失败。只要正确的代码率先创建实例，就确保了其他代码既无法访问那个实例，也无法创建自己的。这个类确保了它关心的唯一实例化要求，但并没有规定这个类应该如何使用。

> **断言**（assertion）函数是一种把契约嵌入代码的方式。当 `assert()` 被调用时，它对传给它的表达式求值。如果求值为 `true`，它什么也不做，游戏继续运行。如果求值为 `false`，它立即在那个点停止游戏。在调试构建里，它通常会拉起调试器，或者至少打印出断言失败的文件和行号。
>
> `assert()` 的意思是："我断言这里应该永远是真的。如果不是，那就是 bug，我想**现在**就停下来让你去修它。"这让你可以在代码区域之间定义契约。如果一个函数断言它的某个参数不是 `NULL`，那就是在说："我与调用者之间的契约是：不会把 `NULL` 传给我。"
>
> 断言帮助我们在游戏做了意外之举时第一时间追踪到 bug，而不是等到那个错误最终以某种对用户可见的方式显现出来。它们是代码库里的围栏，把 bug 圈在产生它的那段代码里，让它们无处可逃。

这种实现的缺点是，防止多次实例化的检查只在**运行时**进行。而单例模式，恰恰相反，通过类的结构本身在编译期保证了单一实例。

### 提供便捷的实例访问

便捷访问是我们求助于单例的主要原因。它让我们轻松拿到在许多不同地方都需要用到的对象。但这种便捷是有代价的——它同样让我们轻松地在**不该**用它的地方拿到这个对象。

通用原则是：在仍能完成任务的前提下，让变量的作用域尽可能窄。一个对象的作用域越小，我们在使用它时需要在脑子里同时维护的地方就越少。在采用单例这把**全局**作用域的霰弹枪之前，先考虑代码库中其他让代码能访问到对象的方式：

**直接传入。** 最简单的方案，往往也是最好的，就是把你需要的对象作为参数直接传给需要它的函数。在把它当作过于繁琐而丢弃之前，值得先认真考虑一下。

> 有些人用"依赖注入"（dependency injection）来描述这件事。不是让代码**伸出手**、通过调用某个全局的东西来找到依赖，而是通过参数把依赖**推入**需要它的代码中。另一些人把"依赖注入"保留给向代码提供依赖的更复杂方式。

考虑一个渲染对象的函数。为了渲染，它需要访问一个代表图形设备并维护渲染状态的对象。通常最简单的做法是直接把它传入所有渲染函数，通常是一个名为 `context` 之类的参数。

另一方面，有些对象并不适合出现在方法签名里。例如，一个处理 AI 的函数也许需要向日志文件写点东西，但日志并不是它的核心关注点。在参数列表里看到 `Log` 会显得奇怪，所以对于这类情况，我们需要考虑其他选项。

> 像日志这样散落在代码库各处的东西，术语叫"横切关注点"（cross-cutting concern）。优雅地处理横切关注点是一个持续的架构挑战，在静态类型语言中尤为如此。
>
> [面向切面编程](http://en.wikipedia.org/wiki/Aspect-oriented_programming)正是为了解决这些问题而设计的。

**从基类获取。** 很多游戏架构采用浅而宽的继承层次，通常只有一层深度。例如，你可能有一个 `GameObject` 基类，然后每个敌人或游戏对象都有对应的派生类。在这类架构里，大量游戏代码会住在这些"叶子"派生类里。这意味着所有这些类已经能访问同一个东西：它们的 `GameObject` 基类。我们可以利用这一点：

```cpp
class GameObject
{
protected:
  Log& getLog() { return log_; }

private:
  static Log& log_;
};

class Enemy : public GameObject
{
  void doSomething()
  {
    getLog().write("I can log!");
  }
};
```

这确保了 `GameObject` 外部的代码无法访问它的 `Log` 对象，但每个派生实体都可以通过 `getLog()` 访问。让派生对象用基类提供的受保护方法来实现自身的这种模式，在[子类沙箱](subclass-sandbox.html)一章中有详细介绍。

> 这引出了一个问题："`GameObject` 是怎么拿到 `Log` 实例的？"一个简单的方案是让基类自己创建并持有一个静态实例。
>
> 如果你不想让基类扮演这么主动的角色，可以提供一个初始化函数让外部传入，或者使用[服务定位器](service-locator.html)模式来找到它。

**从某个已经是全局的东西获取。** 彻底消灭**所有**全局状态的目标值得称赞，但在实践中很少可行。大多数代码库仍然有几个全局可用的对象，比如一个代表整个游戏状态的单一 `Game` 或 `World` 对象。

我们可以通过搭已有全局对象的便车，来减少全局类的数量。与其把 `Log`、`FileSystem` 和 `AudioPlayer` 各自改成单例，不如这样做：

```cpp
class Game
{
public:
  static Game& instance() { return instance_; }

  // 用于设置 log_ 等的函数……

  Log&         getLog()         { return *log_; }
  FileSystem&  getFileSystem()  { return *fileSystem_; }
  AudioPlayer& getAudioPlayer() { return *audioPlayer_; }

private:
  static Game instance_;

  Log         *log_;
  FileSystem  *fileSystem_;
  AudioPlayer *audioPlayer_;
};
```

这样，只有 `Game` 是全局可用的。各函数可以**通过**它访问其他系统：

```cpp
Game::instance().getAudioPlayer().play(VERY_LOUD_BANG);
```

> 纯粹主义者会说这违反了迪米特法则（Law of Demeter）。我的说法是，这仍然比一堆单例好。

如果之后架构改为支持多个 `Game` 实例（也许为了流式加载或测试目的），`Log`、`FileSystem` 和 `AudioPlayer` 都不受影响——它们甚至感知不到有任何变化。当然，这样做的缺点是更多代码最终与 `Game` 本身耦合。如果一个类只是需要播放声音，我们的例子仍然要求它了解整个游戏世界才能拿到音频播放器。

我们用一个混合方案来解决这个问题：已经了解 `Game` 的代码可以直接从它那里访问 `AudioPlayer`；对于不了解 `Game` 的代码，我们用这里描述的其他选项之一来提供对 `AudioPlayer` 的访问。

**从服务定位器获取。** 到目前为止，我们假设全局类是某个普通的具体类，如 `Game`。另一个选项是定义一个类，其唯一存在理由就是提供对对象的全局访问。这种常见模式叫做[服务定位器](service-locator.html)，它有自己专属的一章。

## 单例的剩余用场

问题依然在：**应该**在哪里使用真正的单例模式？老实说，我在游戏里从未用过四人帮的完整实现。为了确保唯一实例化，我通常直接用静态类。如果那行不通，我会用一个静态标志在运行时检查类只被构造了一次。

本书中还有其他几章在这里能帮上忙。[子类沙箱](subclass-sandbox.html)模式让类的实例可以访问某些共享状态，而不把它变成全局可用的。[服务定位器](service-locator.html)模式**确实**让一个对象全局可用，但它给你更多关于如何配置那个对象的灵活性。
