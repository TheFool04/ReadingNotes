# 对象池

**优化模式**

## 意图

*通过从固定池中复用对象，而非逐一分配和释放，来提升性能与内存使用效率。*

## 动机

假设我们正在为游戏制作视觉特效。当英雄施放法术时，我们希望屏幕上绽放出一片闪耀的粒子光芒。这需要一套*粒子系统*——一个负责生成闪光粒子图形、并为其播放动画直至消亡的引擎。

挥动一次魔杖就可能催生数百个粒子，所以系统必须能够极快地创建它们。更重要的是，我们需要确保这些粒子的创建与销毁不会引发*内存碎片化*。

### 碎片化的诅咒

为游戏主机或移动设备编程，在许多方面比传统 PC 编程更接近嵌入式编程。内存十分稀缺，用户期望游戏坚如磐石，而高效的紧凑型内存管理器几乎无处可寻。在这样的环境中，内存碎片化是致命的。

碎片化意味着堆上的空闲空间被<span name="park">切割</span>成若干小块，而非一整片连续的开放区域。*总体*可用内存或许很充裕，但最大的*连续*区域可能小得令人绝望。假设我们有 14 字节空闲，但它被分成两块各 7 字节的碎片，中间夹着一段已占用的内存。若此时我们想分配一个 12 字节的对象，就会失败。屏幕上的粒子效果就这么泡汤了。

> **注：** 就像在繁忙街道上找车位平行停车，而已停的车彼此拉开了太大的间距。要是它们能靠拢一点，就有地方停了——但空闲空间被*碎片化*成了七八辆车之间的零散路边空当。

*（图示：一系列内存操作导致碎片化，最终即便理论上有足够内存，分配请求也告失败。）*

即便碎片化并不频繁，它也会<span name="soak">逐渐</span>将堆蚕食成一块坑坑洼洼、漏洞百出的海绵，最终把游戏彻底拖垮。

> **注：** 大多数主机厂商要求游戏通过"浸泡测试"——在演示模式下连续运行数日。若游戏崩溃，则不允许发售。浸泡测试失败，有时是因为偶发的 bug，但更常见的元凶是悄然蔓延的碎片化或内存泄漏。

### 鱼与熊掌兼得

由于碎片化问题，以及分配操作本身可能很慢，游戏在管理内存时极为谨慎。一个简单的解决方案往往最为有效——游戏启动时申请一大块内存，直到游戏结束才释放。但对于需要在运行时动态创建和销毁对象的系统而言，这就很棘手了。

对象池让我们两全其美。对内存管理器而言，我们只是预先分配了一大块内存，游戏期间从不释放。对池的使用者而言，我们可以随心所欲地分配和回收对象。

## 模式描述

定义一个**池**类，维护一组**可复用对象**的集合。每个对象支持**"是否在用"查询**，以标明自身当前是否"存活"。池初始化时，预先创建整组对象（通常以单次连续分配的方式），并将它们全部初始化为"未在用"状态。

需要新对象时，向池申请。池找到一个可用对象，将其初始化为"在用"状态并返回。对象不再需要时，将其重置为"未在用"状态。如此一来，对象的创建与销毁可以自由进行，无需分配内存或其他资源。

## 使用场景

这一模式在游戏中被广泛使用，既用于游戏实体和视觉特效等显而易见的对象，也用于当前播放的音效等较为隐蔽的数据结构。在以下情况下使用对象池：

- 你需要频繁地创建和销毁对象。
- 对象大小相近。
- 在堆上分配对象速度较慢，或可能导致内存碎片化。
- 每个对象都封装了某种资源（如数据库连接或网络连接），获取代价高昂，适合复用。

## 注意事项

通常情况下，你会依赖垃圾收集器或 `new`/`delete` 来帮你处理内存管理。使用对象池意味着你在说："我知道该如何更好地处置这些字节。"这意味着你必须亲自应对这一模式的种种局限。

### 池可能在不需要的对象上浪费内存

对象池的大小需要根据游戏需求精心调整。调整时，池太*小*通常显而易见（崩溃是最有力的提示）。但也要注意池不要太*大*——更小的池意味着更多内存可用于其他有趣的事情。

### 同一时间只能有固定数量的对象处于活跃状态

从某种角度看，这是一件好事。将内存划分为针对不同对象类型的独立池，可以确保——例如——一连串爆炸不会让粒子系统耗尽*所有*可用内存，从而导致更关键的对象（如新敌人）无法创建。

然而，这也意味着你必须做好应对准备：当你试图从池中复用一个对象时，可能会因全部对象都在使用中而失败。以下是几种常见的应对策略：

- *从源头杜绝。* 这是最常见的"解决方案"：调整池的大小，使其在任何情况下都不会溢出。对于敌人或游戏道具等重要对象的池，这往往是正确答案。玩家到达关卡末尾时，若找不到空槽来创建大 Boss，可能根本没有"正确的"处理方式——所以明智之举是确保这种情况永远不会发生。

  这样做的代价是，你可能不得不为那些只在极少数边缘情况下才会用到的槽位预留大量内存。因此，单一的固定池大小未必适合所有游戏状态。例如，某些关卡可能大量使用特效，另一些则侧重于音效。在这种情况下，可以考虑针对不同场景使用不同的池大小。

- *直接不创建该对象。* 听起来很粗暴，但对于粒子系统这类情形却很合理。如果所有粒子都在使用中，屏幕上很可能已经闪烁着满眼特效。用户不会注意到下一次爆炸比正在进行的那些稍逊一筹。

- *强制销毁一个现有对象。* 设想一个正在播放的音效池，假设你想播放一个新音效，但池已满。你*不能*简单地忽略这个新音效——如果魔杖的挥动声有时戏剧性地响起，有时却顽固地沉默，用户一定会察觉。更好的做法是找出当前正在播放的最安静的音效，用新音效替换它。新音效将掩盖旧音效被截断的痕迹。

  一般而言，如果现有对象的*消失*比新对象的*缺席*更不引人注意，这可能就是正确的选择。

- *动态扩容。* 如果游戏允许在内存方面灵活一些，你或许可以在运行时扩大池的容量，或者创建一个溢出备用池。如果你通过上述方式申请了更多内存，请考虑在额外容量不再需要时，是否应将池收缩回原来的大小。

### 每个对象的内存大小固定

大多数池实现将对象存储在一个就地对象数组中。如果所有对象都是同一类型，这完全没问题。但如果你想在池中存储不同类型的对象，或者可能添加字段的子类实例，就需要确保池中的每个槽位都有足够的内存来容纳*最大*的那个对象。否则，一个超出预期的大对象会踩踏相邻对象，破坏内存。

与此同时，当对象大小参差不齐时，内存会被白白浪费。每个槽位都要足够大，以容纳最大的对象。如果这样大小的对象出现频率很低，那每次放入一个较小的对象时，你都在浪费内存。就像过机场安检，却用巨大的行李托盘来放你的钥匙和钱包。

如果你发现内存以这种方式大量流失，可以考虑将池拆分成针对不同对象大小的<span name="pools">独立</span>池——大托盘放行李，小托盘放零碎物品。

> **注：** 这是实现高速内存管理器的常见模式。管理器维护若干不同块大小的池。当你请求分配一块内存时，它在合适大小的池中找到一个开放槽位并从中分配。

### 被复用的对象不会自动清零

大多数内存管理器都有一个调试功能：将新分配或刚释放的内存清填为某个明显的魔法值，如 `0xdeadbeef`。这有助于发现因变量未初始化或在释放后继续使用内存而引发的棘手 bug。

由于对象池在复用对象时不再经过内存管理器，这道安全网就消失了。更糟糕的是，"新"对象所使用的内存，之前存放着一个完全相同类型的对象。这让你几乎无法判断在创建新对象时是否忘记了初始化某些东西：对象所在内存中可能已经存有它"前世"留下的、几乎正确的数据。

因此，务必格外注意：负责初始化池中新对象的代码要*完整地*初始化该对象。甚至值得花一点时间，添加一个调试功能，在对象被回收时<span name="clear">清零</span>其槽位内存。

> **注：** 如蒙不弃，欢迎将其清零为 `0x1deadb0b`。

### 未使用的对象将长期驻留内存

在支持垃圾收集的系统中，对象池并不那么常见，因为内存管理器通常会替你处理碎片化问题。但池在这些环境中仍有用武之地——它可以避免分配和释放的开销，尤其是在 CPU 较慢、垃圾收集器较简单的移动设备上。

如果你在垃圾收集环境中使用对象池，要警惕一个潜在的冲突。由于池在对象不再使用时并不真正释放它们，这些对象会一直留在内存中。若它们持有对*其他*对象的引用，垃圾收集器就无法回收那些对象。为避免这一问题，当池中的对象不再使用时，清除它持有的所有对其他对象的引用。

## 示例代码

现实中的粒子系统往往会处理重力、风力、摩擦力等物理效果。我们这个简化版本只会让粒子沿直线运动若干帧，然后令其消亡。虽然算不上什么大制作，但足以说明对象池的用法。

我们从最简单的实现开始。首先是粒子类：

```cpp
class Particle
{
public:
  Particle()
  : framesLeft_(0)
  {}

  void init(double x, double y,
            double xVel, double yVel, int lifetime)
  {
    x_ = x; y_ = y;
    xVel_ = xVel; yVel_ = yVel;
    framesLeft_ = lifetime;
  }

  void animate()
  {
    if (!inUse()) return;

    framesLeft_--;
    x_ += xVel_;
    y_ += yVel_;
  }

  bool inUse() const { return framesLeft_ > 0; }

private:
  int framesLeft_;
  double x_, y_;
  double xVel_, yVel_;
};
```

默认构造函数将粒子初始化为"未在用"状态。之后调用 `init()` 将其初始化为存活状态。粒子通过名副其实的 `animate()` 函数随时间播放动画，每帧调用一次。

池需要知道哪些粒子可供复用，这通过粒子的 `inUse()` 函数来判断。该函数利用粒子寿命有限的特点，通过 `framesLeft_` 变量来判断粒子是否在使用中，无需额外存储标志位。

池类同样简洁：

```cpp
class ParticlePool
{
public:
  void create(double x, double y,
              double xVel, double yVel, int lifetime);

  void animate()
  {
    for (int i = 0; i < POOL_SIZE; i++)
    {
      particles_[i].animate();
    }
  }

private:
  static const int POOL_SIZE = 100;
  Particle particles_[POOL_SIZE];
};
```

`create()` 函数供外部代码创建新粒子。游戏每帧调用一次<span name="update">`animate()`</span>，后者再依次驱动池中每个粒子的动画。

> **注：** 这个 `animate()` 方法是[更新方法](18-update-method.md)模式的一个例子。

粒子本身以固定大小数组的形式存储在类中。在这个示例实现里，池大小直接硬编码在类声明中，但也可以通过使用给定大小的动态数组，或使用值类型的模板参数，从外部指定。

创建新粒子非常直接：

```cpp
void ParticlePool::create(double x, double y,
                          double xVel, double yVel,
                          int lifetime)
{
  // Find an available particle.
  for (int i = 0; i < POOL_SIZE; i++)
  {
    if (!particles_[i].inUse())
    {
      particles_[i].init(x, y, xVel, yVel, lifetime);
      return;
    }
  }
}
```

我们遍历池，找到第一个可用的粒子，初始化并返回。注意，在这个实现里，如果没有可用粒子，我们就简单地不创建新粒子。

除了渲染粒子之外，一个简单的粒子系统就这些了。我们现在可以创建池并使用它来生成粒子，粒子会在寿命耗尽后自动停用。

这足以发布一款游戏，但眼尖的读者可能已经注意到：创建新粒子需要<span name="create">遍历</span>（可能是）整个集合，直到找到一个空槽。如果池非常大且几乎满员，这会变得很慢。让我们看看如何改进。

> **注：** 创建粒子的时间复杂度为 *O(n)*，对于还记得算法课的人来说。

### 空闲链表

如果不想浪费时间*寻找*空闲粒子，显而易见的答案是不要失去对它们的追踪。我们可以维护一个单独的指针列表，指向每个未使用的粒子。这样，需要创建粒子时，只需从列表头部取出第一个指针，复用它所指向的粒子即可。

遗憾的是，这需要我们维护一个额外的完整数组，其指针数量与池中对象数量相同。毕竟，当池刚创建时，*所有*粒子都是未使用的，列表初始时需要指向池中的每一个对象。

如果能在*不牺牲任何内存*的前提下解决性能问题，那就再好不过了。恰好，有一些内存已经在那里闲置，随时可以借用——那就是未使用粒子自身的数据。

当一个粒子未在使用时，它的大部分状态都是无关紧要的：位置和速度都没在使用。它唯一需要的状态是用于判断自身是否已死亡的信息。在我们的例子中，这就是 `framesLeft_` 成员。其他所有字节都可以被复用。下面是改版后的粒子：

```cpp
class Particle
{
public:
  // ...

  Particle* getNext() const { return state_.next; }
  void setNext(Particle* next) { state_.next = next; }

private:
  int framesLeft_;

  union
  {
    // State when it's in use.
    struct
    {
      double x, y;
      double xVel, yVel;
    } live;

    // State when it's available.
    Particle* next;
  } state_;
};
```

我们将除 `framesLeft_` 之外的所有成员变量移入 `state_` <span name="union">联合体</span>内的 `live` 结构体中。这个结构体在粒子播放动画时持有其状态。当粒子未被使用时，联合体的另一个分支——`next` 成员——被启用，它持有一个指向下一个可用粒子的指针。

> **注：** 联合体如今似乎已不常用，语法对你来说可能有些陌生。如果你在游戏团队工作，队里可能有一位"内存大师"——那位总在游戏不可避免地超出内存预算时被拉来救场的苦命同事。去问问他们关于联合体的事，他们对联合体以及其他各种位打包技巧如数家珍。

我们可以利用这些指针构建一条链表，将池中所有未使用的粒子串联起来。我们拥有了所需的可用粒子列表，却不需要任何额外内存——而是寄生于死亡粒子自身的内存之中。

这一巧妙技术被称为[*空闲链表*](http://en.wikipedia.org/wiki/Free_list)（free list）。要让它正常工作，我们需要确保指针在初始化时正确设置，并在粒子创建和销毁时得到维护。当然，我们还需要追踪链表的头节点：

```cpp
class ParticlePool
{
  // ...
private:
  Particle* firstAvailable_;
};
```

当池刚创建时，*所有*粒子都是可用的，所以空闲链表应穿过整个池。池的构造函数完成这一初始化：

```cpp
ParticlePool::ParticlePool()
{
  // The first one is available.
  firstAvailable_ = &particles_[0];

  // Each particle points to the next.
  for (int i = 0; i < POOL_SIZE - 1; i++)
  {
    particles_[i].setNext(&particles_[i + 1]);
  }

  // The last one terminates the list.
  particles_[POOL_SIZE - 1].setNext(NULL);
}
```

现在创建一个新粒子，我们直接跳转到<span name="first">第一个</span>可用粒子：

> **注：** *O(1)* 的时间复杂度！现在才叫飞速！

```cpp
void ParticlePool::create(double x, double y,
                          double xVel, double yVel,
                          int lifetime)
{
  // Make sure the pool isn't full.
  assert(firstAvailable_ != NULL);

  // Remove it from the available list.
  Particle* newParticle = firstAvailable_;
  firstAvailable_ = newParticle->getNext();

  newParticle->init(x, y, xVel, yVel, lifetime);
}
```

我们需要知道粒子何时死亡，以便将其重新加入空闲链表，因此修改 `animate()` 使其在存活粒子在该帧消亡时返回 `true`：

```cpp
bool Particle::animate()
{
  if (!inUse()) return false;

  framesLeft_--;
  x_ += xVel_;
  y_ += yVel_;

  return framesLeft_ == 0;
}
```

发生这种情况时，我们只需将其重新穿回链表：

```cpp
void ParticlePool::animate()
{
  for (int i = 0; i < POOL_SIZE; i++)
  {
    if (particles_[i].animate())
    {
      // Add this particle to the front of the list.
      particles_[i].setNext(firstAvailable_);
      firstAvailable_ = &particles_[i];
    }
  }
}
```

就这样，一个创建和删除均为常数时间复杂度的精巧对象池。

## 设计决策

如你所见，最简单的对象池实现几乎微不足道：创建一个对象数组，按需重新初始化它们。生产环境的代码很少如此精简。有几种方式可以扩展这一模式，使池更通用、更安全或更易于维护。在游戏中实现对象池时，你需要回答以下几个问题：

### 对象与池是否耦合？

编写对象池时，你首先遇到的问题是：对象自身是否知道它身处池中？大多数情况下是知道的，但当你编写一个可以容纳任意类型对象的通用池类时，就不一定能做到这一点了。

**如果对象与池耦合：**

- *实现更简单。* 你只需在池化对象中放置一个"是否在用"标志或函数即可。

- *可以确保对象只能由池来创建。* 在 C++ 中，一个简单的做法是让池类成为对象类的友元（`friend`），然后将对象的构造函数声明为私有：

  ```cpp
  class Particle
  {
    friend class ParticlePool;

  private:
    Particle()
    : inUse_(false)
    {}

    bool inUse_;
  };

  class ParticlePool
  {
    Particle pool_[100];
  };
  ```

  这种关系清楚地记录了该类的预期使用方式，并确保用户不会创建未被池追踪的对象。

- *可以避免显式存储"是否在用"标志。* 许多对象已经保有某些状态，可以用来判断其是否存活。例如，粒子的当前位置若已离开屏幕范围，则可视为可复用。如果对象类知道自己可能被用于池中，它可以提供一个 `inUse()` 方法来查询这一状态，从而省去池为每个对象额外存储一个"是否在用"标志所耗费的内存。

**如果对象与池不耦合：**

- *任意类型的对象都可以被池化。* 这是最大的优势。通过将对象与池解耦，你有机会实现一个通用的可复用池类。

- *"是否在用"的状态必须在对象外部追踪。* 最简单的方法是创建一个单独的位域：

  ```cpp
  template <class TObject>
  class GenericPool
  {
  private:
    static const int POOL_SIZE = 100;

    TObject pool_[POOL_SIZE];
    bool    inUse_[POOL_SIZE];
  };
  ```

### 由谁负责初始化被复用的对象？

要复用一个现有对象，必须以新状态对其重新初始化。这里的关键问题是：初始化是在池类内部进行，还是在外部进行？

**如果池在内部完成初始化：**

- *池可以完全封装其对象。* 根据对象需要具备的其他能力，你也许可以将它们完全置于池的内部。这能确保其他代码不会持有对可能被意外复用的对象的引用。

- *池与对象的初始化方式紧密绑定。* 池化对象可能提供多个不同的初始化函数。如果由池来管理初始化，其接口就需要支持所有这些方式，并将调用转发给对象：

  ```cpp
  class Particle
  {
    // Multiple ways to initialize.
    void init(double x, double y);
    void init(double x, double y, double angle);
    void init(double x, double y, double xVel, double yVel);
  };

  class ParticlePool
  {
  public:
    void create(double x, double y)
    {
      // Forward to Particle...
    }

    void create(double x, double y, double angle)
    {
      // Forward to Particle...
    }

    void create(double x, double y, double xVel, double yVel)
    {
      // Forward to Particle...
    }
  };
  ```

**如果由外部代码完成初始化：**

- *池的接口可以更简洁。* 池无需为对象每一种初始化方式提供对应函数，而是简单地返回一个指向新对象的引用：

  ```cpp
  class Particle
  {
  public:
    // Multiple ways to initialize.
    void init(double x, double y);
    void init(double x, double y, double angle);
    void init(double x, double y, double xVel, double yVel);
  };

  class ParticlePool
  {
  public:
    Particle* create()
    {
      // Return reference to available particle...
    }
  private:
    Particle pool_[100];
  };
  ```

  调用方随后可以调用对象暴露的任意方法来完成初始化：

  ```cpp
  ParticlePool pool;

  pool.create()->init(1, 2);
  pool.create()->init(1, 2, 0.3);
  pool.create()->init(1, 2, 3.3, 4.4);
  ```

- *外部代码可能需要处理创建新对象失败的情况。* 上面的示例假设 `create()` 始终能成功返回一个对象指针。但如果池已满，它可能返回 `NULL`。为了安全起见，在初始化对象之前需要先做检查：

  ```cpp
  Particle* particle = pool.create();
  if (particle != NULL) particle->init(1, 2);
  ```

## 参见

- 这与[享元](06-flyweight.md)模式颇为相似。两者都维护一组可复用对象的集合，区别在于"复用"的含义。享元对象通过让多个所有者*同时*共享同一实例来实现复用。享元模式通过在多个上下文中使用同一对象来避免*重复的*内存占用。

  对象池中的对象同样被复用，但只是随时间推移的复用。在对象池的语境中，"复用"意味着在原所有者用完对象*之后*，回收其内存。对象池并不期望一个对象在其生命周期内被共享。

- 将大量同类型对象紧凑地存放在内存中，有助于在游戏遍历这些对象时保持 CPU 缓存的充盈。[数据局部性](24-data-locality.md)模式正是围绕这一点展开的。
