# 数据局部性

**所属章节：优化模式**

## 意图

*通过合理排列数据来利用 CPU 缓存，从而加速内存访问。*

## 动机

我们一直被骗。他们不断给我们看 CPU 速度逐年攀升的图表，仿佛摩尔定律不只是一条历史规律，而是某种神圣的权利。不用动一根手指，我们这些软件人就能看着程序仅凭新硬件就神奇地加速运行。

芯片确实在变得越来越快（尽管就连这一点现在也趋于平缓），但硬件工程师们没提到一件事：没错，我们*处理*数据的速度比以往任何时候都快，但*获取*数据的速度却没有跟上。

<span name="legend"></span>

*（图示：1980 年至 2010 年处理器与 RAM 速度对比图。处理器速度快速攀升，而 RAM 速度远远落后。）*

> **注：** 该图以 1980 年各自的速度为基准，展示了处理器与 RAM 的相对速度。如你所见，CPU 突飞猛进，而 RAM 访问速度却严重滞后。此数据来自 John L. Hennessy、David A. Patterson、Andrea C. Arpaci-Dusseau 所著《计算机体系结构：量化研究方法》，经由 Tony Albrecht 的"[面向对象编程的陷阱][poop]"引用。

[poop]: http://seven-degrees-of-freedom.blogspot.com/2009/12/pitfalls-of-object-oriented-programming.html

为了让超高速 CPU 轰出大量计算，它实际上必须把数据从主内存搬到寄存器中。如你所见，RAM 的速度远远没能跟上 CPU 速度的提升，差得很远。

在当今的硬件上，从<span name="ram">RAM</span> 取一个字节的数据可能需要*数百个*时钟周期。如果大多数指令都需要数据，而获取数据又需要数百个周期，我们的 CPU 怎么可能不是 99% 的时间都在等数据？

> **注：** 之所以叫"随机存取存储器"，是因为与磁盘驱动器不同，你理论上可以以相同的速度访问其中任意一处数据——不必像磁盘那样担心连续读取的问题。或者说，至少*以前*是这样。正如我们将看到的，RAM 已经不再那么"随机存取"了。

事实上，如今 CPU 确实有令人震惊的大量时间在等待内存，但情况没有想象中那么糟。为了解释这是为什么，让我们踏上一段过度冗长的比喻之旅……

### 一座数据仓库

想象你是一位小办公室里的会计。你的工作是申请一箱文件，然后对它们做一些<span name="accountant">会计</span>操作——把一堆数字加起来之类的。你必须按照某种只有其他会计才能理解的神秘逻辑，处理特定标签的箱子。

> **注：** 我大概不应该在这个比喻里用一份我完全不了解的职业。

凭借努力、天赋和一些提神手段，你能在大约一分钟内处理完一整箱文件。但有个小问题：所有这些箱子都存放在另一栋楼的仓库里。要取一个箱子，你必须请仓库管理员给你送来。他去开叉车，在货架间转悠，直到找到你要的箱子。

说真的，这要花他整整一天。和你不同，他近期不会评上月度优秀员工。这意味着无论你多快，每天只能处理一箱文件。其余时间，你只能坐在那里反思是什么人生决策把你带进了这份令人窒息的工作。

某天，一群工业设计师来了，他们的工作是提高运营效率——比如让流水线运转更快。观察你工作几天后，他们注意到了几件事：

- 很多时候，处理完一箱文件后，你下一箱要的文件就在仓库里同一个货架上的<span name="next">旁边</span>。
- 用叉车运单箱文件实在太蠢了。
- 你办公室角落里其实有一点空余空间。

> **注：** 使用刚刚用过的东西附近的东西，专业术语叫*参考局部性（locality of reference）*。

他们想出了一个聪明的解决方案。每当你向仓库管理员申请一个箱子时，他会取来整整一托盘。他拿到你要的那箱，再拿上旁边的一些——他不知道你是否需要那些（凭他的工作态度，显然也不在乎），只是尽可能多地往托盘上装。

他把整托盘运来送给你。不管工作场所安全规范，他开着叉车直接进来，把托盘放到你办公室角落里。

现在，当你需要一个新箱子时，你首先查看它是否已经在办公室的托盘上。如果在，太好了！只需一秒就能取来，继续处理数字。如果一个托盘能放五十箱，而你运气好，需要的*所有*箱子恰好都在上面，你的工作效率就能提升五十倍。

但如果你需要的箱子*不在*托盘上，就回到了起点。由于办公室只能放一个托盘，仓库管理员得把那个托盘运回去，再给你运来一个新的。

### CPU 的"托盘"

说来也奇怪，这与现代计算机的 CPU 工作方式颇为相似。你扮演的是 CPU，你的桌子是 CPU 的寄存器，文件箱是能装进寄存器的数据，仓库是机器的 RAM，那个烦人的仓库管理员是从主内存向寄存器传输数据的总线。

如果我是三十年前写这一章，比喻到这里就结束了。但随着芯片越来越快而 RAM 却……*没有*，硬件工程师开始寻找解决方案，他们想出的就是*CPU 缓存*。

现代计算机在芯片内部有<span name="caches">一小块内存</span>，CPU 从这里读取数据要比从主内存快得多。它很小，因为必须塞进芯片，而且它所用的更快类型的内存（静态随机存取存储器，SRAM）价格昂贵得多。

> **注：** 现代硬件有多级缓存，这就是你听到"L1"、"L2"、"L3"等说法的由来。每一级都比上一级更大但更慢。本章我们不深入探讨内存实际上是一个[层级结构](http://en.wikipedia.org/wiki/Memory_hierarchy)，但这是值得知道的事情。

这一小块内存叫做*缓存*（具体来说，芯片上的那块是*L1 缓存*），在我的繁复比喻里，它扮演的角色是那托盘箱子。每当芯片需要 RAM 中的一字节数据时，它会自动抓取一整块连续内存——通常约 64 到 128 字节——放进缓存。这一块内存叫做*缓存行（cache line）*。

*（图示：一条缓存行，显示了所请求的那一字节以及被一并加载到缓存中的相邻字节。）*

如果你<span name="pallet">接下来需要</span>的数据字节恰好在这块内存中，CPU 就直接从缓存中读取，比访问 RAM *快得多*。在缓存中成功找到所需数据叫做*缓存命中（cache hit）*；如果找不到，必须去主内存取，就叫*缓存缺失（cache miss）*。

> **注：** 在比喻中，我至少忽略了一个细节：你的办公室只能放一个托盘，即一条缓存行。而真实的缓存包含多条缓存行。其工作细节超出本章范围，但你可以搜索"缓存关联性（cache associativity）"来满足求知欲。

当缓存缺失发生时，CPU 会*停顿*——它无法处理下一条指令，因为需要的数据还没到。它就那么干等着，无聊地熬过数百个时钟周期，直到数据取回。我们的任务就是避免这种情况。

想象你正在优化某段游戏中的性能敏感代码，它看起来是这样：

```cpp
for (int i = 0; i < NUM_THINGS; i++)
{
  sleepFor500Cycles();
  things[i].doStuff();
}
```

你会做的第一个改动是什么？对，把那个毫无意义、代价高昂的函数调用去掉。这个调用的性能代价等同于一次缓存缺失。每次你跳到主内存，就好像在代码里插入了一段延迟。

### 等等，数据决定性能？

开始写这一章时，我花时间写了几个类游戏的小程序，用来触发最佳和最差情况的缓存使用。我想要能蹂躏缓存的基准测试，以便亲眼看到这会造成多大的"流血事件"。

当我让这些程序跑起来时，我惊呆了。我知道这是大问题，但亲眼目睹带来的冲击是不可比拟的。<span name="ymmv">我写了两个程序</span>，做的是*完全相同*的计算，唯一的区别是它们触发缓存缺失的次数不同。慢的那个比快的*慢五十倍*。

> **注：** 这里有很多注意事项。特别是，不同计算机的缓存配置不同，我的机器可能与你的不同，而专用游戏主机与 PC 差异很大，PC 又与移动设备差异很大。你的实际效果可能有所不同。

这让我大开眼界。我以前习惯于把性能视为*代码*的属性，而不是*数据*的属性。一个字节无所谓快慢，它只是静静地放在那里。但由于缓存的存在，*你组织数据的方式直接影响性能*。

现在的挑战是把这些内容压缩成本章能容纳的篇幅。针对缓存使用的优化是一个庞大的话题，我甚至还没涉及*指令缓存*——记住，代码也在内存中，必须先被加载到 CPU 才能执行。比我更精通此道的人完全可以写一整<span name="book">本书</span>来讲这个。

> **注：** 事实上，确实有人写了：Richard Fabian 所著的[《面向数据的设计》](http://www.dataorienteddesign.com/dodmain/)。

不过，既然你现在正在读*这本*书，我有一些基本技术可以让你入门，开始思考数据结构如何影响性能。

一切归结为一件很简单的事：每当芯片读取某些内存时，它会取来整条缓存行。你能利用该<span name="line">缓存行中的内容越多，速度就越快</span>。所以目标就是：*组织你的数据结构，让你正在处理的东西在内存中彼此相邻*。

> **注：** 这里有一个关键假设：单线程。如果你在多个线程上修改相邻的数据，反而希望它们位于*不同*的缓存行。如果两个线程同时修改同一条缓存行上的数据，两个核心都必须进行昂贵的缓存同步。

换句话说，如果你的代码依次处理 `Thing`、`Another`、`Also`，你希望它们在内存中这样排列：

*（图示：Thing、Another、Also 在内存中依次紧挨着排列。）*

注意，这些不是*指向* `Thing`、`Another`、`Also` 的指针，而是它们的实际数据，原地，一个接一个排列。CPU 读入 `Thing` 时，就会开始把 `Another` 和 `Also` 也带进来（取决于它们的大小和缓存行的大小）。等你开始处理它们时，它们已经在缓存中了。芯片高兴，你也高兴。

## 模式结构

现代 CPU 拥有**缓存来加速内存访问**，这些缓存访问**紧邻近期已访问内存的数据要快得多**。利用这一点来提升性能：**增加数据局部性**——按你处理它的顺序，将数据保存在**连续的内存中**。

## 使用时机

与大多数优化一样，使用数据局部性模式的第一条准则是：*当你有性能问题时*。不要把时间浪费在代码库中那些很少执行的角落上。优化不需要优化的代码只会让你的生活更难，因为结果几乎总是更复杂、更不灵活。

对于这个模式，你还需要确认性能问题*确实由缓存缺失引起*。如果代码慢是出于其他原因，这招不会有帮助。

粗略的性能分析方法是手动在代码的两个点之间加一点计时器，最好使用高精度计时器。要捕捉糟糕的缓存使用，你需要更精密的工具——需要查看实际发生了多少缓存缺失，以及发生在哪里。

幸运的是，有<span name="cachegrind">性能分析工具</span>可以报告这些信息。在对数据结构大动手术之前，值得花时间把其中一个工具用起来，并确保你理解它抛出的那些（出奇复杂的）数字。

> **注：** 遗憾的是，大多数此类工具并不便宜。如果你在主机开发团队，大概已经有授权了。如果没有，一个出色的免费选项是 [Cachegrind](http://valgrind.org/docs/manual/cg-manual.html)（一款基于 Valgrind 的缓存分析工具）。它在模拟的 CPU 和缓存层级之上运行你的程序，然后报告所有的缓存交互情况。

话虽如此，缓存缺失*确实会*影响游戏性能。虽然不应该花大量时间提前优化缓存使用，但在整个设计过程中，确实要思考你的数据结构有多"缓存友好"。

## 注意事项

软件架构的一大特点是*抽象*。本书的大量篇幅都在讲解将代码块彼此解耦的模式，以便更容易修改。在面向对象语言中，这几乎总意味着接口。

在 C++ 中，使用接口意味着通过<span name="virtual">指针或引用</span>访问对象。但经由指针意味着在内存中跳来跳去，这正是导致缓存缺失的原因——而本模式就是要避免这种情况。

> **注：** 接口的另一面是*虚方法调用*。这要求 CPU 查找对象的虚函数表（vtable），然后找到指向实际方法的指针。所以，你又在追踪指针，这可能导致缓存缺失。

为了遵从这个模式，你将不得不牺牲一些宝贵的抽象。你的程序越是围绕数据局部性来设计，就越需要放弃继承、接口以及这些工具所提供的好处。这里没有银弹，只有充满挑战的权衡取舍。这正是它的乐趣所在！

## 示例代码

如果你真的钻进优化数据局部性的"兔子洞"，会发现无数种方式将数据结构切分成 CPU 最容易消化的形式。为了带你入门，我将为几种最常见的数据组织方式各举一例。我们会在游戏引擎某个具体部分的背景下介绍它们，但（与其他模式一样）请记住，这种通用技术可以在任何适用的地方使用。

### 连续数组

让我们从一个处理大量游戏实体的[游戏循环](13-game-loop.md)开始。这些实体使用[组件模式](20-component.md)被分解为不同的领域——AI、物理和渲染。下面是 `GameEntity` 类：

```cpp
class GameEntity
{
public:
  GameEntity(AIComponent* ai,
             PhysicsComponent* physics,
             RenderComponent* render)
  : ai_(ai), physics_(physics), render_(render)
  {}

  AIComponent* ai() { return ai_; }
  PhysicsComponent* physics() { return physics_; }
  RenderComponent* render() { return render_; }

private:
  AIComponent* ai_;
  PhysicsComponent* physics_;
  RenderComponent* render_;
};
```

每个组件都有少量状态（也许只是几个向量或一个矩阵），以及一个用于<span name="update">更新</span>它的方法。细节并不重要，但大致想象是这样的：

> **注：** 顾名思义，这些是[更新方法](14-update-method.md)模式的示例，就连 `render()` 也是，只是换了个名字。

```cpp
class AIComponent
{
public:
  void update() { /* Work with and modify state... */ }

private:
  // Goals, mood, etc. ...
};

class PhysicsComponent
{
public:
  void update() { /* Work with and modify state... */ }

private:
  // Rigid body, velocity, mass, etc. ...
};

class RenderComponent
{
public:
  void render() { /* Work with and modify state... */ }

private:
  // Mesh, textures, shaders, etc. ...
};
```

游戏维护着一个包含世界中所有实体指针的大数组。每转一圈游戏循环，我们需要依次执行：

1. 更新所有实体的 AI 组件；
2. 更新它们的物理组件；
3. 用渲染组件绘制它们。

许多游戏引擎是这样实现的：

```cpp
while (!gameOver)
{
  // Process AI.
  for (int i = 0; i < numEntities; i++)
  {
    entities[i]->ai()->update();
  }

  // Update physics.
  for (int i = 0; i < numEntities; i++)
  {
    entities[i]->physics()->update();
  }

  // Draw to screen.
  for (int i = 0; i < numEntities; i++)
  {
    entities[i]->render()->render();
  }

  // Other game loop machinery for timing...
}
```

在还没听说过 CPU 缓存之前，这段代码看起来完全无害。但现在你应该已经察觉到有些不对劲了。这段代码不只是在蹂躏缓存，而是把缓存拖到后面一顿毒打。看它在做什么：

1. 游戏实体数组存储的是指向实体的*指针*，所以对数组中的每个元素，我们都要追踪那个指针——一次缓存缺失；
2. 然后，游戏实体里有个指向组件的指针——又一次缓存缺失；
3. 然后我们更新组件；
4. 然后对*游戏中每个实体的每个组件*回到第 1 步。

可怕的是，我们完全不知道这些对象在内存中是怎么排布的，完全受制于内存管理器。随着实体不断分配和释放，堆可能会变得越来越随机地四散分布。

<span name="lines"></span>

*（图示：对象随机分散在内存中，指针把它们全部串联起来的一团乱麻。）*

> **注：** 每一帧，游戏循环都要沿着所有那些箭头前进，才能到达它关心的数据。

如果我们的目标是像某个"四天游览256MB内存！"的廉价旅游套餐一样在游戏的地址空间里兜风，这倒是绝妙的选择。但我们的目标是让游戏快速运行，而在主内存里<span name="chase">漫游</span>绝不是正确的方法。还记得那个 `sleepFor500Cycles()` 函数吗？这段代码实际上是在*一直*调用它。

> **注：** 浪费大量时间追踪指针的行为叫做"指针追踪（pointer chasing）"，事实证明这一点都不像听起来那么好玩。

让我们做点更好的。首先观察到：我们追踪游戏实体指针的唯一原因是为了立即再追踪*另一个*指针来获取组件。`GameEntity` 本身没有有趣的状态，也没有有用的方法。*组件*才是游戏循环真正关心的东西。

与其把游戏实体和组件像繁星般撒落在地址空间的茫茫黑暗中，不如回归大地。我们为每种类型的组件建一个大数组：一个存放 AI 组件的扁平数组、一个存放物理组件的、一个存放渲染组件的。

像这样：

<span name="long-name"></span>

```cpp
AIComponent* aiComponents =
    new AIComponent[MAX_ENTITIES];
PhysicsComponent* physicsComponents =
    new PhysicsComponent[MAX_ENTITIES];
RenderComponent* renderComponents =
    new RenderComponent[MAX_ENTITIES];
```

> **注：** 我最不喜欢使用组件的一点是"component"（组件）这个词太长了。

我要强调，这些是*组件*的数组，而不是*组件指针*的数组。数据全都紧密地排列在一起，一个字节接一个字节。游戏循环就可以直接遍历它们：

<span name="arrow"></span>

```cpp
while (!gameOver)
{
  // Process AI.
  for (int i = 0; i < numEntities; i++)
  {
    aiComponents[i].update();
  }

  // Update physics.
  for (int i = 0; i < numEntities; i++)
  {
    physicsComponents[i].update();
  }

  // Draw to screen.
  for (int i = 0; i < numEntities; i++)
  {
    renderComponents[i].render();
  }

  // Other game loop machinery for timing...
}
```

> **注：** 新代码中 `->` 操作符少了很多，这是我们做得更好的一个暗示。如果想提升数据局部性，就去找那些可以去掉的间接引用操作符。

我们彻底告别了指针追踪，不再在内存中跳来跳去，而是对三个连续数组做直线式扫描。

*（图示：三种不同组件各自的数组，每个数组将其组件整齐地紧凑排列。）*

这向饥渴的 CPU 送去了源源不断的字节流。在我的测试中，这一改动让更新循环比之前版本*快了五十倍*。

有趣的是，我们并没有因此损失多少封装性。没错，游戏循环直接更新组件而不是通过游戏实体，但它之前也是这样做的，只是为了确保以正确顺序处理。即便如此，每个组件本身仍然封装良好——它拥有自己的数据和方法，我们只是改变了使用它的方式。

这也不意味着我们需要去掉 `GameEntity`，可以保留它及其指向组件的指针，让这些指针指向那些数组中的元素。在代码库中其他需要传递一个概念上的"游戏实体"的地方，这仍然很有用。重要的是，性能关键的游戏循环绕过了它，直接访问数据。

### 紧凑数据

假设我们有一个粒子系统。按照上一节的建议，所有粒子都放在一个漂亮的大型连续数组里。我们再把它包进一个小小的<span name="pool">管理类</span>：

> **注：** `ParticleSystem` 类是为单一类型对象定制构建的[对象池](26-object-pool.md)示例。

```cpp
class Particle
{
public:
  void update() { /* Gravity, etc. ... */ }
  // Position, velocity, etc. ...
};

class ParticleSystem
{
public:
  ParticleSystem()
  : numParticles_(0)
  {}

  void update();
private:
  static const int MAX_PARTICLES = 100000;

  int numParticles_;
  Particle particles_[MAX_PARTICLES];
};
```

系统的基本更新方法长这样：

```cpp
void ParticleSystem::update()
{
  for (int i = 0; i < numParticles_; i++)
  {
    particles_[i].update();
  }
}
```

但事实证明，我们并不需要一直处理*所有*粒子。粒子系统有一个固定大小的对象池，但它们通常不会都在屏幕上闪烁。简单的处理方式是这样的：

```cpp
for (int i = 0; i < numParticles_; i++)
{
  if (particles_[i].isActive())
  {
    particles_[i].update();
  }
}
```

我们给 `Particle` 一个标志来跟踪它是否在使用中。在更新循环中，我们对每个粒子<span name="branch">检查</span>这个标志。这会把标志连同该粒子的其他所有数据一起加载到缓存中。如果粒子*未激活*，我们就跳过它处理下一个——刚才加载进缓存的该粒子其余数据就白费了。

活跃粒子越少，我们在内存中跳过的次数就越多，在真正做有用工作（更新活跃粒子）之间产生的缓存缺失也就越多。如果数组很大且有*大量*非活跃粒子，我们又回到了蹂躏缓存的老路。

把对象放在连续数组里，如果我们实际处理的那些对象在其中并不连续，就没多大用处。如果数组里到处都是要绕过的非活跃对象，我们就回到了原来的问题。

> **注：** 精明的底层程序员会看出这里的另一个问题。对每个粒子做 `if` 检查可能导致*分支预测失败（branch misprediction）*和*流水线停顿（pipeline stall）*。在现代 CPU 中，一条"指令"实际上需要数个时钟周期。为了让 CPU 保持忙碌，指令会被*流水线化（pipelined）*，使后续指令在前一条完成之前就开始处理。为此，CPU 必须猜测接下来要执行哪些指令。在直线型代码中这很容易，但在有控制流的情况下就难了。在执行那个 `if` 的指令时，CPU 是猜粒子是活跃的并开始执行 `update()` 的代码，还是猜它不是？为了回答这个问题，芯片会做*分支预测*——观察你的代码之前走了哪条分支，并猜测下次还会那样。但当循环不断地在活跃和非活跃粒子之间来回切换时，预测就会失败。一旦失败，CPU 就必须丢弃已经开始推测性处理的指令（*流水线刷新*）并重新开始。这对性能的影响因机器而异，这也是你有时会看到开发者在热点代码中避免控制流的原因。

看了这一节的标题，你大概猜到了答案。与其*检查*活跃标志，不如*按照*它来*排序*——把所有活跃粒子保留在列表前端。如果我们知道所有这些粒子都是活跃的，就根本不需要检查标志了。

我们还可以轻松跟踪活跃粒子的数量，这样更新循环就变成了这样的美妙之物：

```cpp
for (int i = 0; i < numActive_; i++)
{
  particles[i].update();
}
```

现在我们没有跳过*任何*数据。每一个被吸进缓存的字节都是某个活跃粒子的一部分，而我们确实需要处理它。

当然，我并不是说你应该每帧对整个粒子集合做快速排序，那会远远抵消所有收益。我们想要的是*保持*数组有序。

假设数组已经有序（一开始所有粒子都非活跃时确实如此），唯一可能让它变*无序*的时候是粒子被激活或停用。我们可以很轻松地处理这两种情况。当一个粒子被激活时，通过与第一个*非活跃*粒子交换来把它移到活跃粒子的末尾：

```cpp
void ParticleSystem::activateParticle(int index)
{
  // Shouldn't already be active!
  assert(index >= numActive_);

  // Swap it with the first inactive particle
  // right after the active ones.
  Particle temp = particles_[numActive_];
  particles_[numActive_] = particles_[index];
  particles_[index] = temp;

  // Now there's one more.
  numActive_++;
}
```

停用一个粒子时，做相反的操作：

```cpp
void ParticleSystem::deactivateParticle(int index)
{
  // Shouldn't already be inactive!
  assert(index < numActive_);

  // There's one fewer.
  numActive_--;

  // Swap it with the last active particle
  // right before the inactive ones.
  Particle temp = particles_[numActive_];
  particles_[numActive_] = particles_[index];
  particles_[index] = temp;
}
```

许多程序员（包括我自己）对在内存中移动数据有过敏反应。搬运一堆字节感觉比赋值一个指针*沉重*得多。但当你把*追踪*那个指针的代价算进来，有时会发现直觉是错的。在<span name="profile">某些情况</span>下，如果在内存中移动数据能帮你保持缓存充满，这样做反而更便宜。

> **注：** 这是在做这类决定时请你*性能分析*的友情提醒。

保持粒子按活跃状态*排序*还有一个妙处——我们根本不需要在每个粒子中存储活跃标志了。它可以通过粒子在数组中的位置和 `numActive_` 计数器来推断。这让粒子对象更小，意味着我们可以在缓存行中塞进更多粒子，速度也就更快了。

当然，也不是没有代价。从 API 可以看出，我们在这里损失了一些面向对象的特性。`Particle` 类不再控制自身的活跃状态——你无法对它调用某个 `activate()` 方法，因为它不知道自己的索引。相反，任何想要激活粒子的代码都需要访问粒子*系统*。

在这种情况下，我可以接受 `ParticleSystem` 和 `Particle` 如此紧密的关联。我把它们视为分布在两个物理*类*上的单一*概念*——这只是意味着接受这样一个想法：粒子只在某个粒子系统的上下文中才有意义。而且，在这种情况下，很可能正是粒子系统在生成和销毁粒子。

### 冷热数据分离

好了，这是让缓存更开心的最后一个简单技术示例。假设我们有一个游戏实体的 AI 组件，它包含一些状态——当前播放的动画、正在前往的目标位置、能量值等——这些是它每帧都要检查和调整的东西，大致如下：

```cpp
class AIComponent
{
public:
  void update() { /* ... */ }

private:
  Animation* animation_;
  double energy_;
  Vector goalPos_;
};
```

但它还为较少发生的情况存储了一些状态。它存储了一些数据，描述当它不幸遭遇猎枪的嘈杂一端时会掉落什么战利品。这些掉落数据只在实体生命末尾那一刻使用一次：

```cpp
class AIComponent
{
public:
  void update() { /* ... */ }

private:
  // Previous fields...
  LootType drop_;
  int minDrops_;
  int maxDrops_;
  double chanceOfDrop_;
};
```

假设我们遵循了前面的建议，更新这些 AI 组件时，我们会遍历一个漂亮的、紧凑的连续数据数组。但那些数据包含了所有战利品掉落信息，这让每个组件更大，减少了一条缓存行能容纳的组件数量，缓存缺失增多，因为我们要遍历的内存总量更大。每帧对每个组件，战利品数据都被拉进了缓存，即便我们根本没有用到它。

解决这个问题的方案叫做"冷热数据分离（hot/cold splitting）"。思路是把数据结构拆分为两个独立的部分。第一部分存放"热"数据，即每帧都需要用到的状态。另一部分存放"冷"数据，即使用频率较低的其他所有内容。

热数据部分是*主要的* AI 组件，最常被使用，所以我们不希望追踪指针才能找到它。冷数据组件可以放在旁边，但我们仍然需要访问它，所以给热数据组件一个指向它的指针，像这样：

```cpp
class AIComponent
{
public:
  // Methods...
private:
  Animation* animation_;
  double energy_;
  Vector goalPos_;

  LootDrop* loot_;
};

class LootDrop
{
  friend class AIComponent;
  LootType drop_;
  int minDrops_;
  int maxDrops_;
  double chanceOfDrop_;
};
```

现在，每帧遍历 AI 组件时，加载进缓存的数据只有我们实际要处理的内容（除了指向冷数据的那个小小的<span name="parallel">指针</span>）。

> **注：** 我们也可以通过让冷热组件使用平行数组来去掉那个指针。这样，就可以通过索引来找到某个组件对应的冷数据，因为两个部分在各自的数组中处于相同的索引位置。

不过你会看到，这开始变得模糊了。在我的示例中，哪些数据应该热、哪些应该冷相当明显，但在真实的游戏中，这很少这么清晰。如果某些字段只在实体处于某种模式时才被使用呢？如果实体只在关卡的某些区域才用到某些数据呢？

这类优化介于黑魔法和"兔子洞"之间，很容易陷进去，花无尽的时间搬弄数据来看看速度差异。需要积累经验才能把握在哪里投入精力。

## 设计决策

这个模式实际上关乎一种思维方式——让你把数据在内存中的排布视为游戏性能的关键组成部分。具体的设计空间是完全开放的。你可以让<span name="dod">数据局部性</span>影响整个架构，也可以只在几个核心数据结构上局部应用这个模式。

> **注：** Noel Llopis 那篇引发更多人思考围绕缓存使用来设计游戏的[著名文章](http://gamesfromwithin.com/data-oriented-design)称之为"面向数据的设计（data-oriented design）"。

你需要回答的最大问题是在哪里、何时应用这个模式，但还有几个其他问题可能会出现：

### 如何处理多态？

到目前为止，我们一直避开子类化和虚方法，假设我们有漂亮的、紧凑的*同质*对象数组，知道它们大小完全相同。但多态和动态派发也是有用的工具，如何协调两者？

**干脆不用多态：**

<span name="type">最简单</span>的答案是避免子类化，或者至少在正在为缓存使用做优化的地方避免。软件工程文化本身也在远离对继承的大量使用。

> **注：** 不使用子类化也能保留多态灵活性的一种方式是[类型对象](18-type-object.md)模式。

- *安全且简单。* 你清楚地知道在处理哪个类，所有对象大小显然相同。
- *更快。* 动态派发意味着在虚函数表（vtable）中查找方法，然后追踪指针到达实际代码。虽然这个开销在不同硬件上差异很大，但动态派发确实存在<span name="cpp">*一定*</span>代价。

  > **注：** 一如既往，唯一的绝对是没有绝对。在大多数情况下，C++ 编译器需要为虚方法调用进行间接引用。但在*某些*情况下，如果编译器知道接收者的具体类型，它可能能做*去虚化（devirtualization）*，直接静态调用正确的方法。去虚化在 Java 和 JavaScript 等语言的即时编译器（JIT）中更为常见。

- *不够灵活。* 当然，我们使用动态派发的原因正是它提供了一种强大的方式来在对象之间变化行为。如果你希望游戏中不同实体有各自的渲染风格或各自的特殊招式和攻击，虚方法是建模这些行为的成熟方式。不得不把所有这些代码塞进一个非虚方法（里面可能是一个大型 `switch`）会很快变得一团糟。

**为每种类型使用独立数组：**

我们使用多态，是为了能对一个不知道具体类型的对象调用行为——换句话说，我们有一袋杂物，希望告诉里面每个对象"去做你的事"时，它们能各行其事。

但这引出了一个问题：为何一开始要把袋子弄得杂乱？为什么不为每种类型维护独立的同质集合？

- *对象紧凑排列。* 由于每个数组只包含一种类的对象，不存在填充或其他奇怪的东西。
- *可以静态派发。* 一旦按类型划分了对象，就完全不再需要多态了，可以使用普通的非虚方法调用。
- *需要跟踪一堆集合。* 如果有很多不同的对象类型，为每种类型维护独立数组的开销和复杂性会是个负担。
- *需要了解每种类型。* 由于需要为每种类型维护独立集合，你无法与*这些类的集合*保持解耦。多态的魔力之一正是它的*开放性*——与接口协作的代码可以与实现该接口的（可能很庞大的）类型集合完全解耦。

**使用指针集合：**

如果不担心缓存，这是最自然的解决方案——一个指向某基类或接口类型的指针数组。你拥有所有想要的多态，对象可以是任意大小。

- *灵活。* 使用集合的代码可以处理任何类型的对象，只要它支持你关心的接口，完全开放。
- *缓存不友好。* 当然，我们讨论其他选项的整个原因就在于此——这意味着缓存不友好的指针间接引用。但请记住，如果这段代码并不是性能关键的，这可能没什么问题。

### 游戏实体如何定义？

如果你将这个模式与[组件模式](20-component.md)配合使用，就会为构成游戏实体的所有组件拥有漂亮的连续数组。游戏循环会直接遍历这些数组，所以游戏实体对象本身不那么重要，但在代码库其他部分需要与单个概念"实体"打交道的地方，它仍然有用。

问题是：它应该如何表示？它如何跟踪自己的组件？

**如果游戏实体是持有组件指针的类：**

这就是我们第一个示例的样子——标准的面向对象解决方案。你有一个 `GameEntity` 类，它持有指向所拥有组件的指针。由于只是指针，它对组件在内存中的位置和组织方式没有要求。

- *可以把组件存储在连续数组中。* 游戏实体不关心组件在哪里，所以你可以把它们组织在一个紧凑的数组中，以优化遍历。
- *给定一个实体，可以轻松访问其组件。* 只需一次指针间接引用。
- *在内存中移动组件很麻烦。* 当组件被启用或禁用时，你可能想在数组中移动它们，以保持活跃的在前面且连续排列。但如果你在实体持有原始指针的情况下移动组件，如果不小心，那个指针就失效了，必须确保同时更新实体的指针。

**如果游戏实体是持有组件 ID 的类：**

持有组件原始指针的挑战是，这让在内存中移动组件变得困难。可以用更抽象的东西来解决：一个可以用来*查找*组件的 ID 或索引。

ID 和查找过程的实际语义由你决定。可以简单到在每个组件中存储一个唯一 ID 并遍历数组，也可以复杂到用将 ID 映射到其在组件数组中当前索引的哈希表。

- *更复杂。* ID 系统不必是火箭科学，但仍然比基本的指针多更多工作，需要实现和调试，并有内存开销用于记账。
- *更慢。* 很难打败直接追踪原始指针。从实体到其某个组件可能需要一些搜索或哈希。
- *需要访问组件"管理器"。* 基本思路是有一个抽象 ID 来标识组件，用它可以获取实际组件对象的引用。但要做到这一点，需要把 ID 交给某个实际能找到组件的东西——那就是包裹着你原始连续数组的那个类。有了原始指针，给定一个游戏实体就能找到其组件；用这种方式，则<span name="singleton">需要</span>游戏实体*和*组件注册表。

  > **注：** 你可能在想"把它做成单例不就行了！问题解决！"嗯，算是吧。不过你可能得先看看[关于单例的那一章](09-singleton.md)。

**如果游戏实体*本身*就是一个 ID：**

这是一些游戏引擎使用的较新风格。一旦你把实体的所有行为和状态从主类移到组件中，还剩下什么？结果是，没多少。实体唯一做的事就是把一组组件绑在一起，只是为了说：*这个* AI 组件、*这个*物理组件和*这个*渲染组件定义了世界中一个活生生的实体。

这一点很重要，因为组件之间会互动：渲染组件需要知道实体在哪里（可能是物理组件的属性），AI 组件想要移动实体（需要对物理组件施加力）。每个组件都需要一种方式来访问它所属实体的其他兄弟组件。

一些聪明的人意识到，为此你只需要一个 ID。与其由实体了解其组件，不如让组件了解其实体——每个组件都知道拥有它的实体的 ID。当 AI 组件需要其实体的物理组件时，只需请求持有相同实体 ID 的物理组件即可。

你的实体*类*完全消失，取而代之的是一个围绕一个数字的包装器。

- *实体很小。* 传递游戏实体的引用时，只是一个单值。
- *实体是空的。* 当然，把所有东西都从实体移出的缺点是：你*必须*把所有东西都从实体移出，不再有地方放置非组件专属的状态或行为。这种风格在[组件模式](20-component.md)上孤注一掷。
- *不需要管理其生命周期。* 由于实体只是简单的值类型，不需要显式分配和释放。当实体的所有组件都被销毁时，实体隐式地"死去"。
- *查找某实体的组件可能很慢。* 这与上一个方案的问题相同，但方向相反。要找到某实体的组件，需要将 ID 映射到对象，这个过程可能代价高昂。这一次，它*确实*是性能关键的——组件在更新时经常与兄弟组件互动，所以需要频繁查找组件。一个解决方案是让实体的"ID"就是组件在其数组中的索引。如果每个实体都有相同的组件集合，组件数组就完全是平行的——AI 组件数组第三个槽里的组件，与物理组件数组第三个槽里的组件属于同一个实体。但请记住，这*强制*你保持这些数组平行，而如果你想按不同标准进行排序或紧凑处理，这就很困难了。某些实体可能禁用了物理，另一些可能不可见，如果物理和渲染组件数组必须保持同步，就无法针对两种情况都做最优排序。

## 参考

- 本章的大量内容围绕[组件模式](20-component.md)展开，而组件模式确实是最常见的针对缓存使用做优化的数据结构之一。事实上，使用组件模式让这种优化变得更容易：由于实体是一次一个"领域"（AI、物理等）地更新，将它们拆分为组件让你可以把一堆实体切成正确的片段，以实现缓存友好。但这不意味着你*只能*在组件中使用这个模式！任何时候，当你有性能关键的代码需要处理大量数据时，思考局部性就很重要。
- Tony Albrecht 的[《面向对象编程的陷阱》](http://research.scee.net/files/presentations/gcapaustralia09/Pitfalls_of_Object_Oriented_Programming_GCAP_09.pdf)大概是最广为阅读的、介绍如何为缓存友好性设计游戏数据结构的入门文章，让包括我在内的更多人意识到了这对性能有多大影响。
- 大约同一时期，Noel Llopis 写了一篇[极具影响力的博客文章](http://gamesfromwithin.com/data-oriented-design)，讨论了同一话题。
- 这个模式几乎无一例外地利用同质对象的连续数组。随着时间推移，你很可能会不断向该数组添加和移除对象，而[对象池](26-object-pool.md)模式正是专门讨论这个问题的。
- [Artemis](http://gamadu.com/artemis/) 游戏引擎是最早、也是最著名的将简单 ID 用于游戏实体的框架之一。
